A GENTLE INTRODUCTION

大语言模型，
到底是怎么"想"的？

这是一份给完全不懂数学和机器学习的读者的指南。
我们会从"模型怎么猜下一个字"开始，一直讲到训练、采样、幻觉、上下文窗口。

预计阅读 25 分钟 12 章 · 含动画图解 无需任何前置知识
CHAPTER 01

先用一句话讲清：LLM 到底在干什么

所有听起来吓人的术语——Transformer、Attention、Embedding——其实都是为了一件极其简单的事情服务的。

大语言模型（Large Language Model，简称 LLM），本质上是一个极其擅长猜下一个字的程序。

就这一句话。其他所有东西，都是这件事的支撑。

类比 · 手机输入法

当你在手机上打"今天天"，输入法会建议"气"。LLM 做的事情和这个本质上完全相同。区别只是：它读过的文本比任何一个人类一辈子能读完的都多得多，所以它"建议"的水平能写论文、写代码、回答你各种各样的问题。

这件事最让人意外的地方在于：仅仅靠"不停地猜下一个字"这一个简单任务，居然涌现出了推理、翻译、创作、数学、编程……几乎所有我们认为需要"智能"的能力。

没有人完全理解为什么会这样。但事实就是这样。

所以接下来的所有章节，你都可以带着这一个问题去读：

为了让一个程序能够准确地猜出下一个字应该是什么，需要做哪些事？
CHAPTER 02

Tokenizer：把文字切成模型能"吃"的小块

模型不认识汉字，也不认识英文字母。它只认识数字。所以第一步，必须把文字翻译成数字。

这个翻译器叫 Tokenizer（分词器）。它把一段文字切成若干个 token（语言碎片），然后把每个 token 替换成一个数字 ID。

但它不是一个字一个 ID。它会把高频出现的组合切成一个 token，低频的拆得更细。

我喜欢吃苹果
↓

上面这个动画展示了一个简化的分词过程。真实的分词器（比如 GPT 用的 BPE）规则更复杂，但思想是一样的：

  • "你好" 这种超高频组合，可能就是一个 token。
  • 英文 "unbelievable" 可能被拆成 un / believ / able 三个 token。
  • 生僻字、表情符号往往会被拆成更多 token。

每个 token 在词表（vocabulary）里有一个固定编号。比如 GPT-4 的词表大约有 10 万个 token，LLaMA 3 是 12.8 万。

为什么不一个字一个 ID

因为这样词表会变得极大（几万个汉字 + 各种符号 + 多语言），而且每个句子的 token 数量会变多，模型处理效率变低。BPE 这种"按高频组合切"的方法，是个巧妙的折中。

你用 ChatGPT 被"按 token 计费"，就是按这里的 token 数量算的。粗略地说：

  • 英文：1 个单词 ≈ 1.3 个 token
  • 中文：1 个汉字 ≈ 1.5-2 个 token

但请注意：中文更费 token，不是中文本身的特性，而是因为主流模型的 tokenizer 是为英文优化的。核心逻辑链是：

英文语料占比高 → BPE 算法给英文分配了大量专属 token → 英文常用词大多数都是 1 个 token。

中文语料占比低 + 词表空间有限 → 中文只有极少数高频词有专属 token → 大多数词被拆成单字 → 生僻字甚至会触发"字节回退"被拆成 3 个 token。

如果未来有模型用 50% 以上中文语料训练，并专门为中文设计词表，中文的 token 效率完全可以反超英文。这不是技术问题，是路径选择的结果。

CHAPTER 03

Embedding：给每个词一个"坐标"

光有 ID 还不够。"14523" 这个数字本身没有任何含义。模型需要知道"苹果"和"香蕉"是相似的、和"宇宙"是不同的。

解决方案：把每个 token ID 映射成一个高维向量。

"高维向量"这个词听起来吓人，其实你只需要想象一张地图。地图上每个词都有一个位置：

  • "苹果" 和 "香蕉" 离得很近（都是水果）
  • "苹果" 和 "iPhone" 也不远（都跟苹果公司有关）
  • "苹果" 和 "宇宙" 离得很远
FIG.1 — 在向量空间里，相似的词聚在一起

真实的模型用的不是 2D，而是几千维（LLaMA 3 8B 是 4096 维，GPT-3 是 12288 维）。

我们没法画 4096 维，但概念完全一样：相似的词在向量空间里的位置靠近。这种"用位置表达含义"的方式，是模型理解语言的基础。

这张"地图"叫什么

它叫 Embedding 矩阵，本质上是一张超大的查找表，形状是 [词表大小, 向量维度]。LLaMA 3 8B 这张表是 128256 × 4096，光这一层就有 5 亿多参数，占模型总参数的 6%。

所以，整个流程到这里变成了：

"我喜欢吃苹果"
     ↓ Tokenizer
[1023, 4521, 89, 7733]      ← token ID
     ↓ Embedding 查表
[[0.2, -0.5, 0.8, ...],     ← 每个 token 一个向量
 [-0.1, 0.3, 0.4, ...],
 [0.7, 0.1, -0.2, ...],
 [0.5, -0.3, 0.6, ...]]

下一步，这堆向量要被送进模型的"大脑"——Transformer。

CHAPTER 04

Attention：模型读一句话时，眼睛在哪里

整个 Transformer 最核心、也是最聪明的设计，就是这一个机制：注意力（Attention）。

请你读这句话，并思考"他"指的是谁：

小明把苹果给了小红，因为他饿了。

大多数人会说"小明"——因为是小明把苹果给出去了，所以肯定是小明饿了。但请你换一句：

小明把苹果给了小红，因为他不爱吃。

这次"他"就指小明。"他"具体指谁，取决于上下文。

那模型怎么处理"他"这个词？答案是：在处理"他"的时候，让它看一眼整个句子里所有其他词，然后决定该重点关注哪一个。

小明 把 苹果 给了 小红 因为 他 饿了
↑ 处理"他"时，attention 会把更多权重分给相关的词

这就是 Attention 的核心：每个词都会和其他所有词建立一种"加权联系"。权重高的，意味着两个词在当前语境下相关性强。

这不是被人写死的规则，而是模型在阅读了海量文本之后，自己学出来的关联模式。

为什么这个机制这么强大

因为它解决了"长距离依赖"这个老大难问题。在 Attention 之前的模型，一个词只能"记得住"几步之内的前文，超过就忘了。Attention 让模型可以一次"看到"上千个词，并直接和最相关的几个建立联系——不管它们离当前位置多远。

顺便一提，"Attention is all you need" 是 2017 年 Google 那篇论文的标题。这篇论文提出了 Transformer 架构，成为之后所有 LLM 的基础。

CHAPTER 05

Transformer：一条加工信息的流水线

Attention 是核心，但它通常不是单独工作的。它和另一个组件配合，被堆成几十层，组成完整的 Transformer。

每一层 Transformer 做两件事：

  1. Attention：让每个词和所有其他词交流信息。
  2. Feed-Forward Network (FFN)：对每个词单独做一些非线性的"加工"，提取更高层的信息。

这一对组合叫一个 Transformer Block。LLM 通常会把几十个 Block 堆叠在一起：

第 32 层 (深) 高层语义
第 31 层
第 30 层
…
第 16 层 (中) 句法 / 短语
…
第 2 层
第 1 层 (浅) 字面 / 词法

层数越深，处理的概念越抽象。

浅层在做"识字"——这个词长什么样、有哪些常见搭配。

中层在做"读句子"——理解短语结构、句法关系。

深层在做"想意思"——把握语义、做推理、保持语境一致。

LLaMA 3 8B 有 32 层，70B 版本有 80 层，GPT-4 据信超过 100 层。

每一层都不是从零开始，而是在前一层的基础上加工。所以输入向量经过几十层之后，已经是一个"包含了全句理解 + 上下文 + 推理痕迹"的浓缩向量。

最后一层输出的，就是我们需要的"模型对每个位置的最终判断"。然后我们要做的事情，就是把这个判断变回文字。

CHAPTER 06

输出层：从向量回到文字

Transformer 输出的还是一堆向量。我们需要的是字。这中间隔了三步：lm_head → softmax → 采样。

请把注意力放到最后一个 token 的位置上。这个位置上的向量，浓缩了模型对"下一个字应该是什么"的全部判断。

第一步：lm_head（语言模型头）

这是一个简单的线性层（一次矩阵乘法）：把这个向量映射成一个长度等于词表大小的数字列表，叫做 logits。 

logits = [2.1, -0.5, 8.3, ..., 0.7]
           ↑     ↑    ↑          ↑
          token token token     token
           1    2    3          128256

每个数字代表词表中对应 token 的"得分"。得分越高，模型越认为它适合作为下一个字。

第二步：softmax（归一化为概率）

logits 是任意数字，没法直接比较。Softmax 把它们转换成概率分布——所有数字加起来等于 1：

输入: "今天天气真" _
好
68%
不错
15%
糟糕
8%
冷
5%
热
3%
…其余
1%

第三步：采样（从概率里挑一个）

有了概率分布，怎么决定输出哪个？这一步叫"采样"，有几种常见策略：

策略 行为 效果
Greedy 永远选概率最高的 稳定但可能重复、单调
Temperature 调节分布的"陡峭程度"，T 越大越随机 控制创造力
Top-k 只在概率最高的 k 个里随机 避免低概率胡说
Top-p 累计概率到 p 的最小集合里随机 动态截断，最常用
为什么同样的问题答案不一样

因为采样有随机性。即使是同一个 prompt，每次模型走到这一步，都可能挑到不同的 token。如果你设置 temperature=0（也就是 Greedy），输出会变得确定。

采样选出一个 token 之后，用 tokenizer 反向解码，就能把它变回一个汉字或英文片段。这就是模型吐出的第一个字。

CHAPTER 07

自回归：一个字一个字蹦出来

LLM 一次只能生成一个 token。要生成一段话，就要把前面全部流程反复跑很多遍。

生成出第一个 token 后，把它接到输入末尾，再走一遍整个网络，生成第二个 token。然后再接、再走……如此循环，直到模型生成结束符或达到长度上限。

今天天气真 
循环：
  输入 → Transformer → 下一个 token
  把 token 拼到输入末尾
  再次输入 → Transformer → 下一个 token
  ...
  直到生成 <EOS> 或达到 max_tokens

这种"用自己的输出作为下一步的输入"的方式叫自回归（autoregressive）。

为什么 ChatGPT 像在打字

不是网络慢，而是模型真的就是一个 token 一个 token 算出来的。每生成一个就通过 SSE（流式响应）推一次给浏览器，所以你看到的是"边算边发"的效果。如果等全部算完再发，体验会非常差——一段几百字的回答可能要等十几秒才看到第一个字。

顺带一提，这也解释了为什么"思维链"（Chain-of-Thought）有用——让模型先输出推理过程再给答案，相当于给它更多"思考用的字符"，每一步推理都成为后续生成的输入，最终答案也就更准。

CHAPTER 08

KV Cache：让重复计算消失

上一章的自回归循环里藏着一个看起来很浪费的问题——每生成一个新 token，难道都要把整段历史重新算一遍？现代 LLM 用一个聪明的优化解决了它。

假设你已经和模型聊了 1000 个 token，现在它要生成第 1001 个。理论上，每出一个新 token，都要把前面 1000 个重新过一遍 attention，算它们各自的 K、V、再做一次完整的注意力运算。

但实际上，历史 token 的 K 和 V 在每一步里都是一样的。我们没必要重新算——把它们存起来重复使用就行。

这就是 KV Cache（键值缓存）。它是几乎所有 LLM 推理引擎里的默认优化。

先认识 Q / K / V 三个角色

要看懂 KV Cache，得先简单了解 attention 内部的三个向量。每个 token 进入 attention 时，会被投影成三个不同的向量：

Q
QUERY
我现在想找什么
当前 token 主动发起的"检索请求"，决定它要关注哪些历史信息。
K
KEY
我能被怎样检索到
每个 token 提供的"索引/标签"，用来和 Q 做匹配，决定相关性高低。
V
VALUE
我真正提供什么内容
每个 token 携带的"实际信息"，会按 Q·K 算出的权重被加权聚合。
类比 · 图书馆找书

Q 是你脑子里的检索需求（"我要找法国首都"）；K 是每本书的目录卡（"地理 / 欧洲 / 法国"）；V 是书里实际的文字（"巴黎是法国首都"）。Attention 就是：拿着 Q 和所有 K 配对 → 看哪些最相关 → 把对应的 V 加权拿出来。

为什么只缓存 K 和 V，不缓存 Q

这是 KV Cache 这个名字的核心。关键在于它们的"生命周期"完全不同：

  • K 和 V：一旦计算出来，后续每一步都要拿来用。第 1000 个 token 的 K/V，要被第 1001、1002、1003……每一次新生成都查一遍。这种东西最值得缓存。
  • Q：只在当前这一步用一次。下一步会被新 token 自己的 Q 取代，老的 Q 永远不会再被用到。缓存它毫无意义。

所以名字叫 KV Cache，而不是 QKV Cache。Q 不重要吗？非常重要——只是它"用完即弃"。

FIG.A — KV Cache 内部：新 token 的 Q 与所有历史 K/V 做注意力

缓存带来的速度差距

WITHOUT KV CACHE
每步都重算所有历史
  • 每生成 1 个 token，对前面所有 token 重新计算 K/V
  • 有了 N 个 token，下一步要算 N 次
  • 整段生成累计是 N²
总计算量：O(N²) · 慢
WITH KV CACHE
只算新 token，旧的查表
  • 每生成 1 个 token，只算它自己的 Q/K/V
  • 历史 K/V 从缓存里直接读
  • 每步成本恒定
总计算量：O(N) · 快

对长上下文来说，这个差距是天文级的。1 万 token 的对话，KV Cache 能让推理快 百倍以上。这也是为什么 ChatGPT 能"边算边吐字"——没有这个优化，体验上几乎不可用。

FIG.B — Prefill 一次性算全 Prompt 的 K/V，Decode 阶段每步只算新 token

天下没有免费的午餐

KV Cache 是经典的"用空间换时间"。它要把每一层、每个注意力头、每个历史位置的 K 和 V 都存进 GPU 显存。缓存大小和这些因素成正比：

因素 影响
序列长度 线性增长，最直接的成本来源
模型层数 每一层都要单独缓存（LLaMA 70B 有 80 层）
注意力头数 每个 head 都要缓存自己的 K/V
隐藏维度 K/V 向量越长，每个位置占的字节越多
数据精度 fp16 vs fp8，差一倍显存

所以你会看到这种现象：

  • 上下文窗口越长，KV Cache 越大，越吃显存
  • 长对话或长文档处理，往往是显存先撑不住，而不是算力不够
  • 百万 context 模型推理成本极高，光存 KV Cache 就要专门的显存策略
这就是 LLM 推理优化的主战场

近几年大半的推理加速研究都在围绕 KV Cache 做文章：分页缓存（PagedAttention）、量化压缩（KV 8-bit / 4-bit）、滑动窗口（只保留最近 N 个 token）、跨请求复用……目的都是让这块缓存更小、更高效。

现在再回头看上一章的"自回归一个字一个字蹦"，你会发现它不只是个流程描述——它解释了为什么 KV Cache 是 LLM 推理性能的命脉。

CHAPTER 09

训练 vs 推理：模型怎么"学会"这一切的

到目前为止讲的都是"推理"——也就是模型已经训练好之后，怎么用它生成文字。但模型一开始的能力是哪来的？答案是：训练。而训练分三个阶段。

STAGE 01
预训练
Pre-training
喂海量文本（互联网、书籍、代码、维基百科），让模型反复练习"猜下一个字"。
数据：上万亿 token
成本：数百万至上千万美元
类比：读完整个图书馆
STAGE 02
监督微调
SFT (Supervised Fine-Tuning)
预训练后的模型擅长接龙，但不会"听话回答问题"。给它一些高质量的"问题-答案"样本，让它学会回答风格。
数据：几万至几十万条
成本：相对较低
类比：读教材学怎么答题
STAGE 03
人类反馈强化学习
RLHF
让人类对模型的多个回答打分，训练一个"打分模型"，再用它引导主模型生成更受人类欢迎的回答。
数据：几十万对偏好
成本：人力为主
类比：上岗实习被老板调教

每一步都至关重要：

  • 没有预训练，模型连基础语言能力都没有。
  • 没有 SFT，模型只会接龙，不会回答你的问题。
  • 没有 RLHF，模型可能给出技术正确但毫无用处或有害的回答。
ChatGPT 为什么火

2020 年 GPT-3 已经存在，但只有研究者觉得它惊艳。普通人觉得它"乱说"。2022 年底 ChatGPT 发布之所以引起轰动，关键就是 OpenAI 在 GPT-3.5 上做了大量 SFT + RLHF，让模型变得"听话、有用、不胡说"。模型基础能力没大变，但"使用体验"完全是另一回事了。

训练完成后，模型的所有"知识"都被压缩进了它的参数（也就是那几十亿、几千亿个浮点数字）。之后所有的"推理"都不再修改这些参数——它就是一个静态的、巨大的、可查询的"压缩知识库"。

CHAPTER 10

几个常见疑问

读到这里，你应该已经能回答很多关于 LLM 的问题了。下面是一些最常被问到的。

为什么 LLM 会"幻觉"（一本正经胡说八道）？
因为它本质是在猜"下一个字最可能是什么"。当它没真正读过相关内容时，会按"看起来对"的统计模式硬编一个出来。它没有"我不知道"的本能——除非训练时被特别教导过遇到不确定时要承认。这就是为什么模型会自信地编出不存在的论文、API、人名。
"上下文窗口"是什么？为什么有上限？
模型一次能"看到"的 token 总数上限。GPT-4 是 128k，Claude 是 200k+。超过了，最早的内容就会被截断或压缩。

有上限有两个原因：一是 Attention 计算量随序列长度平方增长（处理 prompt 时尤其明显）；二是上一章讲的 KV Cache 显存占用随长度线性增长，并且乘以层数和注意力头数。所以长上下文模型不只是算得慢，还非常吃显存。
"70B 参数"是什么意思？参数越多越好吗？
参数 = 模型里所有可训练数字的总量。70B = 700 亿。这些数字大部分藏在 Embedding 矩阵、Attention 矩阵、FFN 矩阵里。

参数越多，理论容量越大、能记住的东西越多，但也更慢、更贵、对训练数据要求更高。所以小模型 + 高质量数据 + 巧妙训练，有时能赶上大模型。这也是为什么近年 7B、8B 的小模型也能很能打。
为什么模型有时会"自我纠正"？
当它在生成过程中产生错误后，后续的 token 会基于这些错误继续——但有时模型会在某个时刻"注意到"前后不一致，然后说"等等，我刚才搞错了"。这是大量训练数据中存在"自我纠正"模式造成的涌现能力，没人专门教过它要怎么做。
RAG（检索增强生成）和模型本身是什么关系？
模型训练时有"知识截止日期"，之后的事它不知道；公司内部知识它也没读过。RAG 的做法：用户问问题时，先去外部知识库查相关文档，把找到的内容塞进 prompt 里，再让模型基于这些上下文回答。这样模型不需要重新训练，就能回答新知识或私有知识。

这里的"检索"通常用一种和 LLM 不同的 embedding 模型——它把整段文字压成一个向量，用于相似度搜索。和 LLM 内部的 embedding 层不是一回事。
Agent 又是什么？
Agent = LLM + 工具 + 循环。给模型几个可以调用的工具（搜索、运行代码、调 API），让它自己决定调哪个、看结果后再决定下一步——直到任务完成。本质还是"猜下一个字"，但模型猜出来的"字"可能是一个工具调用指令，而不是给用户看的回复。
