🏗️ 四层记忆架构

L1

Working Memory 工作记忆

当前会话的即时上下文，滑动窗口保留最近消息。

  • 存储：Redis List
  • 容量：20 条消息滑动窗口
  • TTL：2 小时自动过期
  • 特征：零延迟读写，支持 RENAME 原子排空
Redis List Sliding Window
L2

Pending Queue 待处理队列

积累待摘要的消息批次，批量触发 LLM 压缩。

  • 存储：Redis List
  • 触发：达到 batch-size 后触发摘要
  • TTL：2 小时
  • 特征：异步解耦，防止频繁 LLM 调用
Redis List Batch Trigger
L3

Episodic Memory 情景记忆

压缩后的长期记忆片段，支持语义向量检索。

  • 存储：PostgreSQL + pgvector
  • 索引：HNSW + 余弦距离
  • 维度：1024 维向量
  • 特征：语义检索，importance 衰减管理
PGVector HNSW 1024-dim
L4

User Profile 用户画像

从记忆中提炼的长期偏好和身份信息。

  • 存储：Redis Hash
  • TTL：30 天
  • 注入：格式化后写入 System Prompt
  • 特征：Reflection 提炼，永不淘汰
Redis Hash System Prompt

⚡ 事件驱动流水线

消息进入系统后，通过 Spring Event 机制驱动各阶段异步处理，实现最终一致性。

💬 addMessage 用户消息写入 L1
→
📋 SummarizationRequestEvent 达到 batch-size 触发
→
🤖 MemorySummarizer LLM 压缩为摘要
→
📦 ConsolidationRequestEvent 触发向量存储
→
🗄️ MemoryConsolidator 写入 PGVector
→
🔮 ReflectionRequestEvent CAS 计数达阈值
→
🪞 ReflectionWorker 提炼偏好更新画像
ReflectionWorker 输出 → VectorStore (importance=0.9) + UserProfile (Redis Hash)

🧩 核心组件

MemoryService — L1 工作记忆管理

负责维护当前会话的滑动窗口，是记忆系统的入口层。

  • 滑动窗口：Redis List 维护最近 20 条消息，LPUSH + LTRIM
  • 原子排空：使用 RENAME 将 pending list 原子性切换，避免竞态
  • 本地降级：Redis 不可用时，ConcurrentHashMap 作为 fallback
  • 事件发布：消息入队后检查 batch-size，发布 SummarizationRequestEvent

MemorySummarizer — LLM 摘要压缩

监听 SummarizationRequestEvent，调用 LLM 将原始消息压缩为结构化摘要。

  • 压缩目标：约 100 字的中文摘要，保留关键信息
  • Importance 评估：LLM 同时输出 importance 评分 (0.0–1.0)
  • 降级策略：LLM 调用失败时，默认 importance = 0.3，保证流程不中断
  • 输出：发布 ConsolidationRequestEvent，携带摘要 + importance

MemoryConsolidator — 向量持久化

监听 ConsolidationRequestEvent，将摘要写入 PGVector 并触发反思计数。

  • 向量化：使用 Spring AI EmbeddingModel 生成 1024 维向量
  • 写入 PGVector：带 metadata (importance, timestamp, sessionId)
  • CAS 原子计数：使用 compareAndSet 递增反思计数器
  • 触发反思：计数达到 reflection-threshold 时发布 ReflectionRequestEvent

ReflectionWorker — 长期反思与画像更新

最高层级的记忆处理，从情景记忆中提炼用户的长期偏好和身份信息。

  • 触发条件：episode 数量达到 episode-threshold
  • LLM 分析：综合近期记忆，提取偏好模式和身份特征
  • 高重要性：reflection 记录 importance = 0.9，受到特殊保护
  • 画像更新：将提炼结果写入 UserProfileService (Redis Hash)

ImportanceDecayManager — 重要性衰减

定期扫描 L3 记忆，按指数衰减公式降低重要性评分。

  • 衰减公式：importance × 0.5^(days / halfLife)
  • 半衰期：30 天 — 即每 30 天重要性减半
  • 访问刷新：被检索命中时重置衰减计时器（"用进废退"）
  • 最低阈值：min-importance = 0.01，低于此值标记为可淘汰
  • 批量处理：每次处理 500 条，避免长时间锁表

EvictionPolicyManager — 记忆淘汰策略

清理过期和低重要性的记忆，保持存储高效。

  • 淘汰条件：importance < 0.1 且 age > 180 天
  • Reflection 保护：reflection 类型的记忆 永不淘汰，保护用户身份信息
  • 软删除：先标记，后续批量物理删除
  • 定时任务：可配置 cron 表达式定期执行

UserProfileService — 用户画像管理

管理 L4 用户画像，将画像信息格式化注入 System Prompt。

  • 存储：Redis Hash，key 格式 ai:profile:{userId}
  • TTL：30 天，活跃用户自动续期
  • 注入方式：格式化为结构化文本，拼接到 System Prompt 尾部
  • 字段：偏好、身份、习惯、关系模式等

🎯 设计决策

Architecture

事件驱动全异步 — 最终一致性

使用 Spring ApplicationEvent 机制解耦各阶段处理。消息写入 L1 后立即返回，摘要、向量化、反思均异步执行。虽然存在短暂的不一致窗口，但保证了低延迟的用户体验和系统的高可用性。

Storage

Redis + PGVector 双存储 — 热/冷分离

Redis 存储热数据（L1/L2/L4），保证毫秒级访问；PGVector 存储冷数据（L3），支持语义检索。热数据高频读写低延迟，冷数据容量大支持复杂查询，各取所长。

Safety

Reflection 永不淘汰 — 保护用户身份

Reflection 产生的记忆承载用户的长期偏好和身份信息，一旦丢失将严重影响个性化体验。通过标记 type=reflection，在淘汰策略中特殊豁免，确保核心画像数据的安全。

Algorithm

指数衰减 + 访问刷新 — "用进废退"

使用 0.5^(days/halfLife) 指数衰减公式，自然遗忘不常访问的记忆。被检索命中时重置衰减计时器，高频使用的记忆保持高重要性。模拟人类记忆的自然遗忘曲线。

Resilience

LLM 降级策略 — 失败时 importance=0.3

LLM 调用可能因网络、限流等原因失败。降级策略为失败的摘要赋予中等重要性（0.3），既不会因过高重要性污染记忆池，也不会因过低被过早淘汰。保证流程不中断。
