§ 01Agent Loop 模式

所有"看起来花样繁多"的 Agent 架构 —— PlanAct、MultiAgent、CodeAct —— 都是同一个 ReAct Loop 的不同协作组织方式。先把这个根理清楚，再看上层 Pattern 就不会眼花。

1.1 一切始于 ReAct

ReAct = Reason + Act。一个 Agent 在每个 Turn 里做两件事：先推理下一步该干什么（产出思考与工具调用），再执行工具拿到观察结果。把观察送回模型，进入下一个 Turn。如此循环，直到模型决定停下（输出最终答复 / 调用一个"完成"工具 / 满足外部停止条件）。

这个循环本身没什么花哨的。但所有后续的 Agent 架构都可以被还原成"一个或多个 ReAct Loop 之间的协作模式"。理解这点，就理解了大半 Agent 工程。

1.2 三种衍生模式

常见的三种"Agent 架构"，本质都是 ReAct 的不同实现：

VARIANT 01
PlanAct

把 Reason 拆成两步：先 Plan 出多步计划，再按计划执行。计划失败或环境变化时回到 Reason 重规划。

适用：任务步骤明确、可分解、单 Agent 能完成。

VARIANT 02
MultiAgent

多个 ReAct Loop 协同工作，彼此通过消息 / 工具调用 / 共享上下文交流。下一节专题讲它的四种 Pattern。

适用：任务需要多个角色 / 跨领域知识 / 显式并行。

VARIANT 03
CodeAct

把 Act 阶段从"调用结构化 Tool"换成"生成并执行代码"。代码 = 工具的超集，可组合、可循环、可控制流。

适用：需要逻辑组合、变量传递、批量动作的任务。

核心洞见

这三者不是互斥的，可以叠加：一个 MultiAgent 系统的某个 sub-agent 完全可以用 CodeAct，而每个 sub-agent 内部也可以是 PlanAct。真正的设计选择是"什么职责该用哪种 Pattern"，不是"我要做一个 PlanAct 系统还是 MultiAgent 系统"。

1.3 MultiAgent 的四种 Pattern

MultiAgent 不是单一模式，而是一族协作模板。常见有四种：

PATTERN A
Agent Handoff

当前 Agent 判断"这个任务不该我做"，把控制权移交给另一个 Agent，自己退出。上下文随之转交。

类比：客服转接，前一位挂线，新坐席接手。

典型：OpenAI Swarm 的 handoff 设计。

PATTERN B
Agent As Tool

把一个 Agent 当作工具注册给另一个 Agent。调用时同步等返回，调用方继续保留控制权。

类比：函数调用，子函数返回值，主函数继续。

典型：Claude Code 的子 Agent（Agent tool）。

PATTERN C
Leader & N Workers

一个 Leader 拆解任务并分发给多个 Worker 并行执行，最后汇总结果。Leader 通常本身也是 Agent，Worker 多为短生命周期 sub-agent。

类比：MapReduce。

典型：Anthropic 多步研究系统、并行代码 review。

PATTERN D
Agent2Agent (A2A)

多个对等 Agent 通过标准协议直接通信，没有显式的主从关系。强调跨平台互操作。

类比：邮件 / RPC 协议层。

典型：Google A2A 协议、跨组织 Agent 互联场景。

1.4 LoopSession 与 LoopTurn

把"Agent 在跑"这件事拆细，得到两个核心运行时概念：

LoopSession
一次完整的 Agent 会话生命周期。从用户输入到任务结束（或用户主动停止）的全部 Turn 序列，对应一份持久化的上下文 / 状态 / 中间产物。Session 之间可以恢复、克隆、分支。
LoopTurn
Session 中的一次"模型调用 + 工具执行"原子单位。每个 Turn 都是「Model Call → Tool Call(s) → Observation」三件套，结果回流到下一 Turn 的输入。

为什么要 Batch

同一个 Turn 内，模型可以一次性发出多个工具调用（如同时读 3 个文件）。运行时并行执行，把所有 observation 合并后再进入下一个 Turn。显著减少 Turn 数 → 减少 Model Call → 降低延迟与成本。这是现代 Agent 性能的关键优化。

1.5 控制原语：Steer · Followup · Interrupt

用户不是"输入 prompt → 等结果"的被动方。在 Loop 运行中，他需要能主动施加三种控制：

PRIMITIVE 01
Steer · 引导

在 Agent 已经开始执行任务的过程中注入新的指令或约束，但不打断当前 Turn。"顺便也看一下 X" / "改用 Y 风格"。

通常通过追加到下一个 Turn 的上下文实现。

PRIMITIVE 02
Followup · 追问

Agent 已完成一轮任务后，用户基于结果继续提问或扩展。前一轮的全部上下文、产出物均可复用。

从运行时看，这是同一 Session 内开启新 Turn 序列。

PRIMITIVE 03
Interrupt · 打断

用户立即叫停当前正在跑的 Turn（甚至 Tool 执行）。需要明确的语义：是中止整个 Session，还是仅当前 Turn，是否保留已产生的副作用。

关键：Interrupt 必须能被 Tool 层感知并优雅退出，否则副作用难以回滚。

1.6 多 Turn 上下文压缩

长 Session 的最大敌人是上下文爆炸。每个 Turn 都把历史 observation 追加进去，几十个 Turn 后 token 数轻松破 10 万。一个成熟的 Agent 框架必须提供上下文压缩机制。

常见压缩策略

策略 做法 保留内容 损失
Sliding Window 只保留最近 N Turn 近期上下文完整 早期信息直接丢失
Summarization 用模型把历史压成 summary 核心结论 / 决策 细节、措辞、未被认为重要的事实
RAG-Style 检索 历史进向量库，按需检索 相关片段精准回召 依赖检索质量；冷启动差
结构化抽取 抽取 facts / decisions / TODO 等结构化记忆 关键事实 / 状态 叙事流失，需 schema 设计
Tool-Result Pruning 只保留最新一次 tool 调用结果，旧结果丢弃或摘要 当前可用状态 "为什么走到这一步"的过程
实战建议

没有一种策略普适。生产 Agent 通常是组合策略：核心 facts 用结构化抽取持久存；最近 Turn 用 sliding window；远期工具结果做摘要。压缩本身要可观测、可回滚，否则会变成隐形 bug 源头。

1.7 HITL：Middleware 与 StopReason

HITL = Human In The Loop。生产 Agent 不可能完全自治 —— 在关键节点必须能让人介入。HITL 不是一两个 if-else 能搞定的，需要架构级支持。

Middleware 机制：把"人"装成插件

把 Loop 的每个生命周期阶段做成可插拔的 hook 点，HITL 就是注册在这些 hook 上的中间件：

HOOK 01
PreTurn

每个 Turn 开始之前触发。可以修改即将送入模型的上下文、注入 system 提醒、做权限检查、决定是否跳过本 Turn。

用例：风险审计、配额检查、动态注入指令。

HOOK 02
MidTurn

模型已经产出工具调用、即将执行之时触发。可以审批每个 tool call、修改参数、拦截危险操作。

用例：高风险工具的二次确认（写文件、发邮件、转账）。

HOOK 03
PostTurn

本 Turn 全部结果回流后、下一 Turn 开始之前触发。可以审查 observation、终止 Loop、修改要传给下 Turn 的内容。

用例：质量门、回归检测、按结果决定是否退出。

StopReason：定义"为什么停下来"

Loop 退出的原因不止一种。一个良好设计的运行时会用枚举型 StopReason明确区分，让上层调用者据此决定后续动作：

StopReason含义调用者通常做什么
end_turn模型输出了"最终答案"展示给用户，等待新输入
tool_use暂停以等待人工审批 tool 调用渲染审批 UI，得到结果后 resume
max_tokens触达上下文 / 输出 token 上限提示用户 / 触发压缩 / 重启
stop_sequence命中预设停止符按业务语义处理
interrupt外部 / 用户主动打断清理副作用，保留可恢复点
errorTool 异常 / 模型异常 / 框架异常记录 + 重试 / 升级
policy_block被 Middleware 阻止展示阻止原因，请求确认
设计要点

StopReason 不应该和 final_answer 这种业务概念混在一起。它是运行时的协议，告诉调用者发生了什么以及该不该 resume；业务语义应该解析输出内容自己得出。把这两层分清楚，Loop 才能复用。

1.8 Stop-Resume vs Hang-Wait

HITL 的实现可以分成两大流派，区别在于"等待人决定"这段时间，Agent 进程占不占资源"：

MODE A
Stop-Resume · 停下来再继续

命中 HITL 节点后，Agent 持久化全部状态 → 进程退出 / 释放资源。人决策完毕后，调用 resume 接口，加载状态从断点继续。

优点：等多久都不耗资源；天然支持跨天审批；适合无服务器架构。

难点：状态必须可序列化（包括 Tool 的中间态、模型的 streaming 缓冲、外部句柄等）。

MODE B
Hang-Wait · 挂起等待

命中 HITL 节点后，Agent 进程继续活着，阻塞在等待信号。人决策的回调直接唤醒原进程，状态在内存里。

优点：实现简单，无需可序列化的状态机；Tool 句柄、连接都活着。

难点：进程长期占用；崩溃即丢；不适合长时间审批。

维度Stop-Resume 更适合Hang-Wait 更适合

1.9 StopReason ↔ SSE 事件矩阵EXPAND

§ 1.7 已定义 StopReason；§ 3.1 又会讲到 SSE 通道。两者之间的桥是事件序列：客户端收到的并不是"任务结果"，而是按时间排列的 SSE 事件，最后由某一个事件触发 StopReason 闭环。下表给出最常见的对应关系：

StopReason典型 SSE 事件序列客户端应该做什么
end_turn message_start → N× content_block_delta → content_block_stop → message_stop 渲染最终回答 + 解锁输入框
tool_use …content_block_start{type:tool_use} → input_json_delta×N → message_stop(stop_reason=tool_use) 执行工具 → 把 tool_result 拼回上下文，发起下一 Turn
max_tokens …message_stop(stop_reason=max_tokens) 提示用户"输出被截断"，提供"继续"按钮或自动续写
refusal content_block_delta(type:refusal) → message_stop(stop_reason=refusal) 显示拒绝原因，不要再续写该 Turn
pause_turn …message_stop(stop_reason=pause_turn) 这是断点续传信号（如长 tool_use 链中段），客户端原样回传以续跑
interrupted HTTP 流被客户端主动断开 / AbortController.abort() 本地标记 Turn 失败 + 提示用户已停止；副作用按 § 1.12 处理
设计要点

StopReason 是协议层的状态机，SSE 事件是它的"展开形式"。框架要做的是不丢事件（用 Last-Event-ID 续连，§ 3.1）+不混淆终态（一个 Turn 只允许一个 StopReason）。把这两点做扎实，UI 层就不会出现"卡在 loading"或"明明 tool_use 还没跑完就显示已完成"的灵异 bug。

1.10 Middleware 洋葱模型EXPAND

§ 1.7 提到 Middleware 是可组合的插件。它们到底怎么组合？答案是经典的洋葱模型（Koa / Express / Connect 都用同一套）：每个 middleware 同时拦截"进入"与"返回"两个方向，外层包内层，请求穿过、响应穿回。

Layer 1 · Auth身份认证 / 权限校验。最外层，拒绝就直接 short-circuit，不再向内传递。
Layer 2 · Rate Limit限流 / 配额。在 auth 之后才知道是谁，再决定能跑多少。
Layer 3 · Context Inject注入 system prompt、动态指令、工具白名单。
Layer 4 · HITL Gate风险动作拦截，按需让人审批（§ 1.11）。
Core · Model Call模型推理本体。返回后，结果按相反顺序穿回每一层 middleware。
组合性 · Koa 经验

洋葱模型的精髓不是"链式调用"，而是每个 middleware 持有 next()，调用前是 pre-hook，调用后是 post-hook。所以 logger 能记录耗时（包住 next）、cache 能在 next 之前直接返回缓存、retry 能在 next 失败后重跑。中间件之间互不感知，只通过共享的 ctx 通信。这就是为什么 Koa 出来十年后大家还在 copy 它。

1.11 HITL 审批 UI 模式EXPAND

§ 1.7 解决了 HITL 的后端机制（Middleware + StopReason），§ 1.11 关注前端审批界面怎么设计才不让人疯。三种主流模式各有场景：

PATTERN 01
Inline Approval · 行内审批

在对话流中插入一张"待审批卡片"，展示动作摘要 + diff + 关键参数，两个按钮：通过 / 拒绝。

适用：操作可读性强（如代码 patch、SQL）、单次决策、用户在线。

PATTERN 02
Side Drawer · 侧栏队列

所有待审项汇总到固定侧栏，可批量勾选、设置默认规则（"以后这类自动通过"）。

适用：高频审批、运维场景、需要把决策从对话流里剥离。

PATTERN 03
Async Notify · 异步通知

Agent 触发审批后立即落库挂起，通过 Slack / 邮件 / 工单系统通知审批人，审批结果回流唤醒 Session（典型 Stop-Resume，§ 1.8）。

适用：跨时区、需要团队会签、用户可能不在线。

共同设计原则

  • 展示 diff 而非动作描述。"将更新 user.balance" 远不如"balance: 100 → 80"清晰。
  • 给"取消并修改提示"出口。审批不只有 Yes/No，第三个选项是"否，原因是 ___"，把否决理由回写给模型当上下文。
  • 记录决策 trace。谁审的、何时、看到了什么版本的 diff、决策耗时 —— 这些是事后审计与改进 UI 的金矿。
  • 超时策略要显式。审批 10 分钟没回 → 自动拒绝？自动通过？升级到下一审批人？默认行为决定信任度。

1.12 Tool 副作用的回滚与补偿EXPAND

Tool 一旦真正执行（发了邮件、改了数据库、下了订单），就无法 ctrl+z。但 Agent 又会犯错 —— 怎么办？三种主流策略：

策略核心思想典型场景代价
Dry-Run + Confirm 所有写操作分两步：第一步只返回"将要做什么"，第二步真正提交。 不可逆动作（删除、转账、发邮件） 每个 tool 都要双倍接口；用户体验有等待
Compensating Action 每个写操作配套定义补偿操作，失败时按相反顺序触发（Saga 模式）。 多步事务、跨系统调用 补偿逻辑要严格幂等；难以覆盖"已发出去的邮件"
Snapshot + Restore 执行前对相关状态做快照（数据库行 / 文件 / 配置），失败后恢复。 本地文件 / 容器化操作 状态空间大时存储成本高；外部世界状态不可快照

实践建议

  1. 把 tool 分类：read-only / reversible-write / irreversible-write 三档。后两档强制走 HITL（§ 1.11）。
  2. 不要假装能回滚。已发邮件不能"撤回"，能做的只有"补发更正"+"通知人"。诚实告诉用户哪些是真正可逆、哪些只能补偿。
  3. 把回滚也记入 trajectory。回滚动作本身可能失败，需要可观测、可重试（§ 3.2）。
  4. 测试中故意失败。Chaos 注入：让某个 tool 执行后期失败，看回滚链是否真的能跑通。生产环境第一次出问题再调，损失太大。

§ 02Skill 范式

模型能力达到某个门槛之后，"路由到不同 Agent"这件事的性价比开始崩塌 —— 路由本身成了延迟与错误源。Skill 范式给出另一种答案：一个 ReAct Loop Agent × N 个 Skill，按需召唤经验。

2.1 从多 Agent 路由到 One Loop × N Skill

早期的 MultiAgent 系统里，"路由 Agent"是核心组件：用户输入进来，路由 Agent 决定该派给"代码 Agent / 写作 Agent / 数据 Agent"等之一。这种架构的代价：

  • 路由本身是一次 Model Call，多了一跳延迟
  • 路由错了，下游 Agent 接到不该处理的任务，失败成本高
  • 多个 Agent 各自有自己的上下文，共享与协作复杂
  • 新增能力 = 新增 Agent + 改路由规则，扩展性差

当主力模型有了足够强的判断力和工具使用能力，更朴素的做法浮现：

范式转变

One ReactLoop Agent × N Skill —— 只跑一个 Loop，所有能力打包成 Skill。Skill 不是"另一个 Agent"，而是"一份在需要时载入的经验包"。模型自己判断要不要召唤、召唤哪个。

2.2 Skill 是 Experience 的编排

Skill 不是"工具"也不是"prompt 模板"。一个完整的 Skill 通常包含：

Trigger 触发条件
什么样的用户请求会让模型决定召唤这个 Skill。通常表达为自然语言描述 + 关键词命中规则。
Workflow 工作流
这件事该按什么顺序做。比如"设计 Skill"会包含：先问需求 → 给计划 → 等批准 → 构建 → 截图验证。
References 参考资源
领域知识、模板代码、检查清单、反例库等。渐进式披露：先给概览，深入到具体步骤时再加载细节。
Templates 模板产物
可直接复制的代码骨架、文档结构等。Skill 提供"现成可改"的起点，避免每次重新发明。
Hooks 行为约定
这个 Skill 在 Loop 中需要哪些约束：是否必须先问问题、最终交付前要不要截图、是否禁用某些工具等。

所以一句话：Skill 是把"做某类事的经验"封装成可由模型在 Loop 内召唤的对象。Experience 是名词 —— 它沉淀的是人的经验，不是模型权重。

2.3 渐进式披露 · 嵌套 · 参数化

渐进式披露

Skill 不应该一上来就把所有细节灌给模型 —— 那会污染上下文、增加成本、降低注意力。理想结构是三层洋葱：

  1. 概览层：Skill 名 + 一两句话描述 + 触发条件。永远常驻。
  2. 主流程层：召唤之后载入。讲清楚整体步骤、关键决策点。
  3. 细节层：执行到具体步骤时再按需 Read。比如"现在到了截图验证步骤，去读 verification-protocol.md"。

嵌套

Skill 可以在执行过程中召唤其他 Skill。比如"产品研发"Skill 可以在编码阶段召唤"前端设计"Skill，在评测阶段召唤"指标设计"Skill。这要求 Skill 的接口是组合性的，不能假设自己是顶层。

参数化

同一个 Skill 应该能适配不同 context。设计 Skill 该能输出 mobile mockup 或 desktop mockup；代码 Skill 该能写 Python 或 Go。参数可以是 explicit 的（Skill 入参），也可以是从 conversation 推断的（"用户在 Python 项目里" → 默认 Python）。

2.4 不强绑定 Sandbox

有一种误解："Skill 需要一个隔离沙箱来执行"。事实上一个设计良好的 Skill：

  • 本质是对模型的指令 + 资源，不需要新进程
  • 需要的工具能力，复用Loop 已有的 Tool就行（文件、Bash、Web）
  • 真要隔离（比如执行不信任的代码），那是Tool 层的事，不是 Skill 层
边界划分

Skill 关心"做什么、怎么做"；Sandbox 关心"在哪儿做、能做多深"。混淆这两层，会把 Skill 设计得复杂且难以组合。

2.5 伪代码 + CodeAct 增强可控性

Skill 中的"流程描述"如果只是散文式自然语言，模型可能漏步、错序、跳过验证。一个好用的技巧：在 Skill 关键流程里嵌入伪代码，模型在 CodeAct 模式下把它执行成真实步骤。

# 伪代码示意：一个 Skill 的核心流程
def design_task(brief):
    facts = verify_facts(brief)          # P0: 先验证事实
    if not has_enough_context(facts):    # P1: 上下文不够就先问
        ask_route_shaping_questions()
    plan = make_plan(facts)              # P1.5: visible plan
    wait_for_approval(plan)
    artifact = build(plan, section_by_section=True)
    verify_self(artifact)                # P7: 三阶段验证
    show_to_user(artifact)
    return deliver()

伪代码不是给模型执行的"代码"，是给模型看的"控制流提示"。配合 CodeAct，效果远好过自然语言流程。

2.6 可评估 · 可自进化

一个 Skill 不是写完就完事。它要能被持续度量、被改进、自我打磨：

EVAL 01
可评估

每个 Skill 需要配套 eval set：一组代表性输入 + 期望产出。版本迭代时跑回归，确保没有 silent regression。

EVAL 02
可观测

记录 Skill 被召唤的频次、成功率、用户反馈、回退率、被中途打断率。这些是改进的输入。

EVAL 03
可自进化

失败 case 自动归入 anti-pattern 库；成功 case 自动归入 reference；Skill 自身被定期 review 与 refactor。

2.7 Skill ↔ MCP 的关系EXPAND

MCP（Model Context Protocol，2024 年由 Anthropic 提出）和 Skill 经常被混用。它们解决的不是同一件事：

MCP
一个传输协议。规定"模型如何发现 / 调用外部资源（工具、文件、prompt 模板）"的接口与消息格式。可以理解为"AI 的 USB-C 接口" —— 它解决互联互通。
Skill
一个经验组织模型。规定"做某类事的整套知识 / 工具 / 模板"如何打包给 Loop 召唤。它解决能力沉淀。
CHANNEL
MCP 的视角

"我有一台 GitHub server，提供 5 个 tool。任何符合 MCP 客户端规范的 Agent 都能用。"

典型实现：mcp_server_github、mcp_server_filesystem。模型只看到工具列表，不关心工具背后是哪种实现。

EXPERIENCE
Skill 的视角

"做'Postmortem 写作'这件事，包括：先查 incident log → 然后召集相关 commit → 按模板填 5 个段落 → 让 owner review。"

典型实现：Skill 内部可能用 MCP 工具，但 Skill 本身额外打包了流程 / 模板 / 检查清单 / 反例。

一句话

MCP 是基础设施，Skill 是上层组织。一个 Skill 可以调用若干 MCP 工具；一个 MCP server 可以被多个 Skill 复用。两者正交、互补，不是替代关系。

2.8 Skill 版本化与依赖管理EXPAND

Skill 是会演化的：trigger 词调整、workflow 改动、模板更新。一旦 Skill 进入生产，就必须像软件包一样做版本化：

SemVer
MAJOR.MINOR.PATCH。MAJOR：触发条件 / 输入输出协议变了；MINOR：新增能力但向后兼容；PATCH：模板措辞、文案、内部步骤微调。
Lockfile
每个 Agent 部署都要锁定它依赖的 Skill 版本集合（含传递依赖）。skill.lock 类似 package-lock.json。
Compatibility Matrix
Skill 声明它需要的 模型能力（如"需要 200k context"、"需要 vision"）。模型升级时自动跑兼容检查。
Deprecation Window
旧 Skill 不能一刀切下线。先标 deprecated + 共存 N 天，期间日志记录还有谁在用，再退役。

依赖管理的两类陷阱

  • Skill 互相调用形成环。"设计 Skill" 召唤"调研竞品"，"调研竞品"又召唤"设计 Skill" —— 必须在加载期检测出环路并拒绝。
  • 版本漂移。开发环境 Skill v1.3，预发 v1.4，生产 v1.2 —— 出问题时回放都对不上。所有环境的 lockfile 必须由 CI 强制对齐。

§ 03Agent Framework

框架是 Loop 与 Skill 的承载体。这一章关注三个底层设计点：SSE/Stream 实现、Rollout/Trajectory 采集、Middleware/Hook 机制。框架的好坏，常在这些细节里见分晓。

3.1 SSE 与 Stream 实现

Agent 必须支持流式输出 —— 否则用户看不到中间过程，体验近似不可用。两种主流通道：

CHANNEL A
SSE (Server-Sent Events)

HTTP 长连接，服务器主动 push 事件。浏览器原生支持，运维简单，自动重连。

典型事件：message_start / content_block_delta / tool_use / message_stop。

适合：Web UI、用户交互式 Agent。

CHANNEL B
WebSocket / Bi-directional Stream

全双工连接，客户端可以随时反向发送（Interrupt、Steer、追加输入）。

适合：需要双向交互的场景，如 voice Agent、协作编辑、低延迟控制。

设计要点

  • 事件粒度：太细（每字符一事件）→ 客户端开销大；太粗（每 Turn 一事件）→ 失去流式意义。常见折中：按 token block / tool boundary 切。
  • 恢复语义：SSE 自动重连后，事件流要能从断点续传（Last-Event-ID）。
  • 反压：客户端处理慢时，服务器需要有 buffer 策略，避免 OOM。
  • 错误信令：流中的 error 该用专门事件类型，而非 HTTP 状态码（连接已建立）。

3.2 Rollout / Trajectory 数据采集

这一组词原本来自 RL（强化学习）。在 Agent 工程里：

Rollout
一次完整的 Agent 执行过程的记录：从初始输入到最终输出的全部 Turn、Tool Call、Observation、Model 内部状态（如有）。
Trajectory
这次执行沿时间轴的轨迹，强调"按时间顺序的事件序列"。在数据结构上等同于 Rollout，但语义偏分析视角。

为什么这些数据是金子

  • 评测：人工标注 / 自动评分都依赖完整轨迹
  • 调试：模型决策错在哪步、Tool 返回了什么，必须能复现
  • 训练 / 微调：成功的轨迹可作为正例；失败的可作为反例
  • 用户回看：让用户能 replay 过去某次 Session 中模型的全部思考过程

3.3 Middleware 与 Hook 的用途

§ 1.7 已经从 HITL 角度介绍过 Middleware；这里从框架视角再总结一遍它"为什么必须有"：

USE 01
横切关注点

日志、tracing、计费、配额、审计 —— 这些都是横切关注点。塞到 Loop 主流程里会污染核心逻辑。Middleware 让它们以插件方式叠加。

USE 02
策略注入

"高风险工具必须二次确认"、"周末降级到便宜模型"、"输出长度超 X 自动压缩" —— 这些都是策略，应该可独立配置、可热更新，不和 Loop 代码绑死。

USE 03
扩展点

用户 / 团队需要的功能千差万别。一个框架内核应该小而稳定，把多样需求让给 Middleware 实现。这是开放-封闭原则在 Agent 框架里的体现。

优秀框架的判别标准

看一个 Agent 框架成不成熟，一个快速判定方法：它的 Middleware/Hook 接口是不是稳定且文档完整？是否能在不改框架源码的前提下，干预到 PreTurn / MidTurn / PostTurn / Tool Call 全生命周期？ 答案是 Yes，才算合格的工程基座。

关键工程细节

  • 数据 schema 要稳定。Rollout 一旦改 schema，半年前的数据全要重洗。建议早期就用 protobuf / pydantic 锁死。
  • tool_call / tool_result 要完整保留。RL 训练需要建模"工具反馈 → 下一步决策"的因果，少一环就训不出来。
  • 分布漂移监控。线上数据分布与训练时差异越大，模型越差。每周做一次 KL 对比。
  • 正样本稀缺，反样本要 mine。"成功 trace"少、"失败 trace"多。后者经过偏好配对一样有用。

3.7 分布式 Agent 状态一致性EXPAND

当单机部署变成多副本 + 跨地域，"Session 状态在哪"突然变成大问题。三种主流方案：

PATTERN A
Sticky Session · 黏性会话

同一个 Session 通过 Load Balancer 始终落到同一台机器，状态存本地内存。优势：实现简单，延迟低。代价：节点挂了状态全没；副本之间负载不均。

PATTERN B
External Store · 外部存储

每个 Turn 开始前从 Redis / 关系库 / 对象存储拉状态，结束写回。优势：任意副本可服务任意 Session，容灾好。代价：每 Turn 多一次 IO；并发更新需要锁。

PATTERN C
Event Sourcing · 事件溯源

状态本身不存，只存"事件流"（每次 Turn 产生的事件）。读时按需 replay。优势：天然审计、可时间穿越。代价：replay 成本随历史增长；要做 snapshot 优化。

最常见踩坑

很多团队第一版用 Sticky Session，"先跑起来"。等业务起量后被迫迁外部存储，发现 Turn 内部还藏着 in-memory cache，迁完全部副本数据错乱。第一天就要明确状态边界：什么是 Session 状态（必须持久化）、什么是 Turn 内瞬态（不能跨副本共享）。

§ 04评测 & 指标

Agent 是评测驱动的工程。没有评测，迭代就是凭直觉；没有指标，"变得更好了"就只是错觉。这一章给评测体系的最小可用骨架。

4.1 Agent 是评测驱动的

传统软件的"对错"清晰：要么编译过、要么测试 pass。Agent 的产出是开放式的，没有唯一正确答案。这带来两个后果：

  • "看起来还行"是最危险的状态 —— 没有数据支撑的判断，是直觉，三个月后没人记得为什么这么改
  • 每一次模型升级、prompt 改动、Skill 调整，都可能同时改善某些 case、恶化另一些 case。没有评测就是赌
第一性原理

评测体系应该和 Agent 同步建立、同步演进。不是"做完了再补"，而是先有 eval 才能讨论"做得对不对"。这一点上没有捷径。

4.2 Metric 设计

设计 Metric 比想象的难。同一个 Agent，可以从这些维度衡量：

设计要点

Metric 设计的关键不是"指标越多越好"，而是选少数几个北极星指标 + 一组护栏指标。北极星拉着进步方向，护栏防止改一处坏一片。每次发版都要看护栏。

4.3 Offline / Online 流程

Agent 评测分两个层次，互为补充：

OFFLINE
离线评测

预先收集一份固定的eval set（任务 + 期望产出），在 CI / 发版前跑回归。

优势：可复现、可对比版本、便宜快。

不足：eval set 永远滞后于真实分布；过拟合 eval 是常见陷阱。

ONLINE
在线评测

在生产流量上做 A/B 或 shadow，采集真实用户的行为和反馈。

优势：真实分布、捕获 long-tail。

不足：信号噪声大 / 慢 / 有用户风险 / 难做反事实分析。

4.4 Single Turn vs Multi Turn

Agent 评测有一个常被忽视的维度：评测对象是一个 Turn，还是一整段会话。两者方法论不同：

维度Single Turn 评测Multi Turn 评测
输入固定上下文 + 单一用户问多轮交互 / 长 Session
判定看本次输出质量看 Session 是否达成目标
难度低高（路径多 / 反事实难做）
典型方法LLM-as-Judge / Exact Match / 规则评分Goal Completion / 用户模拟器 / 人工标注
常见误用用 Single Turn 评测代替 Multi Turn → 掩盖累积错误只看终态 → 漏掉过程中的伤害（如错误副作用、走了弯路）
实战提醒

多数生产 Agent 是 Multi Turn 的，但绝大多数 eval 还停留在 Single Turn 层级。这是评测能力的最大欠债。一个简单起点：用用户模拟器（user simulator）跑端到端 session，按 Goal Completion 评分。即便简陋，也比单 Turn 测试更接近现实。

4.5 新特性 / 新模型上线方案

每次"模型升级"或"重要 feature 上线"，都该走标准化的评测节奏。下面是一份最小可用 playbook：

  1. Freeze baseline：明确"上线前的版本"是什么、它在 eval set 上的分数是多少。没有 baseline 就没法对比
  2. Offline 回归：新版本跑全部 eval set。每条 case 都要看 diff，不能只看总分（总分持平可能掩盖一升一降）
  3. 红线 case 必过：维护一组 "must-not-regress" case（安全 / 高价值 / 历史故障）。这些不通过直接 block 上线
  4. Canary 灰度：1-5% 流量发布。预先定好护栏指标的阈值，触发自动回滚
  5. Shadow 对比（可选）：新旧版本同时跑，只展示旧版输出，新版结果落盘对比。对低风险特性是黄金方案
  6. 扩量：阶梯式扩量（5% → 25% → 100%），每一档观察 24-72 小时
  7. 失败回流：上线后采集到的失败 case，回流到 eval set，下次迭代不重蹈覆辙
承上启下

第 7 步"失败回流"是评测体系自我进化的关键。没有这一步，eval set 会随时间变成"已经会做的事的集合"，对新失败模式无感。再回头看 §2.6 的"Skill 可自进化" —— 同一个原理在两层都成立。

4.6 用户模拟器的设计与质量评估EXPAND

Multi Turn 评测离不开"模拟用户"。手工写脚本扩展性差，最现实的方案是用模型扮演用户。但模拟器本身的质量直接决定评测结果可信度，所以它自己也需要被评测。

模拟器的 4 个设计要点

DESIGN 01
角色卡（Persona Card）

明确人设：技术背景、表达风格、耐心程度、目标清晰度、是否会主动澄清。不要用一个"通用用户"，要覆盖分布。

DESIGN 02
目标驱动而非脚本

给模拟器目标（"订一张周五到上海的机票"），而不是脚本（"先说想去上海"→"然后说周五"）。否则脚本一断模拟器就崩。

DESIGN 03
退出条件可判定

什么算"任务完成"？什么算"放弃"？必须是机器可判定的信号（订单号生成、明确的"算了"等）。

DESIGN 04
允许真实噪声

真实用户会打错字、改主意、问无关问题。模拟器要有概率注入这些行为，否则评测出的"成功率"虚高。

模拟器质量怎么评

  • 人工对比抽检：随机抽 100 个模拟对话给人评 1–5 分（自然度、是否像真实用户）。
  • 分布对齐：把模拟用户的提问与线上真实用户的提问做 embedding 聚类，看分布是否相似。
  • 对抗稳定性：换 Agent 实现（强 Agent vs 弱 Agent），模拟器是否表现出合理差异化（强 Agent 上更早完成，弱 Agent 上更频繁补充澄清）。

4.7 LLM-as-Judge 的偏置矫正EXPAND

LLM 当评委便宜又快，但有系统性偏差。下面是已被多篇论文实证的 5 大偏置：

偏置表现矫正手法
Position Bias评 A/B 对比时，倾向选第一个或第二个出现的把 A/B 位置随机互换跑两遍取一致
Length Bias倾向给长答案高分（"看起来更详细"）评分前先做长度归一化；或加入"简洁性"维度
Verbosity Bias倾向认为"措辞华丽"= 质量高用 rubric 拆维度，强制评 factual / actionable / brief
Self-Preference同家模型评同家模型，分数偏高跨家交叉评（用 Claude 评 GPT 的输出反之亦然）
Authority Bias引用了"研究表明" / 列了数字就觉得对评测维度里加入"事实准确性"，并做样本人工抽检
实战 SOP

LLM-Judge 不是"一次性打分器"，而是"漏斗的第一道"。流程：LLM-Judge 自动评全量 → 高分疑似 + 低分疑似 + 不一致样本三类进入人工复审 → 复审结果回流校准 Judge prompt。一年下来 Judge 准确率能从 70% 拉到 90%+。

4.8 Tool 调用专项评测EXPAND

"任务成功率"是综合指标，但工具调用链路出问题时，它不告诉你错在哪一环。专项评测把它拆成三段，每段独立监控：

Tool Selection
给定用户请求 + 工具列表，模型选对了工具吗？指标：Precision / Recall（应该选 X 而真的选了 X）。
常见错误：选了功能相近的错误工具、漏选了必要工具、过度调用不需要的工具。
Tool Args
选对了工具，参数填对了吗？指标：Exact Match / Semantic Match。
常见错误：必填参数缺失、类型错误（string vs int）、值越界、把上下文里的占位符当真实值。
Failure Recovery
工具返回错误时，模型能正确恢复吗？指标：Recovery Rate（错误后 N Turn 内回到正轨）。
常见错误：把错误当作普通文本继续走；陷入相同错误的无限重试；放弃任务但不告诉用户。
数据从哪来

这三类专项评测需要带 ground truth 的工具调用数据集，公开 benchmark 如 ToolBench、API-Bank、τ-bench 可参考。但更关键的是从线上 Rollout 沉淀自己的：每一次失败的 tool call 都是金矿，人工标注 1-2 次后就能进入回归集。

4.9 长尾分布下的统计显著性EXPAND

Agent 任务的分数分布是双峰而非正态：要么任务做成了（接近满分），要么彻底失败（接近 0 分），中间样本稀少。这让"平均分高了 2%"这种说法毫无意义。

3 个常见错误

  1. 用 t 检验。t 检验假设近似正态，双峰分布下 p 值不可信。改用 bootstrap 重采样 或 Wilcoxon 符号秩。
  2. 样本太小。Agent 评测一个样本可能要跑几分钟、调几次模型，总成本高，工程师容易"50 个样本就下结论"。50 个样本在双峰分布下置信区间会大得发指 —— 至少 200 个，敏感场景 1000 个。
  3. 忽略相关性。同 prompt 反复跑多次（多 sample），样本之间不独立。要用分层 bootstrap（先按 prompt 抽，再按 sample 抽）。
推荐工具链

原型阶段用 scipy.stats.bootstrap 算置信区间；上规模后用 statsmodels 跑 mixed-effects 模型把 prompt × model 双随机效应建模。结果用带误差棒的对比图呈现而不是"提升 X%"的单一数字 —— 误差棒重叠就要诚实说"未达显著"，别给老板灌米汤。

4.10 Agent 安全评测EXPAND

能力评测告诉你 Agent 有多强；安全评测告诉你 Agent 在攻击下有多稳。三大类：

THREAT 01
Jailbreak

用诱导提示（角色扮演、虚构场景、隐喻）让模型输出本应拒绝的内容。评测：用对抗 prompt 数据集跑 ASR（Attack Success Rate）。

THREAT 02
Prompt Injection

恶意指令藏在工具返回值 / 文档 / 网页里，被读取后劫持 Agent。评测：构造含注入的工具结果，看 Agent 是否仍执行用户原意图。

THREAT 03
权限越权

Agent 调用了不该有权限的工具（如以 A 用户身份读 B 用户数据）。评测：注入跨用户 reference，看 Agent 是否拦截。
