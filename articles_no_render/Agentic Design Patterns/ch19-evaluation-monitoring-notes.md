# 第19章：评估与监控 / Evaluation and Monitoring

**来源 URL**: https://adp.xindoo.xyz/chapters/Chapter%2019_%20Evaluation%20and%20Monitoring/  
**整理日期**: 2026-03-23

---

## 核心概念

评估与监控（Evaluation and Monitoring）是使智能体能够**系统地评估其性能、监控目标进展并检测操作异常**的方法论体系。它侧重于对智能体效率、效能和合规性要求进行**持续的、通常是外部的测量**。

核心要素：
- 定义清晰的指标（准确性、延迟、资源消耗）
- 建立反馈循环（持续改进）
- 实施报告系统（确保与期望对齐）
- 分析智能体轨迹（理解推理过程）

---

## 解决什么问题

智能体和 LLM 的性能可能随时间退化，传统软件测试不足以确保可靠性：

- 概率性输出难以用传统断言测试
- 数据漂移导致模型性能在部署后悄然下降
- 多智能体系统的协作成功难以度量
- 主观质量（如"有用性"）无法用简单指标衡量
- 工具调用异常和意外行为难以及时发现
- 成本不受控：token 使用量飙升但没有预警机制

---

## 工作原理/关键机制

```
智能体运行
    ↓
[实时监控层]
├── 延迟监控：记录每次请求处理时间
├── Token 使用量跟踪：输入/输出 token 计数
├── 准确性评估：响应与预期对比
└── 资源消耗监控：计算/内存/成本
    ↓
[评估层]
├── 响应准确性：精确匹配 / 语义相似度 / LLM-as-a-Judge
├── 轨迹分析：实际操作序列 vs 理想路径
├── A/B 测试：并行比较不同版本智能体
└── 漂移检测：识别性能退化趋势
    ↓
[报告与告警]
├── 生成 KPI 报告
├── 触发异常告警
└── 人机协同验证
    ↓
[反馈循环] → 改进智能体设计
```

**关键评估指标类型**：

| 指标类型 | 具体方法 |
|---------|---------|
| 响应准确性 | 精确匹配、Levenshtein 距离、Jaccard 相似性、语义余弦相似度 |
| 有用性（主观） | LLM-as-a-Judge（用另一个 LLM 评估） |
| 延迟 | 记录处理时间，存入时序数据库（InfluxDB/Prometheus） |
| Token 使用 | 累计输入/输出 token，映射到成本 |
| 轨迹质量 | 比较实际操作序列与标准（ground truth）路径 |

---

## 应用场景

1. **实时系统性能跟踪**：持续监控客服聊天机器人的问题解决率、响应时间和资源消耗

2. **智能体改进的 A/B 测试**：并行比较物流智能体的两种规划算法，确定最优方法

3. **合规性和安全审计**：自动生成审计报告，跟踪智能体遵守道德准则、监管要求的情况

4. **企业系统治理**：通过"AI 合约"编纂智能体目标、规则和控制机制

5. **漂移检测**：监控输出相关性，检测因输入数据分布变化（概念漂移）导致的性能退化

6. **异常检测**：识别智能体异常操作，可能表明错误、恶意攻击或涌现的不良行为

7. **学习进度评估**：跟踪设计为持续学习的智能体的能力提升和泛化情况

## 框架实现

### Google ADK（三种评估方式）

**1. Web UI（交互式）**：
```bash
adk web  # 启动交互式评估界面，生成评估数据集
```

**2. Pytest 集成（CI/CD）**：
```python
from google.adk.evaluation import AgentEvaluator

AgentEvaluator.evaluate(
    agent_module="my_agent",
    eval_dataset_file="test_cases.json"
)
```

**3. 命令行（自动化）**：
```bash
adk eval my_agent eval_dataset.json --config config.json
```

### LLM-as-a-Judge（主观质量评估）

```python
# 用一个 LLM 评估另一个 LLM 的输出"有用性"
judge_prompt = """
请评估以下 AI 回答的有用性（1-5分）：
问题：{question}
回答：{answer}
评估维度：准确性、完整性、清晰度、可操作性
"""
```

### "AI 合约"框架（企业级治理）

正式协议机制，为智能体委派任务编纂：
- **可验证的可交付成果**（而非模糊指令）
- **协商与澄清**机制（解决歧义）
- **层次化分解**（主合约 → 子合约）
- **自我验证循环**（生成 → 审查 → 改进）

## 注意事项或权衡

| 权衡点 | 说明 |
|--------|------|
| 评估复杂度 | 全面评估框架堪比一门学术学科，不能追求完美而忽视核心指标 |
| 主观性难题 | "有用性"等指标天然主观，LLM-as-a-Judge 也存在评估偏差 |
| 轨迹分析成本 | 记录和分析完整操作序列会增加存储和计算开销 |
| 多智能体复杂度 | 评估协作成功比评估单智能体性能复杂得多 |
| 精确匹配局限 | 简单字符串比较无法捕捉语义等价（"巴黎是法国首都" ≠ "法国首都是巴黎"） |
| 监控基础设施 | 生产级监控需要专门的时序数据库、可观测性平台 |

**评估存储建议**：
- 结构化日志（JSON 格式）
- 时序数据库（InfluxDB、Prometheus）
- 数据仓库（Snowflake、BigQuery、PostgreSQL）
- 可观测性平台（Datadog、Splunk、Grafana）

---

## 一句话总结

> 评估与监控通过定义多维指标、分析智能体轨迹、运用 LLM-as-a-Judge 等技术，构建持续反馈循环，确保 AI 智能体在生产环境中始终表现如预期，并在性能退化或异常行为出现时及时预警。
