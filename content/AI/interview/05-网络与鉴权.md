# Q18 · WebSocket 和 SSE 有什么区别？

## 一句话

WebSocket 是**独立协议的全双工长连接**；SSE 就是**一个不结束的 HTTP 响应**，只能服务端往客户端单向推。

## 全维度对比

| 维度 | WebSocket | SSE |
|---|---|---|
| **协议本质** | 独立协议 `ws://` / `wss://`。用 HTTP `Upgrade` 握手，握完就脱离 HTTP 语义 | **就是 HTTP**，`Content-Type: text/event-stream`，响应体一直不结束 |
| **方向** | 全双工，两边随时发 | 单向，只能 server → client |
| **数据类型** | 文本 + 二进制（帧协议） | **只有 UTF-8 文本**。要传二进制得自己 base64 |
| **断线重连** | 自己实现（心跳、退避、状态恢复） | 浏览器 `EventSource` **自动重连**，还会带上 `Last-Event-ID` 让服务端续传 |
| **代理穿透** | 有些企业代理/防火墙不认 Upgrade | 普通 HTTP，穿透性好 |
| **HTTP/2** | 不走 HTTP/2 多路复用 | 走，不受浏览器同域连接数限制（HTTP/1.1 下受 6 连接限制） |
| **鉴权** | 握手时不能自定义 header，通常靠 URL 参数或 Cookie，或连上后先发一条 auth 消息 | `EventSource` 也不能自定义 header（同样的坑），实践中常用 `fetch` + `ReadableStream` 替代 |
| **调试** | 需要专门工具 | **`curl` 直接看** |
| **服务端资源** | 长连接占用 | 同样占用，但就是普通 HTTP 连接，运维熟悉 |

## SSE 的协议长什么样

简单到几乎不需要库：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"delta": "北"}

data: {"delta": "京"}

event: done
data: {"usage": {"output_tokens": 128}}

```

规则：
- 每条消息是 `字段: 值` 的若干行，**用空行分隔**
- 字段有 `data`（内容）、`event`（事件类型）、`id`（用于 `Last-Event-ID` 续传）、`retry`（重连间隔）
- `data:` 可以多行，会被拼接
- 以 `:` 开头的是注释，**常用来做心跳保活**（`: ping`）

## 为什么 LLM 流式输出普遍用 SSE

这题在 AI 语境下问，一定要答到这一层：

| 理由 | 说明 |
|---|---|
| **需求就是单向的** | 用户发一次请求，服务端持续吐 token。不需要全双工 |
| **数据就是文本** | token 就是 UTF-8 文本，SSE 天然合适 |
| **穿透和运维成本低** | 就是 HTTP，网关、负载均衡、日志、监控全都不用改 |
| **调试简单** | `curl -N` 就能看流，出问题好排查 |
| **自动重连** | 长响应中途断线能续 |

**标准形态**：输入走普通 `POST`（请求体可以很大，还能被网关正常处理），输出走 SSE。请求和响应用不同的通道，比 WebSocket 里自己定义消息协议清爽得多。

## 什么时候才真需要 WebSocket

- **双向实时**：协同编辑、多人游戏、白板
- **客户端高频上行**：鼠标位置、语音流、实时音视频信令
- **需要传二进制**：音频帧、图像流
- **超低延迟**：不想要 HTTP 的每消息开销

> [!tip] 面试加分
> 主动说一句「LLM 流式场景 SSE 就够了，上 WebSocket 是过度设计」—— 说明你是按需求选型，不是按技术新旧选型。

## 还有第三个选项：长轮询

面试官可能追问「那 long polling 呢」：

客户端发请求，服务端**hold 住不返回**，直到有数据或超时。有数据了返回，客户端立刻再发一个。

- 优点：兼容性最好，任何环境都能跑
- 缺点：每条消息一次完整 HTTP 往返，开销大、延迟高
- 现状：**只作为 SSE/WebSocket 的 fallback**，不作为首选

# Q19 · Cookie 和 JWT 有什么区别？

## 第一步：先纠正这个问题

**这是本题最大的得分点。** 大部分候选人会直接开始列对比表，那就掉坑里了。

> **Cookie 和 JWT 不在一个维度上。**
> - **Cookie 是浏览器的存储 + 自动传输机制** —— 它管的是"数据放哪、怎么带上"
> - **JWT 是一种令牌格式** —— 它管的是"这段凭证长什么样、怎么防伪"
>
> **JWT 完全可以装在 Cookie 里传。** 这俩不是二选一。

那真正在被对比的是什么？

> **服务端有状态的 Session ID，vs 自包含无状态的 JWT。**

先把这句说出来，后面的对比才站得住。

## 两种方案的对比

| 维度 | Session ID + Cookie | JWT |
|---|---|---|
| **状态存哪** | 服务端（内存 / Redis / DB） | **客户端** —— token 自带信息 |
| **服务端要做什么** | 拿 ID 去查表 | **验签**（只需密钥，不碰数据库） |
| **水平扩展** | 要共享 session 存储，或者粘性会话 | 天然无状态，任何节点都能验 |
| **撤销** | 删记录，**即时生效** | **难** —— 签出去就有效到过期 |
| **体积** | Cookie 里就一个随机串，几十字节 | 几百字节到几 KB，**每个请求都带** |
| **跨域 / 多端** | 受同源和 SameSite 限制，App 端不方便 | `Authorization` header，跨域和 App 都友好 |
| **主要风险** | **CSRF**（Cookie 会自动携带） | **XSS**（存 localStorage 就会被偷） |
| **单点登出 / 强制下线** | 简单 | 要额外机制 |

## Cookie 的三个安全属性（必背）

| 属性 | 作用 | 防什么 |
|---|---|---|
| `HttpOnly` | JS **读不到**这个 Cookie | XSS 偷 token |
| `Secure` | 只在 HTTPS 下发送 | 中间人窃听 |
| `SameSite=Lax/Strict` | 跨站请求不带这个 Cookie | **CSRF** |

`SameSite` 三个值：
- `Strict`：任何跨站都不带 —— 最安全，但从外站点链接进来会显示未登录
- `Lax`：顶层导航的 GET 会带，其它跨站不带 —— **现代浏览器的默认值**，平衡点
- `None`：都带，但**必须同时加 `Secure`**

## 最佳实践：把 JWT 放进 HttpOnly Cookie

这是本题的收尾答案 —— **两边的优点都要**：

```http
Set-Cookie: token=eyJhbGci...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=900
```

| 得到什么 | 来自哪边 |
|---|---|
| JS 偷不到 token | `HttpOnly` |
| 不会被 CSRF 利用 | `SameSite` |
| 传输不被窃听 | `Secure` |
| 服务端无状态、可水平扩展 | JWT 本身 |

**权衡**：这样一来纯前后端分离的跨域场景会麻烦一些（需要配 CORS `credentials`），移动端 App 也用不上 Cookie。所以实际项目常常是：**Web 端走 Cookie，App 端走 `Authorization` header**，服务端两种都接受。

## 常见追问

**Q：JWT 存 localStorage 行不行？**
能跑，但有 XSS 风险 —— 页面上任何一段被注入的 JS 都能 `localStorage.getItem('token')` 拿走。而 `HttpOnly` Cookie 是 JS 读不到的。所以：**能用 HttpOnly Cookie 就别用 localStorage**。

**Q：用了 JWT 还需要 CSRF 防护吗？**
看放哪：
- 放 `Authorization` header → **不需要**，因为浏览器不会自动带 header，攻击者的站点没法伪造
- 放 Cookie → **需要**，因为 Cookie 会自动带。靠 `SameSite` + CSRF token 双保险

**Q：为什么 JWT 撤销这么难？**
见下面 Q21。

# Q20 · JWT 的结构是什么？

## 三段式

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiIxMjMiLCJleHAiOjE3MDB9 . dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
└──────────── header ────────────┘   └────────── payload ──────────┘   └──────────── signature ───────────┘
```

用 `.` 连接，前两段是 **Base64URL 编码的 JSON**，第三段是签名。

> Base64URL 和普通 Base64 的区别：把 `+` `/` 换成 `-` `_`，去掉末尾的 `=` 填充 —— 这样才能安全地放进 URL 和 header。

## Header

```json
{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "key-2026-08"
}
```

| 字段 | 说明 |
|---|---|
| `alg` | 签名算法。`HS256` / `RS256` / `ES256` 等 |
| `typ` | 类型，固定 `JWT` |
| `kid` | Key ID，**密钥轮换时用来告诉验证方该用哪把钥匙** |

## Payload —— claims

```json
{
  "iss": "https://auth.example.com",
  "sub": "user-12345",
  "aud": "https://api.example.com",
  "exp": 1735689600,
  "nbf": 1735685000,
  "iat": 1735685000,
  "jti": "a1b2c3d4",
  "role": "admin",
  "tenant": "acme"
}
```

**注册声明**（RFC 7519 定义的标准字段，必背）：

| claim | 全称 | 含义 |
|---|---|---|
| `iss` | issuer | 谁签发的 |
| `sub` | subject | 主体（通常是 user id） |
| `aud` | audience | 给谁用的 —— **防止 A 服务的 token 拿去 B 服务用** |
| `exp` | expiration | 过期时间（Unix 秒） |
| `nbf` | not before | 生效时间 |
| `iat` | issued at | 签发时间 |
| `jti` | JWT ID | 唯一标识，**做黑名单和防重放靠它** |

后面的 `role`、`tenant` 是自定义 claims，按业务加。

## Signature

```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```

注意签的是**前两段拼起来的字符串**（含中间那个点），不是原始 JSON。所以只要有一个字节被改，签名就对不上。

## 最重要的一句话

> [!danger] Base64URL 是**编码**不是**加密**
> payload 任何人拿到都能直接解开看 —— 浏览器控制台一行 `atob()` 就出来了，jwt.io 网站上贴进去就能看。
>
> **JWT 保证的是「没被篡改」，不是「看不见」。**
>
> 所以：**绝不要往 payload 里放密码、身份证号、手机号、内部 ID 之类的敏感信息**。
> 真的需要内容保密，要用 **JWE**（JSON Web Encryption），那才是加密的。

这一条几乎每次面试都会被追问，是最典型的送分/送命题。

## 三类 JWT 相关规范（可能被追问）

| 规范 | 全称 | 干什么 |
|---|---|---|
| JWS | JSON Web **Signature** | 签名 —— **平时说的 JWT 基本都是 JWS** |
| JWE | JSON Web **Encryption** | 加密 —— 内容不可见 |
| JWK | JSON Web **Key** | 密钥的 JSON 表示；`JWKS` 是密钥集合，非对称验签时从对方的 `/.well-known/jwks.json` 拉 |

# Q21 · 为什么 JWT 通常不需要像随机 Session ID 一样在服务端保存会话状态？

## 核心：信息在哪

这题的答案就一句话 —— **两者的信息位置不同**。

### 随机 Session ID 是一个「指针」

```
Cookie: sid=8f3a2b1c9d4e5f6a7b8c9d0e
```

这串字符**本身没有任何含义**，就是一串随机数。服务端拿到它，必须去查表：

```
sid=8f3a...  →  { user_id: 12345, role: "admin", login_at: ... }
```

**没有这张表，这个 ID 就是一串废字符。** 所以服务端必须存，而且所有节点都得能访问到这张表 —— 要么 Redis，要么粘性会话。

### JWT 是「数据本身」

```
Authorization: Bearer eyJhbGci...
                      ↓ 解开就是
{ "sub": "12345", "role": "admin", "exp": 1735689600 }
```

服务端拿到就能读，**不需要查任何表**。

### 那怎么防伪造？

有人会立刻想到：我自己伪造一个 `{"sub":"1","role":"admin"}` 不就当管理员了？

**靠签名。** 服务端用只有自己知道的密钥，对收到的 token 重新算一遍签名，和 token 自带的第三段比：
- 对得上 → 这个 token 确实是我签的，而且一个字节都没被改过
- 对不上 → 伪造的，拒绝

**关键在于：验签只需要密钥，不需要数据库。**

## 一个好用的类比

| | Session ID | JWT |
|---|---|---|
| 类比 | **存包柜号牌** | **带防伪钢印的身份证** |
| 牌/证上有什么 | 只有一个编号 | 姓名、有效期、权限，全印在上面 |
| 怎么用 | 拿号牌去柜台**查登记本** | 直接看证上的字，**验一下钢印真假** |
| 需要什么 | 登记本（服务端存储） | 验钢印的能力（密钥） |
| 挂失 | 划掉登记本那一行，**立刻生效** | **做不到** —— 证已经在人家手里了 |

面试时用这个类比讲，比背定义清楚得多。

## "无状态"到底是什么意思

准确表述是：

> **不是没有状态，是状态被搬到了客户端手上，用签名保证它没被篡改。**

好处：
- 任何一台服务器都能独立验证，不需要共享存储
- 加机器就是加机器，不用考虑 session 同步
- 跨服务、跨域名验证方便（尤其非对称签名，验证方只要公钥）

## 代价：撤销困难

这是必须主动说出来的 trade-off，只讲好处会显得片面。

**一旦签发，在过期前它就是有效的。** 意味着：
- 用户点了"退出登录" → token 还能用
- 管理员把某人权限降级 → 旧 token 里的 `role: admin` 还在生效
- 账号被封禁 → 封不掉已发出的 token
- token 泄漏了 → 在过期前无法止损

### 实践中怎么办

| 手段 | 做法 | 代价 |
|---|---|---|
| **短 TTL** | access token 设 5-15 分钟 | 泄漏的窗口小；但要频繁换发 |
| **refresh token** | 长效 refresh token（有状态、存服务端）换发短效 access token | **撤销 refresh token 就能在一个 TTL 内切断访问** |
| **黑名单** | 把撤销的 `jti` 存 Redis，每次请求查一下 | 又变回有状态了，但只存"被撤销的"，量比全量 session 小得多 |
| **版本号** | user 表存一个 `token_version`，签进 token，改密码时递增 | 每次要查一次 user，也是有状态 |

> [!tip] 这才是完整答案
> 「JWT 无状态」和「能撤销」**本质上是矛盾的**。
> 生产环境的常见解法是**混合**：access token 短效无状态（承担绝大多数请求，性能好），refresh token 有状态可撤销（低频，性能压力小）。
>
> 主动说出这个矛盾和折中方案，比只背"JWT 是无状态的"高一个层次。

# Q22 · 服务端如何验证 JWT 的真实性和完整性？

## 完整流程（按顺序）

### 1. 切分与解码

按 `.` 切成三段。Base64URL 解开第一段拿到 header。

**这时候还不能信任任何内容** —— 只是拿到了一些"声称"的信息。

### 2. 校验 alg —— 最关键的一步

```java
// ❌ 致命错误：直接用 header 里声明的算法
String alg = header.get("alg");
verify(token, alg, key);

// ✅ 正确：用自己配置的算法，header 里的只用来做一致性检查
if (!ALLOWED_ALGS.contains(header.get("alg"))) {
    throw new InvalidTokenException("algorithm not allowed");
}
verify(token, MY_CONFIGURED_ALG, key);   // 用自己的，不用它给的
```

**永远不要让攻击者决定用什么算法验证。** 两个经典漏洞都源于此，见下面。

### 3. 找到密钥

- 对称（HS256）：用配置的 secret
- 非对称（RS256/ES256）：按 header 里的 `kid` 从 JWKS 端点找对应公钥。**JWKS 要本地缓存**（别每次请求都去拉），但也要能在 `kid` 未命中时刷新一次。

### 4. 重算签名并比对

对 `base64url(header) + "." + base64url(payload)` 用密钥重新算一遍签名，和第三段比。

> [!warning] 必须用常量时间比较
> ```java
> // ❌ 普通 equals 会在第一个不同字节就返回 —— 泄漏了「前几个字节对了」
> if (computed.equals(provided)) { ... }
>
> // ✅ 常量时间比较，不管对多少都跑完全程
> if (MessageDigest.isEqual(computed, provided)) { ... }
> ```
> 攻击者能通过测量响应时间，一个字节一个字节地把签名试出来。这叫**时序攻击（timing attack）**。

### 5. 签名过了，才能校验 claims

**顺序绝对不能反。** 先验签，再读 payload —— 否则你在拿未经验证的数据做业务判断。

| claim | 校验 | 备注 |
|---|---|---|
| `exp` | 当前时间 < exp | 留 clock skew 容忍（通常 60s） |
| `nbf` | 当前时间 ≥ nbf | 同样留容忍 |
| `iat` | 不能是未来，也不能太老 | 防重放 |
| `iss` | 等于期望的签发者 | 防止别家的 token 拿来用 |
| `aud` | **包含自己** | **防止 A 服务的 token 拿去 B 服务用** —— 很多人漏这条 |

### 6. 业务层校验

- `jti` 在黑名单里吗（如果实现了撤销）
- 用户还存在吗、被禁用了吗
- `token_version` 对得上吗

## 两个必背的经典漏洞

### 漏洞 1：`alg: none`

JWT 规范里有一个 `none` 算法（表示"不签名"）。攻击者：

1. 拿一个合法 token，解开 payload
2. 把 `role` 改成 `admin`
3. 把 header 的 `alg` 改成 `"none"`
4. **把第三段签名整个删掉**，只留 `header.payload.`

实现不严的库看到 `alg: none`，就**直接跳过签名验证**放行了。

**防御**：算法白名单，`none` 永不接受。

### 漏洞 2：RS256 降级成 HS256

这个更阴险。前提是服务端用 RS256（私钥签、**公钥验**），而公钥是公开的。

攻击者：
1. 把 header 的 `alg` 从 `RS256` 改成 `HS256`
2. 修改 payload
3. **用服务端的公钥当作 HMAC 的密钥**去签名

服务端如果傻乎乎地按 header 说的用 HS256 验证，就会**拿公钥去做 HMAC 校验** —— 而攻击者用的正是同一把公钥，所以校验通过。

**公钥是公开的，于是任何人都能伪造 token。**

**防御**：同样是算法白名单 —— 服务端配置死了用 RS256，就绝不接受 HS256。

> [!danger] 两个漏洞的根因是同一个
> **信任了未经验证的 header。**
> header 是攻击者可以随意修改的部分，把它当配置来用就是灾难。
> 记住一句话：**header 里的信息只能用来「辅助定位」（比如 kid 找哪把钥匙），绝不能用来「决定验证策略」。**

## 算法选型

| 算法 | 类型 | 签 / 验 | 适合 |
|---|---|---|---|
| `HS256` | 对称 HMAC | 同一个 secret | 单体应用、内部服务。**简单快，但验证方也能签发** |
| `RS256` | 非对称 RSA | 私钥签 / 公钥验 | 多方验证、开放平台。**验证方拿到公钥也伪造不了** |
| `ES256` | 非对称 ECDSA | 私钥签 / 公钥验 | 同 RS256，但**签名更短、性能更好** |

**选型的判断标准很简单：验证方是否可信。**
- 只有自己验 → HS256 够了
- 要给第三方 / 多个微服务验 → 必须非对称，否则等于把签发权给出去了

## 完整校验清单

```
□ 算法在白名单内（拒绝 none，拒绝降级）
□ 用配置的算法，不用 header 声明的
□ kid 命中已知密钥
□ 签名重算通过（常量时间比较）
□ ── 以上全过，才开始读 payload ──
□ exp 未过期（带 clock skew）
□ nbf 已生效
□ iss 匹配
□ aud 包含自己
□ jti 不在黑名单
□ 用户仍然有效
```
