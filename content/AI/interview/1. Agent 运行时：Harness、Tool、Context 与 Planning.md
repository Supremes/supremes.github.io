# Agent 运行时：Harness、Tool、Context 与 Planning

这一组回答「Agent 怎么跑」：Harness 驱动循环，Tool 把决定变成动作，Context / Memory 决定模型看到什么，Planning 决定先做什么。目标是能从用户输入开始口述一次完整 Agent Loop。

本文包含：

- Agent Harness 与运行时
- Agent Tool、MCP 与 Skill
- Agent Context 与 Memory
- Agent Planning 与 Reasoning

---

## Agent Harness 与运行时

Harness 把模型变成可以持续执行任务的系统。它组装上下文、调用模型、执行工具、回填结果，并在预算耗尽或任务完成时停止。

### 复习范围

| 模块 | 要讲清的内容 |
|---|---|
| Agent Loop | input → context → LLM → tool → observation → next turn |
| 状态模型 | message、turn、run、session、checkpoint 的关系 |
| 事件模型 | start、delta、tool call、tool result、error、end |
| 终止条件 | final answer、最大轮数、token/时间/成本、安全熔断 |
| 并发控制 | 只读工具并行，写操作串行，状态快照隔离 |
| 恢复 | append-only 日志、checkpoint、未完成调用的处理 |

### 高频问题

1. 一次 Agent 请求从用户输入到最终回答经过哪些步骤？
2. `tool_call` 和 `tool_result` 如何重新进入上下文？
3. Agent Loop 如何判断继续或停止？
4. 用户消息在工具执行期间到达，运行时怎么处理？
5. 热更新工具或 Prompt 时，如何避免在途请求漂移？
6. 进程崩溃后，哪些状态可以恢复，哪些不能？

### 要点reference

- *一次请求经过哪些步骤*：`StepCollector.init` 重置请求态 → `TaskPlanner.plan`（可选，独立一次 LLM 调用）→ 拼 system prompt → `chatClient.prompt().toolNames(...).stream()` 把 tool-calling loop 交给 Spring AI → AOP 拦每次工具调用记 step → `StepCollector.collect` → 写 Redis 历史 → `finally` 清 ThreadLocal。**loop 本身是框架托管的黑盒**，自己写的是 loop 外面那一圈。
- *tool_call / tool_result 怎么回到上下文*：框架收到 `tool_calls` → 按 name 找 `FunctionToolCallback` → 反序列化成 Request → `apply()` → 结果序列化成 tool message 追加到消息列表 → 再调一次模型。工具输出先过 `TokenWindowManager.truncateToolOutput`（3000 token）再回灌，否则一次 `cat` 能吃掉整个窗口。
- *继续还是停止*：三类终止——模型自己不再发 tool_call（`finish_reason=stop`）；`max-steps: 10` 到顶，`StepCollector.getAndIncreaseStepNumber` 抛 `MaxStepsExceededException`，被 `ToolExecutionExceptionProcessor` 转成一段「请停止调用工具并总结」的 observation 回灌给模型，**不是直接掐断**；client 断连时 `takeWhile(!isCancelled)` 撕掉 pipeline。
- *工具执行期间用户新消息到了*：dawn-ai 不处理——一个 `streamChat` = 一个 turn，原子、瞬时；新消息是新 turn，靠 Redis 历史串联。要支持「打断」，得先把 turn 升级成有 id、可持久化的 run。
- *热更新怎么防在途请求漂移*：Skill 靠 `SkillRegistry.refresh()` synchronized 整体替换 immutable Map，在途请求拿的是旧引用；system prompt 每 turn 重新拼，天然是快照；工具列表 `toolRegistry.getNames()` 每 turn 读一次，同理。
- *崩溃后什么能恢复*：Redis 里的对话历史能；`StepCollectorContext` 是 ThreadLocal 里的活对象，不能；没有 checkpoint，半途的 run 直接丢。所以 dawn-ai 的恢复粒度是 turn，不是 step。
- *dawn-ai 实践里最值得讲的一处：ThreadLocal 跨线程*。流式模式下 Spring AI 在 Reactor Netty worker 线程上跑 tool callback，跟调 `init()` 的 `chatStreamExecutor` 线程不是同一个，`StepCollector` 直接 NPE、工具静默失败。修法是 Micrometer context propagation：`StepCollectorContextAccessor` 注册进 `ContextRegistry` + `Hooks.enableAutomaticContextPropagation()`，Reactor 每次切线程前存/恢复 ThreadLocal。关键细节：传的是**引用**不是拷贝，所以所有线程往同一个 `StepCollectorContext` 里 append 才对得上。这段注册放在 `ApplicationRunner` 里——所有 bean 就绪后、第一个请求前——纯粹是时序控制。

### 容易讲错的地方

- API 通常无状态，客户端要维护并重发历史。
- 模型决定想做什么，运行时决定是否允许和如何执行。
- 超时不代表工具没有产生副作用。
- checkpoint 保存可序列化状态，不保存任意运行时对象。
- 观测 hook 不应改变执行结果，控制 hook 可以。

### 项目证据

准备一张事件时序图，并从 Trace 中找一条真实失败路径。说明首错发生在哪个 turn，运行时如何终止或恢复。

## Agent Tool、MCP 与 Skill

工具让模型的决定变成动作。Tool Calling 是调用协议，MCP 是工具的发现与接入标准，Skill 是按需加载的流程知识。三者分别解决「怎么调」「从哪来」「什么时候用」。

执行代码时使用什么环境、怎么收集结果和取消进程，见 [Agent 沙箱与执行环境](<3. Agent 生产化：评测、可观测性、可靠性、安全与性能.md#agent-sandbox>)。

### 复习范围

| 主题 | 要讲清的内容 |
|---|---|
| Tool Schema | 名称、描述、参数 JSON Schema、返回结构、幂等性声明 |
| 调用协议 | tool_call → 执行 → tool_result 回灌；并行调用与顺序依赖 |
| Registry | 注册、发现、版本、按上下文裁剪可见工具集 |
| MCP | server / client、resources / tools / prompts、传输层、鉴权边界 |
| Skill | 触发条件、渐进加载、与 system prompt 的 token 预算 |
| 权限 | 模型可见 ≠ 可调用；调用前的参数与策略检查 |

### 高频问题

1. 工具描述写得好坏对成功率影响有多大，怎么评测？
2. 1000 个工具怎么让模型选对？
3. MCP 解决了什么，没解决什么？
4. Skill 和 system prompt、RAG 的边界在哪？
5. 工具返回体太大怎么办？
6. 工具调用失败的错误怎么回给模型？（见「生产化 → 可靠性与生产化」）

### 要点reference

- *工具描述对成功率的影响，怎么评*：描述是模型选工具的唯一依据，改一句描述等于改一次路由策略。评法：固定一组 query，看 tool 选择的 top-1 accuracy、invalid call rate、unnecessary call rate，改描述前后对比。dawn-ai 的 `system-prompt.st` 里残留 Calculator / Weather 文案但 Registry 里没这俩——**判断能力以 Registry 和运行时 bean 为准，别看静态 prompt**。
- *1000 个工具怎么选对*：不能全量注入（1000 × 300 token = 30 万）。做 coarse-to-fine：policy filter（权限 / 租户 / 风险，确定性，先做）→ server 检索 top-10 → tool 检索 top-20 → rerank 到 3~8 → 只加载这几个的完整 schema，连接 lazy create。常驻 prompt 里只留 `search_tools` / `load_tool_schema` 两个 meta-tool。dawn-ai 目前是全量列表 + 500 token 砍尾，扩不动。
- *MCP 解决什么、没解决什么*：解决的是「外部能力怎么标准化接入」——tools / resources / prompts 一套协议，换 server 不改 Agent。没解决：权限、审批、schema 爆炸、server 健康。MCP ≠ Skill：一个是「能调什么」，一个是「这类任务怎么做」。dawn-ai 明确不接 MCP（`docs/roadmap.md` 列为 non-goal）。
- *Skill 和 system prompt、RAG 的边界*：system prompt 是常驻人设和硬约束；Skill 是按需加载的 SOP，常驻的只有 name + description；RAG 是证据不是指令。dawn-ai 的 progressive disclosure：`SkillRegistry` 扫 `SKILL.md` → prompt 只注入 name + description（`max-skills-tokens: 500`）→ 模型命中后 `loadSkillTool(name)` 拿正文 → 需要附件再 `readSkillResourceTool(skill, path)`。
- *工具返回体太大*：`ToolExecutionAspect` 对 String 输出统一 `truncateToolOutput`（3000 token），BashTool 另有 `max-output-bytes: 51200`。截断要留尾注 `[已截断，原文约 N tokens]`，让模型知道自己没看全。
- *dawn-ai 实践*：`ToolRegistry` 启动时扫 Spring Context，三个条件——实现 `Function`、有 `@Description`、在 `com.dawn.ai.agent.tools` 包下；`AgentOrchestrator` 用 `.toolNames(toolRegistry.getNames())` 按名字交给 Spring AI，`SpringBeanToolCallbackResolver` 按 beanName 找 bean、从泛型推 Request 类型、Jackson 反射 `@JsonPropertyDescription` 生成 JSON Schema。**Schema 和行为来自同一份类型声明**，这是 Java 做 Tool 相对 Python docstring 方案的实质优势。已知短板：`.toolNames()` 在 Spring AI 2.0 被删，要迁 `@Tool`；无 tenant / user 级 ACL，Registry 是全局的。

### 常见错误与风险

- 工具描述含糊，模型选错或乱传参。
- 所有工具全量塞进 context，token 和选错率一起涨。
- 工具输出不截断，一次调用吃掉整个上下文窗口。
- 把权限判断写在工具描述里，指望模型遵守。

### 项目证据

dawn-ai：`ToolRegistry`、`SkillRegistry`、`max-tool-output-tokens: 3000` 截断、`max-skills-tokens: 500` 预算。准备一次工具描述改写前后的成功率对比。

## Agent Context 与 Memory

Context 是当前调用送进模型的工作集。Memory 是跨 turn 或跨 session 保留、检索和更新的信息。两者不能混为一谈。

### 复习范围

| 层次 | 内容 |
|---|---|
| Working Context | system、tools、history、retrieval、current input |
| Short-term State | 当前任务计划、临时变量、未完成工具调用 |
| Long-term Memory | 用户事实、偏好、历史事件、经验规则 |
| Memory Pipeline | 提取、规范化、去重、写入、检索、遗忘 |
| Context Engineering | Select、Compress、Isolate、Write |
| 质量指标 | 命中率、精确率、时效性、冲突率、作用域正确率 |

### 高频问题

1. Memory 与 RAG 有什么区别？
2. 为什么不能把所有历史对话都塞进 Context？
3. 用户新要求与旧偏好冲突时，谁优先？
4. 如何处理过期、重复和互相矛盾的记忆？
5. 什么时候写 Memory，谁来验证提取结果？
6. 如何评测“检索到了，但用错了作用域”？

### 要点reference

- *Memory 与 RAG 的区别*：RAG 存的是外部知识，按 query 相似度召回，谁问都一样；Memory 存的是关于这个用户的事实，按 `userId` 过滤，还带 importance、时间、访问记录。dawn-ai 两者共用一个 pgvector 表，靠 metadata `type` 区分，但 Memory 多一层 JPA 作 source of truth。
- *为什么不能全塞进 context*：self-attention $O(n^2)$，长了慢且贵；Lost in the Middle，中间段注意力衰减；历史里大量低价值 token 会挤掉真正要用的东西。dawn-ai 的历史是 `max-history-tokens: 8000` 从最新往回装，装不下就停。
- *新要求和旧偏好冲突谁优先*：当前 turn 的显式指令永远优先。工程上把 Memory 放在 system prompt 的【相关记忆】段，用户消息在后面，模型天然更看重后者。dawn-ai 的 Fact 去重 prompt 专门写了「偏好冲突不判为重复」，避免新偏好被旧记忆吞掉。
- *过期、重复、矛盾怎么处理*：
	- 重复：两级——md5 精确去重 → 向量召回 top-10 候选交给 LLM 判「是不是同一个事实」（few-shot 三组：同义改写判重、主题相近不判重、多候选选一个）。判重不是丢弃，是 `bumpImportance` +0.05。
	- 过期：Decay 软遗忘，`half-life-days: 30`，30 天没访问 importance 减半；Eviction 硬清理，每天 03:00 删 `importance < 0.1` 且超龄的。检索命中会刷 `lastAccessedAt`，用过的记忆活得久。
	- 矛盾：目前靠 LLM 判重时不合并 + 检索时 importance 加权，没有显式的冲突解决。这是短板。
- *什么时候写 Memory、谁验证*：不是每轮写。Redis 滑动窗口 `max-history: 10`，溢出的进 pending list，攒够 `summary.batch-size: 4` 触发 `SummarizationRequestEvent` → `FactExtractor` 抽离散事实存 SEMANTIC（importance 0.6）、`MemorySummarizer` 压成 <100 字摘要存 EPISODIC（0.5）→ 摘要攒够 `episode-threshold: 4` 触发 `ReflectionWorker` 提炼长期偏好存 PROCEDURAL（0.9）。**Fact 直接写、不经验证；PROCEDURAL 只能由 Reflection 产生**，这是唯一的「验证」层。
- *怎么评「检索到了但用错作用域」*：所有 Memory 检索都带 `userId` filter，作用域错只可能是 session 级信息被当成 user 级。评测：构造 trajectory-prefix 用例，同一 userId 两个 session，A 里说的临时约束不该出现在 B 的 system prompt 里。dawn-ai 单用户部署 `default-user-id: local-user`，这个问题被绕开了，多租户要补。
- *dawn-ai 实践*：三类记忆各自去向不同——SEMANTIC 和 PROCEDURAL 进 system prompt（`semantic-top-k: 3` / `procedural-top-k: 2`，总预算 `max-memory-tokens: 1000`），EPISODIC **不进 prompt**，只做 Reflection 输入。检索打分 `similarity × (1 + 0.3 × importance)`，先取 2 倍候选再重排截断。写入顺序：先写 VectorStore 再写 JPA，VectorStore 失败 JPA 不提交；删除反过来，JPA 软删是真相，VectorStore 删失败没关系，`search()` 会用 JPA post-filter 挡掉。

### 建议的数据模型

每条长期记忆至少记录：

- `subject`、`predicate`、`value`
- 来源和证据
- 作用域
- 生效时间与过期时间
- 置信度
- 版本和冲突关系

### 常见错误与风险

- 把推测写成事实。
- 旧偏好覆盖当前明确指令。
- 检索命中，但人物或时间关系拼错。
- 压缩时丢失否定词、数字和约束。
- 不做遗忘，Context 被低价值记忆占满。

准备一个记忆冲突案例。展示原始对话、提取结果、检索结果、最终决策和修复后的回归用例。

## Agent Planning 与 Reasoning

Planning 决定任务怎么拆、先做什么和何时调整。Reasoning 是模型在当前状态下做决策的能力。工程上关注可观察动作和计划状态，不依赖隐藏思维链。

### 复习范围

| 模式 | 适用场景 |
|---|---|
| ReAct | 边观察边行动，适合开放式工具任务 |
| Plan-and-Execute | 先拆任务再执行，适合多阶段工作 |
| Planner-Executor | 规划和执行用不同角色或模型 |
| Reflection / Critic | 对结果做检查，但要防止无效自我循环 |
| State Graph | 分支、回退和人工节点明确的业务流程 |

### 高频问题

1. ReAct 解决了什么问题？
2. 为什么计划写得很完整，执行仍可能失败？
3. 什么时候应该重规划，而不是继续重试？
4. Planner 和 Executor 应不应该使用不同模型？
5. 如何限制反思循环和 token 消耗？
6. 计划如何与工具结果、用户新消息保持一致？

### 要点reference

- *ReAct 解决了什么*：把「想」和「做」交错，每步都基于真实观察而不是脑补。代价是每步一次 LLM 调用，长任务容易跑偏。ReAct 适合局部决策节点，整体流程确定的场景用 workflow 保稳定。dawn-ai 的 ReAct loop 是 Spring AI 托管的，自己没写。
- *计划完整为什么执行仍失败*：Planner 看的是静态输入，Executor 面对的是动态环境——工具报错、返回空、发现新信息。严格照旧计划走会撞墙，完全不管计划又漂。dawn-ai 踩过这个坑：Plan agent 和 ReAct agent 的 prompt 没对齐，行为偏差。修法两条：prompt 里写明「步骤空结果或报错时不要机械执行下一步」，加动态 re-plan。
- *什么时候重规划而不是重试*：重试是「同样的事再来一次」，只对瞬时错有效；重规划是「换路」。触发条件要确定性：dawn-ai 用 `replan-threshold: 2`——连续 2 次工具空结果（字符串启发式判 `docsFound=0` / `未找到` / `No results`）→ `TaskPlanner.rePlan()` 生成 1~3 步新建议，作为 tool result 回灌，SSE 推 `replan` 事件，一次 run 只触发一次。
- *Planner 和 Executor 该不该用不同模型*：可以不同，但更重要的是不同参数——Planner 要全局、低温（dawn-ai `temperature 0.3`，不带完整历史，只带最近 6 轮各 200 字的压缩上下文用于解指代），Executor 要贴着上下文。dawn-ai 同一模型，sub-agent 留了 `model-override` 口子没用。
- *怎么限制反思循环*：不要让模型自己决定停——`max-steps: 10`、RAG `max-calls-per-session: 3`、sub-agent `max-dispatches-per-session: 3`、`block-after-empty-searches: 2`，多个独立上限叠加。`StepCollector.isQueryRetrieved` 拦同一 query 重复检索。
- *计划怎么和工具结果、用户新消息保持一致*：计划是建议不是合同。dawn-ai 把计划拼进 system prompt 的【执行计划】段，紧跟【执行约束】写清什么情况下可以偏离、偏离要说明原因；全是 `finish` 的计划转成「优先直接回答」的策略提示，不注入空计划。
- *dawn-ai 实践*：`TaskPlanner` 用 `BeanOutputConverter<List<PlanStep>>` 把 JSON Schema 拼进 prompt 强制结构化，`validatePlan` 校验 action 必须在工具集内、最后一步必须 `finish`，不合法抛 `PlanGenerationException` → 记 `ai.planner.result{status=parse_error}` → **降级为无计划直接执行**，不阻塞主流程。Planner fallback 率 >20% 有告警。三层兜底提 `reasoning_content`（GenerationMetadata → Message metadata → 原始 HTTP body），因为 OpenAI-compatible 接 DeepSeek 时 Spring AI 认不出。

### 工程约束

- 计划项要有状态：pending、running、done、blocked。
- 每一步要绑定证据和验收条件。
- 环境变化后检查计划是否仍成立。
- 高风险动作前增加确认节点。
- 用最大步骤、时间、token 和成本共同限制任务。

### 常见错误与风险

- 计划和真实环境脱节。
- 只更新自然语言计划，没有更新执行状态。
- Planner 给出工具并不存在的步骤。
- 反思只是重复原答案，没有新证据。
- 为简单任务强制规划，延迟和成本反而上升。
