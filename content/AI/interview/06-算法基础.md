# Q23 · 爬楼梯：N 级台阶，每次走 1 级或 2 级，求到第 N 级共有多少种走法。用递归实现，解释递推关系和边界条件

## 递推关系怎么推出来的

**别背 `f(n)=f(n-1)+f(n-2)`，要能推。推导过程本身就是考点。**

> 我要站上第 n 级。**看最后一步**：
> - 最后一步迈了 1 级 → 之前必然站在第 **n-1** 级 → 这类走法有 `f(n-1)` 种
> - 最后一步迈了 2 级 → 之前必然站在第 **n-2** 级 → 这类走法有 `f(n-2)` 种
>
> 这两类**既不重叠也不遗漏**：
> - **不重叠** —— 最后一步的步长不同，不可能是同一条路径
> - **不遗漏** —— 最后一步只能是 1 或 2，没有第三种可能
>
> 所以直接相加：`f(n) = f(n-1) + f(n-2)`

> [!tip] 「不重不漏」是关键词
> 计数类 DP 的正确性全靠这四个字。主动说出来，说明你懂的是**方法**而不是**这一道题**。
>
> 按「第一步」分类也能推出同样的式子。按最后一步更自然，因为它直接对应到子问题。

## 边界条件从哪来

| 定义 | 值 | 解释 |
|---|---|---|
| `f(0)` | **1** | 站在起点原地不动，算**一种**走法（空走法） |
| `f(1)` | 1 | 只能迈 1 级 |
| `f(2)` | 2 | `1+1` 或 `2` |

**为什么 `f(0)=1` 而不是 0？** 两个角度都要能说：

1. **组合意义**：从 0 级到 0 级，"什么都不做"本身是一个合法方案，所以是 1 种。
2. **自洽性**：这样定义能让递推在 n=2 处成立 —— `f(2) = f(1) + f(0) = 2`，和手数的结果对上。定义成 0 就会算出 `f(2)=1`，错。

也可以避开 `f(0)`，直接定 `f(1)=1, f(2)=2` 从 n=3 递推，完全等价。

**这就是 Fibonacci 错开一位**：1, 1, 2, 3, 5, 8... 可以点一句显得有全局观，但**别只说这一句** —— 面试官要的是推导。

## 四个版本

### 版本 1：朴素递归 —— O(2ⁿ) 时间

```python
def climb(n: int) -> int:
    if n <= 1:
        return 1                       # f(0) = f(1) = 1
    return climb(n - 1) + climb(n - 2)
```

**这是题目要的"递归实现"，但必须主动指出问题。**

复杂度怎么来的 —— 画递归树：

```
                climb(5)
              /          \
        climb(4)         climb(3)      ← climb(3) 出现了 2 次
        /     \          /     \
   climb(3) climb(2) climb(2) climb(1) ← climb(2) 出现了 3 次
```

每层节点近似翻倍，总数 O(2ⁿ)。**重复子问题就是优化的入口。**

### 版本 2：记忆化 —— O(n) 时间，O(n) 空间

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def climb_memo(n: int) -> int:
    if n <= 1:
        return 1
    return climb_memo(n - 1) + climb_memo(n - 2)
```

每个 `n` 只算一次。**这是从递归到 DP 的桥梁** —— 自顶向下的 DP。

面试时手写一个不依赖装饰器的版本更保险：

```python
def climb_memo(n: int, memo: dict[int, int] | None = None) -> int:
    if memo is None:
        memo = {}
    if n <= 1:
        return 1
    if n in memo:
        return memo[n]
    memo[n] = climb_memo(n - 1, memo) + climb_memo(n - 2, memo)
    return memo[n]
```

> 小坑：用 `if memo[n] != 0` 这种「零值代表没算过」的写法，前提是结果不可能为 0。
> 本题成立，但一般情况下用 `in` 判断或者单独一个 `computed` 集合更稳。

### 版本 3：自底向上迭代 —— O(n) 时间，**O(1) 空间**

```python
def climb_iter(n: int) -> int:
    if n <= 1:
        return 1
    prev, curr = 1, 1                  # f(0), f(1)
    for _ in range(2, n + 1):
        prev, curr = curr, prev + curr
    return curr
```

**滚动变量**把空间压到 O(1) —— 每一步只依赖前两个值，不需要留整个数组。

**生产代码用这个**：没有递归深度限制，空间最省。

### 版本 4：矩阵快速幂 —— O(log n)

被问到"还能更快吗"时用：

$$\begin{pmatrix} 1 & 1 \\ 1 & 0 \end{pmatrix}^{n} = \begin{pmatrix} f(n+1) & f(n) \\ f(n) & f(n-1) \end{pmatrix}$$

```python
def climb_fast(n: int) -> int:
    if n <= 1:
        return 1

    def mul(a, b):
        return [[a[0][0]*b[0][0] + a[0][1]*b[1][0], a[0][0]*b[0][1] + a[0][1]*b[1][1]],
                [a[1][0]*b[0][0] + a[1][1]*b[1][0], a[1][0]*b[0][1] + a[1][1]*b[1][1]]]

    result, base = [[1, 0], [0, 1]], [[1, 1], [1, 0]]   # 单位矩阵 / 转移矩阵
    while n:
        if n & 1:
            result = mul(result, base)
        base = mul(base, base)
        n >>= 1
    return result[0][0]
```

实际用得少，但**能说出来**说明知识面够。

## 复杂度演进

| 版本 | 时间 | 空间 | 定位 |
|---|---|---|---|
| 朴素递归 | O(2ⁿ) | O(n) 栈 | 题目要求的形式，要指出问题 |
| 记忆化 | O(n) | O(n) | 消除重复子问题 |
| 迭代滚动 | O(n) | **O(1)** | **生产首选** |
| 矩阵快速幂 | **O(log n)** | O(1) | 理论最优 |

**能把这条演进链讲完整，这题就满分了** —— 它展示的是"发现瓶颈 → 针对性优化"的完整思路，而不只是会写代码。

## 追问清单

**Q：递归深度会有问题吗？**
会。**Python 默认递归上限只有 1000**（`sys.setrecursionlimit` 可改，但栈仍会爆），比 JVM 更容易撞墙。这是选迭代的实际理由，不只是"省空间"。

**Q：会溢出吗？**
Python 整数是任意精度，**不会溢出**，但大数运算本身会变慢（`f(10000)` 有两千多位）。
静态语言里要注意：32 位整数 n≈46 溢出，64 位 n=92 到顶。竞赛题通常要求对 `1e9+7` 取模。

**Q：如果每次能走 1、2、3 级？**
`f(n) = f(n-1) + f(n-2) + f(n-3)`，边界补到三个（Tribonacci）。

**Q：如果每次能走的步数是任意集合 S？**
```python
def climb_steps(n: int, steps: list[int]) -> int:
    f = [0] * (n + 1)
    f[0] = 1
    for i in range(1, n + 1):          # 外层：台阶数
        for s in steps:                # 内层：步长
            if i >= s:
                f[i] += f[i - s]
    return f[n]
```
这是**完全背包的排列数**形式。
> ⭐ 常见追问：**外层遍历台阶、内层遍历步长 → 排列数**（1+2 和 2+1 算两种，符合爬楼梯语义）；
> 反过来外层步长、内层台阶 → **组合数**（只算一种）。这个顺序区别是考点。

**Q：某些台阶是坏的不能踩？**
`f[bad] = 0`，其余照常递推。

**Q：要输出所有具体走法而不是数量？**
那就不是 DP 而是回溯，复杂度必然指数级 —— 因为**答案本身就有指数条**，这是问题的下界不是算法的问题。

# Q24 · 如何基于数组实现一个 Map？

## 三个核心问题

任何哈希表实现都在回答这三件事。**按这个框架答，条理立刻就有了**：

1. **定位** —— 怎么把任意 key 映射到数组下标？
2. **冲突** —— 两个 key 撞到同一个下标怎么办？
3. **扩容** —— 装满了怎么办？

## 1. 定位：hash → index

### 基本做法

```
index = hash(key) % capacity
```

取模慢。**如果容量取 2 的幂**，可以用位与代替：

```
index = hash(key) & (capacity - 1)
```

因为 `capacity = 2^k` 时 `capacity - 1` 的二进制是低 k 位全 1，位与等价于取模但快得多。

### 为什么要「扰动」

```python
h = hash(key)
h ^= (h >> 16)          # 让高位参与低位的下标计算
```

**原因**：`h & (capacity - 1)` 在容量小的时候**只有最低几位参与运算**。容量 16 就只看低 4 位 —— 高位信息全被浪费了。

如果一批 key 的哈希值恰好低位相同高位不同（比某些人想的常见得多，比如带固定后缀的 ID、对象地址、结构化 key），它们会**全部撞进同一个桶**。

扰动就是把高位异或到低位上，一次异或成本几乎为零，但显著降低这类冲突。

## 2. 冲突处理：两条路线

### 路线 A：拉链法（separate chaining）

每个桶挂一条链表，冲突的往链上加。

```
table[0] → None
table[1] → [k1,v1] → [k9,v9] → None      ← k1 和 k9 冲突
table[2] → [k5,v5] → None
table[3] → None
```

- 查找最坏 O(n)（全撞一个桶）
- 优化方向：链表太长时换成**平衡树**，最坏降到 O(log n)

### 路线 B：开放寻址（open addressing）

不挂链表，冲突了就在数组里往后找空位。

| 探测方式 | 公式 | 特点 |
|---|---|---|
| 线性探测 | `(h + i) % cap` | 简单、**缓存友好**；容易聚集成一大片 |
| 二次探测 | `(h + i²) % cap` | 缓解聚集 |
| 双散列 | `(h₁ + i·h₂) % cap` | 分布最好，要算两次 hash |

> [!danger] 开放寻址的删除必须用墓碑
> 直接把槽位置空会**切断探测链** —— 后面本该继续探测才能找到的元素，就永远找不到了。
>
> 所以删除要写一个特殊的「已删除」标记（tombstone）：查找时**继续往后探测**，插入时**可以覆盖它**。
> 代价是墓碑积累多了要 rehash 清理。
>
> **这是开放寻址最容易被追问、也最容易答错的点。**

### 两条路线的取舍

| | 拉链 | 开放寻址 |
|---|---|---|
| 负载因子 | 可以 > 1 | **必须 < 1**，通常 ≤ 0.7 |
| 缓存局部性 | 差（指针跳来跳去） | **好**（都在连续数组里） |
| 删除 | 简单 | 要墓碑 |
| 内存 | 每节点有指针开销 | 紧凑 |
| 最坏查找 | O(n) / 树化后 O(log n) | 退化时也会很差 |

**判断标准**：内存紧张、key 小、追求缓存性能 → 开放寻址；元素大、删除频繁、不想调负载因子 → 拉链。

## 3. 扩容

```
if size > capacity * LOAD_FACTOR:
    resize()
```

**负载因子（如 0.75）是空间和时间的经验平衡点**：
- 太小（0.5）→ 冲突少但内存浪费
- 太大（1.0）→ 内存省但冲突暴增

扩容做两件事：**容量翻倍 + rehash 所有元素**（因为 `& (capacity-1)` 的结果变了）。

代价 O(n)，所以**能预估大小时要在构造时指定初始容量**，避免反复扩容。

> [!tip] 容量取 2 的幂的第二个好处
> 容量从 `2^k` 变成 `2^(k+1)` 时，下标只多看一个 bit。判断 `hash & oldCap`：
> - 为 0 → 留在原位 `i`
> - 非 0 → 移到 `i + oldCap`
>
> **只需判断一个 bit，不用重新计算 hash。** 这是实现里很漂亮的一个优化，值得主动说。

## 完整实现（拉链法）

```python
class SimpleMap:
    _LOAD_FACTOR = 0.75
    _MISSING = object()                        # 用于区分「值是 None」和「key 不存在」

    def __init__(self, capacity: int = 16):
        self._cap = capacity                   # 必须是 2 的幂
        self._buckets: list[list] = [[] for _ in range(capacity)]
        self._size = 0

    @staticmethod
    def _hash(key) -> int:
        h = hash(key)
        return h ^ (h >> 16)                   # 扰动：高位参与低位

    def _index(self, h: int) -> int:
        return h & (self._cap - 1)             # 位与代替取模

    def get(self, key, default=None):
        h = self._hash(key)
        for k_hash, k, v in self._buckets[self._index(h)]:
            if k_hash == h and (k is key or k == key):   # 先比 hash（快），再比相等（慢）
                return v
        return default

    def put(self, key, value):
        h = self._hash(key)
        bucket = self._buckets[self._index(h)]
        for i, (k_hash, k, _) in enumerate(bucket):
            if k_hash == h and (k is key or k == key):
                bucket[i] = (h, k, value)      # key 已存在 → 覆盖
                return
        bucket.append((h, key, value))
        self._size += 1
        if self._size > self._cap * self._LOAD_FACTOR:
            self._resize()

    def remove(self, key):
        h = self._hash(key)
        bucket = self._buckets[self._index(h)]
        for i, (k_hash, k, v) in enumerate(bucket):
            if k_hash == h and (k is key or k == key):
                bucket.pop(i)                  # 拉链法删除很简单，不需要墓碑
                self._size -= 1
                return v
        return None

    def _resize(self):
        old = self._buckets
        self._cap <<= 1                        # 容量翻倍
        self._buckets = [[] for _ in range(self._cap)]
        for bucket in old:
            for entry in bucket:               # entry = (hash, key, value)
                self._buckets[self._index(entry[0])].append(entry)

    def __len__(self):
        return self._size
```

**几个刻意的设计点，面试时可以点出来**：
- **entry 里存了 hash 值**，避免 resize 和查找时重复计算（hash 一个长字符串不便宜）
- **先比 hash 再比 `==`**：hash 是整数比较，极快；`==` 可能很慢（长字符串、复杂对象）
- `k is key or k == key`：先做 identity 检查，同一个对象直接短路

## key 的契约（必考的追问）

| 规则 | 违反的后果 |
|---|---|
| `a == b` → **必须** `hash(a) == hash(b)` | 存进去，用相等的 key 取不出来（算出了不同的桶） |
| `hash(a) == hash(b)` **不代表** `a == b` | 所以查找必须先比 hash 再比相等，不能只比 hash |
| **key 必须不可变** | key 放进去后被修改，hash 变了，元素留在旧桶里 —— **成了永远找不到的孤儿** |

第三条最容易被忽略。所以字符串、数字、元组这类不可变类型是理想的 key。

> Python 在语言层面强制了这条 —— `list` 和 `dict` 是 unhashable，**根本不让你拿它当 key**。
> Java 不强制，所以用可变对象当 key 是 Java 里的经典 bug 来源。

## 标准库怎么做的（一句话对照，别展开）

| | 冲突策略 | 备注 |
|---|---|---|
| **Python `dict`** | **开放寻址** + 紧凑布局 | 3.7+ 保持插入顺序；索引表和 entry 表分离，省内存 |
| **Java `HashMap`** | **拉链** + 长链转红黑树 | 最坏 O(n) → O(log n) |
| **Go `map`** | 桶数组，每桶 8 槽 | 桶内线性查找，缓存友好 |

> [!warning] 到此为止就够了
> 具体的树化阈值是多少、什么时候从头插改成尾插、并发扩容怎么协同 ——
> **这些是 Java 后端面试的考点，在 Agent 岗位上讲这些是跑题。**
> 面试官想听的是你懂**设计取舍**（拉链 vs 开放寻址、负载因子怎么定、墓碑为什么必要），
> 不是你背过某个版本的源码常量。

## 高频追问

**Q：为什么容量必须是 2 的幂？**
两个理由：① 位与代替取模，快；② 扩容时只需判断一个 bit 决定元素留原位还是移到 `i + oldCap`，不用重算 hash。

**Q：实际时间复杂度？**
平均 O(1)；最坏（全部冲突）拉链是 O(n)，树化后 O(log n)。**注意"平均 O(1)"的前提是 hash 分布均匀** —— 恶意构造的 key 可以让哈希表退化，这就是 **hash collision DoS**，现代语言的对策是加随机种子（Python 的 `PYTHONHASHSEED`）。

**Q：怎么做线程安全？**
三个层次：① 全表一把锁（简单、性能差）；② **锁分段 / 锁桶头**（并发度 = 桶数）；③ **无锁**，读用 CAS + 不可变节点。各语言的具体实现不同，但取舍逻辑是一样的 —— **锁粒度越细，并发度越高，实现越复杂**。

**Q：什么时候不该用哈希表？**
需要**有序遍历**或**范围查询**时 —— 那要用平衡树（`TreeMap` / `std::map`）或跳表，O(log n) 换有序性。哈希表天生无序。
