# Q23 · 爬楼梯：N 级台阶，每次走 1 级或 2 级，求到第 N 级共有多少种走法。用递归实现，解释递推关系和边界条件

## 递推关系怎么推出来的

**别背 `f(n)=f(n-1)+f(n-2)`，要能推。** 推导过程本身就是考点。

> 我要站上第 n 级。**看最后一步**：
> - 如果最后一步迈了 1 级，那我之前必然站在第 **n-1** 级 → 这类走法有 `f(n-1)` 种
> - 如果最后一步迈了 2 级，那我之前必然站在第 **n-2** 级 → 这类走法有 `f(n-2)` 种
>
> 这两类**既不重叠也不遗漏**：
> - **不重叠** —— 最后一步的步长不同，不可能是同一条路径
> - **不遗漏** —— 最后一步只能是 1 或 2，没有第三种可能
>
> 所以直接相加：`f(n) = f(n-1) + f(n-2)`

> [!tip] 「不重不漏」是关键
> 计数类 DP 的正确性全靠这四个字。面试时主动说出来，说明你懂的是**方法**而不是**这道题**。
> 反过来，如果按「第一步」分类也一样成立（第一步走 1 或走 2），结论相同。按最后一步分类通常更自然，因为它直接对应子问题。

## 边界条件从哪来

| 定义 | 值 | 解释 |
|---|---|---|
| `f(0)` | **1** | 站在起点原地不动，算**一种**走法（空走法） |
| `f(1)` | 1 | 只能迈 1 级 |
| `f(2)` | 2 | `1+1` 或 `2` |

**为什么 `f(0)=1` 而不是 0？**

两个角度都要能说：
1. **组合意义**：从 0 级到 0 级，"什么都不做"本身就是一个合法方案，所以是 1 种，不是 0 种。
2. **自洽性**：这样定义能让递推在 n=2 处成立 —— `f(2) = f(1) + f(0) = 1 + 1 = 2`，和手数的结果对上。如果定义 `f(0)=0`，就会算出 `f(2)=1`，错。

也可以避开 `f(0)`，直接定义 `f(1)=1, f(2)=2`，从 n=3 开始递推 —— 完全等价，看个人习惯。

## 这就是 Fibonacci

`f(n)`：1, 1, 2, 3, 5, 8, 13...

和标准 Fibonacci（0,1,1,2,3,5...）**错开一位**。面试时点一句"这本质是 Fibonacci 移位"能显得有全局观，但**别只说这一句** —— 面试官要的是推导。

## 四个版本的实现

### 版本 1：朴素递归 —— O(2ⁿ) 时间，O(n) 栈

```java
static long climb(int n) {
    if (n <= 1) return 1;               // f(0) = f(1) = 1
    return climb(n - 1) + climb(n - 2);
}
```

**这是题目要求的"递归实现"，但必须主动指出它的问题。**

复杂度怎么来的：画递归树。`climb(5)` 会调 `climb(3)` 两次，`climb(2)` 三次…… 每层节点数近似翻倍，总节点数是 O(2ⁿ) 量级。

```
                climb(5)
              /          \
        climb(4)         climb(3)      ← climb(3) 出现了两次
        /     \          /     \
   climb(3) climb(2) climb(2) climb(1) ← climb(2) 出现了三次
```

**重复子问题**就是优化的入口。

### 版本 2：记忆化递归 —— O(n) 时间，O(n) 空间

```java
static long climbMemo(int n) {
    return helper(n, new long[n + 1]);
}

private static long helper(int n, long[] memo) {
    if (n <= 1) return 1;
    if (memo[n] != 0) return memo[n];               // 算过就直接返回
    return memo[n] = helper(n - 1, memo) + helper(n - 2, memo);
}
```

每个 `n` 只算一次，O(n)。**这是从递归到 DP 的桥梁** —— 自顶向下的 DP。

> 小坑：用 `memo[n] != 0` 判断是否算过，前提是结果不可能为 0。本题成立；一般情况下更稳妥的是用 `-1` 初始化或者单独一个 `boolean[] computed`。

### 版本 3：自底向上迭代 —— O(n) 时间，O(1) 空间

```java
static long climbIter(int n) {
    if (n <= 1) return 1;
    long prev = 1, curr = 1;                        // f(0), f(1)
    for (int i = 2; i <= n; i++) {
        long next = prev + curr;
        prev = curr;
        curr = next;
    }
    return curr;
}
```

**滚动变量**把空间从 O(n) 压到 O(1) —— 因为每一步只依赖前两个值，不需要留整个数组。

**生产代码用这个版本**：没有栈溢出风险，空间最省。

### 版本 4：矩阵快速幂 —— O(log n)

如果面试官问"还能更快吗"：

$$\begin{pmatrix} 1 & 1 \\ 1 & 0 \end{pmatrix}^n = \begin{pmatrix} f(n+1) & f(n) \\ f(n) & f(n-1) \end{pmatrix}$$

用快速幂算矩阵的 n 次方，O(log n) 次矩阵乘法。

```java
static long climbFast(int n) {
    if (n <= 1) return 1;
    long[][] base = {{1, 1}, {1, 0}};
    long[][] r = matPow(base, n);
    return r[0][0];                                  // 对应 f(n)
}

private static long[][] matPow(long[][] m, int p) {
    long[][] r = {{1, 0}, {0, 1}};                   // 单位矩阵
    while (p > 0) {
        if ((p & 1) == 1) r = matMul(r, m);
        m = matMul(m, m);
        p >>= 1;
    }
    return r;
}

private static long[][] matMul(long[][] a, long[][] b) {
    long[][] c = new long[2][2];
    for (int i = 0; i < 2; i++)
        for (int j = 0; j < 2; j++)
            for (int k = 0; k < 2; k++)
                c[i][j] += a[i][k] * b[k][j];
    return c;
}
```

> 实际用得少（n 通常不大，而且要取模才不溢出），但**能说出来**说明知识面够。

## 复杂度演进总结

| 版本 | 时间 | 空间 | 说明 |
|---|---|---|---|
| 朴素递归 | O(2ⁿ) | O(n) 栈 | 题目要求的形式，但要指出问题 |
| 记忆化 | O(n) | O(n) | 消除重复子问题 |
| 迭代滚动 | O(n) | **O(1)** | **生产首选** |
| 矩阵快速幂 | **O(log n)** | O(1) | 理论最优（不算大数运算） |

## 追问清单

**Q：会溢出吗？**
会。`f(n)` 是指数级增长的：
- `int`：n ≈ 46 就溢出
- `long`：n = 92 是极限
- 更大要么用 `BigInteger`，要么题目会要求**对 1e9+7 取模**（竞赛标配）

**Q：递归会栈溢出吗？**
会。Java 默认栈约 512KB-1MB，递归深度到几千上万就爆 `StackOverflowError`。**这是选迭代的实际理由**，不只是"省空间"。

**Q：如果每次能走 1、2、3 级？**
`f(n) = f(n-1) + f(n-2) + f(n-3)`，边界要补到三个：`f(0)=1, f(1)=1, f(2)=2`。（这叫 Tribonacci）

**Q：如果每次能走的步数是任意集合 S？**
```java
f[0] = 1;
for (int i = 1; i <= n; i++)
    for (int step : S)
        if (i >= step) f[i] += f[i - step];
```
这就是**完全背包的排列数**形式 —— 注意外层遍历"容量"内层遍历"物品"，得到的是**排列数**（走法有序，1+2 和 2+1 算两种）。反过来外层物品内层容量，得到的是**组合数**。这个区别常被追问。

**Q：如果某些台阶是坏的不能踩？**
`f[bad] = 0`，其余照常递推。

**Q：要求输出所有具体走法而不是数量？**
那就不是 DP 了，是回溯 —— 复杂度必然是指数级的，因为**答案本身就有指数条**。

# Q24 · 如何基于数组实现一个 Map？

## 三个核心问题

任何哈希表实现都在回答这三件事：

1. **定位** —— 怎么把任意 key 映射到数组下标？
2. **冲突** —— 两个 key 撞到同一个下标怎么办？
3. **扩容** —— 数组满了怎么办？

按这个框架答，条理就有了。

## 1. 定位：hash → index

### 基本做法

```java
int index = hash(key) % capacity;
```

但取模慢。**如果容量是 2 的幂**，可以用位与代替：

```java
int index = hash(key) & (capacity - 1);
```

因为 `capacity = 2^k` 时，`capacity - 1` 的二进制就是低 k 位全 1，位与等价于取模，但快得多。

### 扰动函数：为什么要 `h ^ (h >>> 16)`

```java
static int hash(Object key) {
    int h;
    return (key == null) ? 0 : ((h = key.hashCode()) ^ (h >>> 16));
}
```

**原因**：`hash & (capacity - 1)` 在容量小的时候，**只有最低几位参与运算**。比如容量 16，只看低 4 位 —— `hashCode` 的高 28 位全被浪费了。

如果一批 key 的 `hashCode` 恰好低位相同高位不同（很常见，比如某些自增 ID 或者对象地址），它们就会**全部撞进同一个桶**。

扰动做的事：**把高 16 位异或到低 16 位上**，让高位信息也参与下标计算。一次异或，成本几乎为零，但显著降低了这类冲突。

## 2. 冲突处理

### 方案 A：拉链法（Java HashMap 用这个）

每个桶挂一条链表，冲突的元素往链上加。

```
table[0] → null
table[1] → [k1,v1] → [k9,v9] → null      ← k1 和 k9 冲突了
table[2] → [k5,v5] → null
table[3] → null
```

**Java 8 的优化**：当链表长度 ≥ **8** **且**数组容量 ≥ **64** 时，链表转**红黑树**，查找从 O(n) 降到 O(log n)。

> 两个条件都要说：容量 < 64 时优先扩容而不是树化 —— 因为小容量下的长链多半是容量不够导致的，扩容更划算。
> 反向阈值是 6（树中元素少于 6 个退化回链表），**8 和 6 之间留了缓冲**，避免在阈值边界反复转换。

### 方案 B：开放寻址

不挂链表，冲突了就在数组里往后找空位。

| 探测方式 | 公式 | 特点 |
|---|---|---|
| 线性探测 | `(h + i) % cap` | 简单、缓存友好；但容易**聚集**成一大片 |
| 二次探测 | `(h + i²) % cap` | 缓解聚集 |
| 双散列 | `(h1 + i·h2) % cap` | 分布最好，但计算两次 hash |

> [!warning] 开放寻址的删除必须用墓碑
> 直接把槽位置空会**切断探测链** —— 后面本该通过这个位置继续探测才能找到的元素，就永远找不到了。
> 所以删除要写一个特殊的「已删除」标记（tombstone）：查找时继续往后探测，插入时可以覆盖它。
> 代价是墓碑积累多了要 rehash 清理。

### 两种方案对比

| | 拉链 | 开放寻址 |
|---|---|---|
| 负载因子 | 可以 > 1 | 必须 < 1，通常 ≤ 0.7 |
| 缓存局部性 | 差（链表指针跳） | **好**（都在连续数组里） |
| 删除 | 简单 | 要墓碑 |
| 内存 | 每个节点有指针开销 | 紧凑 |
| 代表 | Java HashMap | Python dict、Go map（变体） |

## 3. 扩容

```java
if (++size > capacity * LOAD_FACTOR) resize();
```

**负载因子 0.75 是怎么来的**：空间和时间的经验平衡点。
- 太小（如 0.5）→ 冲突少但内存浪费大
- 太大（如 1.0）→ 内存省但冲突暴增，链表变长

扩容做两件事：**容量翻倍 + rehash 所有元素**（因为 `& (capacity-1)` 的结果变了）。

代价是 O(n)，所以**能预估大小时要在构造时指定初始容量**，避免反复扩容。

## 完整实现（拉链法）

```java
class SimpleMap<K, V> {

    static class Node<K, V> {
        final int hash;
        final K key;
        V value;
        Node<K, V> next;
        Node(int hash, K key, V value, Node<K, V> next) {
            this.hash = hash; this.key = key; this.value = value; this.next = next;
        }
    }

    private static final float LOAD_FACTOR = 0.75f;
    private Node<K, V>[] table;
    private int size;

    @SuppressWarnings("unchecked")
    SimpleMap() { table = new Node[16]; }

    /** 扰动：让高位参与低位的下标计算 */
    private static int hash(Object key) {
        int h;
        return (key == null) ? 0 : ((h = key.hashCode()) ^ (h >>> 16));
    }

    private boolean matches(Node<K, V> e, int h, Object key) {
        // 先比 hash（快），hash 相同才比 equals（慢）
        return e.hash == h && (e.key == key || (key != null && key.equals(e.key)));
    }

    public V get(Object key) {
        int h = hash(key);
        for (Node<K, V> e = table[h & (table.length - 1)]; e != null; e = e.next)
            if (matches(e, h, key)) return e.value;
        return null;
    }

    public V put(K key, V value) {
        int h = hash(key);
        int i = h & (table.length - 1);

        for (Node<K, V> e = table[i]; e != null; e = e.next)
            if (matches(e, h, key)) {                  // key 已存在 → 覆盖
                V old = e.value;
                e.value = value;
                return old;
            }

        table[i] = new Node<>(h, key, value, table[i]); // 头插新节点
        if (++size > table.length * LOAD_FACTOR) resize();
        return null;
    }

    public V remove(Object key) {
        int h = hash(key);
        int i = h & (table.length - 1);
        Node<K, V> prev = null;
        for (Node<K, V> e = table[i]; e != null; prev = e, e = e.next)
            if (matches(e, h, key)) {
                if (prev == null) table[i] = e.next;
                else prev.next = e.next;
                size--;
                return e.value;
            }
        return null;
    }

    @SuppressWarnings("unchecked")
    private void resize() {
        Node<K, V>[] old = table;
        table = new Node[old.length << 1];              // 容量翻倍
        for (Node<K, V> head : old)
            for (Node<K, V> e = head; e != null; ) {
                Node<K, V> next = e.next;               // 先存住，下面会改 e.next
                int i = e.hash & (table.length - 1);
                e.next = table[i];
                table[i] = e;
                e = next;
            }
    }

    public int size() { return size; }
}
```

## `equals` / `hashCode` 契约

这是必考的追问：

| 规则 | 违反的后果 |
|---|---|
| `a.equals(b)` → **必须** `a.hashCode() == b.hashCode()` | 存进去用相等的 key 取不出来（算出不同的桶） |
| `a.hashCode() == b.hashCode()` **不代表** `a.equals(b)` | 所以查找时要先比 hash 再比 equals |
| **key 必须不可变** | key 存进去后被改，hash 变了，元素留在旧桶里 —— **成了永远找不到的孤儿** |

第三条最容易被忽略。所以 `String`、`Integer` 这些不可变类是最理想的 key；用可变对象当 key 一定要保证放进去之后不改参与 `hashCode` 的字段。

## 高频追问

### Q：为什么容量必须是 2 的幂？

两个理由，都要说：

1. **位与代替取模** —— `h & (cap-1)` 比 `h % cap` 快很多。
2. **扩容时不用重算 hash** —— 容量从 `2^k` 变成 `2^(k+1)`，下标只多看一个 bit。判断 `hash & oldCap`：
   - 为 0 → 留在原位 `i`
   - 非 0 → 移到 `i + oldCap`

   **只需判断一个 bit，不用重新计算 hash。** 这是 Java 8 resize 的核心优化。

### Q：Java 8 为什么把头插改成尾插？

头插在**并发** resize 时可能把链表接成**环**，之后 `get` 遇到这个桶就死循环，CPU 直接打满 100%，而且现场很难还原。

尾插保持了原有顺序，不会成环。

> 但要补一句：**HashMap 本来就不保证线程安全**，多线程下用它本身就是错的，尾插只是把一种极端后果变得没那么恐怖。正解是 `ConcurrentHashMap`。

### Q：怎么做到线程安全？

| 方案 | 做法 | 评价 |
|---|---|---|
| `Hashtable` | 所有方法 `synchronized` | 全表一把锁，性能差，已淘汰 |
| `Collections.synchronizedMap` | 包一层同步 | 同样是全表锁 |
| **`ConcurrentHashMap`** | 空桶用 **CAS** 写入；非空桶 `synchronized` 锁**桶头节点** | **锁粒度到单个桶**，并发度 = 桶数量 |

Java 8 的 `ConcurrentHashMap` 还有个亮点：**扩容可以多线程协同** —— 其它线程发现正在扩容时会来帮忙搬运，而不是干等着。

### Q：HashMap 和 TreeMap 怎么选？

| | HashMap | TreeMap |
|---|---|---|
| 底层 | 数组 + 链表/红黑树 | 红黑树 |
| 查找 | 平均 O(1) | O(log n) |
| 有序 | ❌ 无序 | ✅ 按 key 排序 |
| 范围查询 | ❌ | ✅ `subMap` / `headMap` / `tailMap` |
| key 要求 | `hashCode` + `equals` | `Comparable` 或传 `Comparator` |

**只要不需要顺序，HashMap 永远是首选。**

### Q：HashMap 的实际时间复杂度？

- 平均：**O(1)**
- 最坏（全部冲突到一个桶）：Java 8 前 **O(n)**，Java 8 后树化成 **O(log n)**
- 但注意：**树化只在 key 实现了 `Comparable` 时才能有效比较**，否则退化到用 hash 和 identity 比较
