# Agent 协作与路由：Multi-Agent 与模型路由

这一组回答「什么时候不该只用一个 Agent、一个模型」：Multi-Agent 拆职责与上下文，模型路由按能力、风险、成本选模型。两者共同的追问都是：拆分的收益能不能用数据证明。

本文包含：

- Agent Multi-Agent 协作
- Agent 模型路由与多模态

---

## Agent Multi-Agent 协作

Multi-Agent 用多个角色分担上下文和职责。只有任务可以并行、专业能力确实不同或上下文需要隔离时，它才比单 Agent 更划算。

### 复习范围

| 模式 | 特点 |
|---|---|
| Agent as Tool | 主 Agent 保持控制，子 Agent 返回结果 |
| Handoff | 控制权转给另一个 Agent |
| Supervisor | 中央角色分配、检查和汇总 |
| Peer-to-Peer | 角色直接通信，协调成本高 |
| Parallel Workers | 独立任务并行，最后聚合 |

### 高频问题

1. 什么时候该拆子 Agent，什么时候不该拆？
2. Agent as Tool 和 handoff 有什么区别？
3. 子 Agent 应继承多少父上下文？
4. 多 Agent 如何共享文件、状态和消息？
5. 两个 Agent 同时修改同一资源怎么处理？
6. 如何评测协作质量，而不只看最终答案？

### 要点reference

- *什么时候该拆*：三个条件满足其一——任务可并行、专业能力确实不同、上下文需要隔离。dawn-ai 拆 sub-agent 的动机只有第三个：主 Agent 上下文随 plan / skill / RAG 结果膨胀，把深度检索这种脏活派出去，只带摘要回来。不是为了角色扮演。
- *Agent as Tool vs handoff*：Agent as Tool 主 Agent 保持控制，子 Agent 是函数调用，返回值回 ReAct loop；handoff 是控制权转移，像客服转接。dawn-ai 是前者（`DispatchSubAgentTool` 就是普通工具，复用 `ToolRegistry` / `ToolExecutionAspect`），Swarm 是后者。中心化编排 vs 去中心化接力。
- *子 Agent 继承多少父上下文*：dawn-ai 选**零继承**——不读对话历史、不读 Memory，`taskDescription` 必须自包含。sessionId 只用于 Langfuse 归组。代价是主 Agent 要把上下文写进任务描述；收益是子 Agent 上下文干净、行为可预测。
- *怎么共享状态*：不共享。返回值是纯函数 `SubAgentResult(summary, subSteps, status)`，subSteps 只用于观测。`StepCollectorContext` 是 detached 的独立实例，步数计数互不污染。
- *并发写同一资源*：dawn-ai 靠不并发绕开——同步阻塞、一次一个。要并行得先有单写者 lease 和 hash / CAS。
- *怎么评协作质量*：三层——组件（子 Agent 单测）、交互（派发时机对不对、摘要有没有丢限定条件）、端到端。必须有单 Agent 基线证明拆分有收益，否则只是加成本。
- *dawn-ai 实践*：`SubAgentRegistry` 自动收集 `SubAgentDefinition` bean，MVP 只有 `research`（工具白名单 `knowledgeSearchTool` / `loadSkillTool` / `readSkillResourceTool`，**拿不到 `DispatchSubAgentTool`，硬禁递归**，调用栈最多 2 层）。`subAgentExecutor` 2 / 8 / queue 16 `AbortPolicy`。失败处理全是软失败：超时 / 步数超限 / RuntimeException → `PARTIAL_SUCCESS` + 已完成步骤拼摘要（截 200 字，**不再调 LLM**，避免失败时再花 token 再失败）；`AiConfigurationException` 直接抛；派发达上限返回 REFUSED 字符串不抛异常，让模型看见边界自己收敛。SSE 加 `sub_progress` 事件，子 Agent 每步冒泡，前端不认就退化成只看 `step`。设计文档里明确不做：Supervisor、并行派发、自动重试（「业务无关重试容易掩盖真实问题，失败信号交给主 Agent 决策」）。

### 设计约束

- 给每个 Agent 明确输入、输出和权限。
- 委派任务要有可验证的完成条件。
- 并行任务必须真正独立。
- 汇总者要拿到原始证据，不只拿摘要。
- 限制层级、消息轮数、总 token 和重复委派。

### 失败模式

- 多个 Agent 重复调查同一问题。
- 摘要丢失限定条件，错误逐层放大。
- 所有角色使用相同能力和上下文，只增加成本。
- 并发写文件造成覆盖或冲突。
- Supervisor 成为新的单点瓶颈。

## Agent 模型路由与多模态

模型路由根据任务能力、风险、延迟和成本选择模型。多模态路由还要处理消息格式、附件生命周期和能力升级。

### 复习范围

| 主题 | 要讲清的内容 |
|---|---|
| 静态路由 | 按任务类型固定模型 |
| 动态路由 | 分类器或强模型判断复杂度 |
| Capability Routing | 文本、视觉、音频、工具能力匹配 |
| Escalation | 轻模型失败后升级，保留状态和证据 |
| Fallback | 限流、超时、区域故障时降级 |
| 选型评测 | 质量、延迟、成本、稳定性联合比较 |

### 高频问题

1. 为什么不能按 Prompt 长度简单判断任务难度？
2. 第一轮是文本、第二轮出现图片，怎么无感切换模型？
3. 路由器选错模型后如何恢复？
4. 多模型 fallback 如何保持输出和工具协议一致？
5. 轻模型节省的成本，会不会被失败重试吃掉？
6. 如何避免路由本身成为高延迟单点？

### 要点reference

- *为什么不能按 prompt 长度判难度*：长度和难度不相关——一句「帮我看这张图」需要 vision，一段 2000 字的粘贴只是要摘要。要看 required capabilities（TEXT / VISION / TOOLS / STREAMING）和任务类型，不看字数。
- *第一轮文本、第二轮图片怎么切*：最短路径是全程用一个多模态模型，零路由状态。成本敏感时上 capability router：入口按 MIME / magic bytes 算 required capabilities → Model Registry 硬过滤 → 按成本延迟选。第二轮收到图片在**调模型前**升级 session，之后 pin 住不降回（monotonic upgrade），避免来回抖动。前提：历史要存成 provider-neutral 的结构化 parts，不是 `role + content` 字符串。
- *路由选错怎么恢复*：Escalation——轻模型失败后升级，**传原始证据不传摘要**，切换只在新 turn 开始前，不在 streaming 中途。
- *多模型 fallback 保持工具协议一致*：canonical message + provider adapter，工具 schema 定义在自己这边，adapter 负责翻译。fallback 前先判工具有没有产生副作用。
- *轻模型省的钱会不会被重试吃掉*：会。比 `cost_per_success` 不比单价；路由决策写进 Trace，离线算每条路径的成功率和成本。
- *路由怎么不成为单点*：路由用规则或小分类器，不用强模型；决策缓存到 session；路由服务挂了默认走安全模型。
- *dawn-ai 实践*：**没有模型路由**。`ChatRequest` 只有 `message / sessionId / topicId`，历史只存 `role + content` 文本，API 层表达不了图片。单模型 `${CHAT_MODEL}` 从配置读，唯一的「多模型」口子是 sub-agent 的 `model-override` / `temperature-override`，留着没用。`AiAvailabilityChecker` 只检查 API key 有没有配。面试讲这个：为什么当前不需要（单用户、单 provider、纯文本），要加的话第一步是消息模型改 parts，第二步才是 router。

### 设计约束

- 为模型维护能力矩阵和固定版本。
- 路由决策写入 Trace，支持离线复盘。
- 升级模型时传递原始证据，不只传摘要。
- 失败切换前判断工具是否已经产生副作用。
- 比较 `cost_per_success`，不要只比较 token 单价。

### 失败模式

- 把复杂任务误分给轻模型。
- 模型切换后不支持原工具 Schema。
- 多模态附件在重放或持久化时丢失。
- fallback 反复切换，形成隐性循环。
- 新模型公开榜单更高，但核心任务桶退化。
