# Q2 · 如何设计 benchmark，保证不同方案是在相同环境下进行比较？

## 先想清楚：benchmark 到底是什么

benchmark 不是"跑一下看看多快"，它是一次**受控实验**。实验的结论要成立，只需要满足一件事：

> **两组之间只有一个变量不同，其它全都一样。**

所有的技巧 —— 预热、交替执行、固定 seed、看分布 —— 都是在服务这一件事。面试时先把这句话说出来，后面的展开才有骨架。

## 三类必须钉死的东西

### 1. 环境变量

| 项 | 怎么钉 | 不钉会怎样 |
|---|---|---|
| 机器 | 同一台物理机 / 同规格独占实例 | 云上邻居抢 CPU，误差能到 30% |
| CPU | 绑核（`taskset`）、关掉 turbo boost 和降频 | 频率漂移直接改变绝对数值 |
| 内存 | 固定堆大小 `-Xms = -Xmx` | 堆增长本身就是耗时 |
| 运行时 | pin 住 JDK 版本、GC 算法和参数 | G1 和 ZGC 的停顿特征完全不同 |
| 后台 | 关掉定时任务、监控 agent、杀毒 | 随机抖动无法归因 |

### 2. 数据与负载

- 同一份数据集，同样的规模和分布。**别一组用热数据一组用冷数据**。
- 随机的地方固定 seed。
- 并发模型一致：同样的线程数、同样的连接池大小、同样的请求到达模式（恒定速率 vs 泊松到达，结果差很多）。

### 3. 执行流程

- **预热（warmup）**：JVM 需要跑够次数让 JIT 把热点方法编译成机器码。不预热就是在测解释器，数字毫无意义。
- **交替执行 A/B/A/B**：这条最容易被漏。跑完 A 再跑 B，中间机器状态已经漂了（缓存变热、温度升高、内存碎片）。交替执行把漂移平摊到两组。
- **跑够次数**：至少让**组间差异 > 组内方差**，否则你测的是噪声。

## 工具选型

| 场景 | 工具 | 为什么 |
|---|---|---|
| Java 微基准 | **JMH** | 自动处理 warmup、死代码消除、常量折叠、fork 隔离。手写 `System.nanoTime()` 几乎必错 |
| HTTP 压测 | wrk / k6 / Gatling | 能控制到达速率，能出 p99 |
| 全链路 | 真实流量回放 / 影子流量 | 合成负载测不出真实分布 |

> [!danger] 为什么手写微基准几乎必错
> ```java
> long start = System.nanoTime();
> for (int i = 0; i < 1_000_000; i++) { compute(i); }   // 返回值没被用
> long cost = System.nanoTime() - start;
> ```
> JIT 会发现 `compute(i)` 的结果没人用，直接把整个循环**优化掉**，你测出来是 0ns。JMH 用 `Blackhole` 消费返回值来防这个。

## 指标怎么看

**永远不看均值，看分布。**

- p50：典型用户体验
- p95 / p99：**这才是"慢"的地方**，也是 SLA 通常约定的位置
- max：极端情况，通常是 GC 停顿或锁等待
- 方差 / 标准差：**判断这次测量本身可不可信**

一个反例：A 方案均值 10ms、p99 500ms；B 方案均值 15ms、p99 20ms。看均值 A 赢，看用户体验 B 完胜。

## LLM / Agent 场景的额外要求

这套题的语境是 AI，所以这块要主动讲：

| 项 | 做法 |
|---|---|
| 模型版本 | **pin 具体 model id，别用 `latest` 之类的别名** —— 别名背后的模型会悄悄换 |
| 采样随机性 | temperature 归零或固定 seed；**即便如此仍有随机性**，所以每题跑 N≥3 次 |
| prompt | 逐字节固定。改一个空格都可能影响 tokenization |
| 指标 | 除了延迟，**token 消耗和成本必须是一等指标** |
| 延迟拆分 | TTFT（首 token 延迟，影响体感）和总时长要分开看 |
| 缓存 | prompt cache 命中与否，成本差 10 倍。对比时要么都命中要么都不命中 |

> [!warning] LLM benchmark 最容易踩的坑
> **评测集泄漏。** 如果评测用例被写进了 prompt、skill 正文或者 fine-tune 数据里，那就是拿答案考试。要留一份从未进入过任何上下文的 holdout 集。

## 一句话收尾

> benchmark 设计的本质是控制变量。判断一个 benchmark 靠不靠谱，只需要问一句：**如果我把两组的顺序反过来重跑，结论会变吗？** 会变，说明没控住。

# Q3 · 一个系统比竞品慢时，怎样定位具体慢在哪个环节？

## 第 0 步：先确认「慢」这件事本身成立

这一步最容易被跳过，但它排掉的假问题最多。

- 两边测的**是同一件事**吗？同样的请求、同样的数据量、同样的并发？
- 两边的**网络位置**一样吗？你在国内测自己的服务、测竞品的 CDN 边缘节点，这不叫对比。
- 看的是**同一个指标**吗？你看 p99 对方宣传均值，那没法比。
- 是**冷启动**还是稳态？

> 面试时先说这一步，会立刻和"上来就猜数据库"的候选人拉开差距。

## 自顶向下分层剥离

核心思路：**先定位在哪一层，再钻进那一层找具体位置。** 不要一上来就开 profiler —— 如果瓶颈在网络，profiler 什么都看不到。

```
客户端渲染
    ↓
DNS 解析 / TCP 握手 / TLS 协商        ← 首次请求的大头，常被忽略
    ↓
网络传输 RTT + 带宽
    ↓
网关 / LB（限流、鉴权、路由）
    ↓
应用层（业务逻辑、序列化、锁、GC）
    ↓
中间件（缓存、MQ、RPC）
    ↓
数据库（SQL 执行、索引、连接池、锁）
    ↓
下游依赖（第三方 API）
```

**给每一层定一个耗时预算（latency budget）**，然后看谁超预算。比如目标 200ms：网络 30ms、网关 5ms、应用 40ms、DB 80ms、下游 45ms。实测哪层超了就往哪层钻。

## 有 trace 的情况：直接看火焰图

分布式追踪（OpenTelemetry / Jaeger / SkyWalking）是最快的路径 —— span 的宽度就是耗时，最宽的那个就是嫌疑人。

看 trace 要注意三种形态：

| 形态 | 含义 |
|---|---|
| 一个 span 特别宽 | 单点瓶颈，钻进去 |
| 很多小 span 串行排列 | **N+1 问题**，要批量化或并行化 |
| span 之间有空白间隙 | 时间花在**没有埋点的地方** —— 队列等待、线程池排队、GC 停顿 |

第三种最阴，也最能体现水平。span 加起来不等于总时长时，差值就是答案。

## 没有 trace 的情况：用方法论兜底

**RED（看服务）**：Rate 请求量、Errors 错误率、Duration 耗时分布。
**USE（看资源）**：Utilization 使用率、Saturation 饱和度、Errors 错误。对每个资源（CPU、内存、磁盘、网络、连接池、线程池）都过一遍。

> Saturation 比 Utilization 更重要。CPU 使用率 60% 但 run queue 长期 > 核数，说明已经在排队了。

## 钻进应用层：profiler 怎么用

用 **async-profiler**（低开销、无 safepoint bias），关键是**两种模式都要跑**：

| 模式 | 测量的东西 |
|---|---|
| `-e cpu` | 真正消耗 CPU 的代码 |
| `-e wall` | 墙上时钟时间，**包括阻塞等待** |

**两者的差值就是"在等"的时间。**

- wall 火焰图很宽、cpu 火焰图很窄 → 在等 IO 或等锁，加机器没用
- 两个都宽 → 真在烧 CPU，要优化算法或加机器
- `-e lock` 看锁竞争，`-e alloc` 看内存分配（分配多 → GC 压力大）

Java 上还有 `arthas trace` 做方法级耗时下钻，适合已经缩小到某个类之后。

## 四类根因，处理方式完全不同

| 根因 | 症状 | 处理方向 |
|---|---|---|
| **CPU 密集** | CPU 打满，cpu 和 wall 火焰图形状一致 | 优化算法、加缓存、水平扩容 |
| **IO 等待** | CPU 低但延迟高，wall 远宽于 cpu | 并行化、批量化、异步化、连接池调大 |
| **锁竞争** | 并发上不去，加机器不见效，lock profiler 有热点 | 减小锁粒度、无锁结构、分片 |
| **GC 停顿** | 延迟毛刺规律出现，GC 日志对得上 | 减少分配、调整堆和 GC 算法、换 ZGC |

> 判断顺序建议：**先看 GC 日志**（最容易排除也最容易被忽略），再看 CPU 曲线，再看 wall vs cpu，最后才是业务逻辑。

## 对比竞品的现实做法

拿不到竞品的内部可观测数据，所以只能：

1. **黑盒分层测量**：DNS、TLS、TTFB、总时长分别测（`curl -w` 就能出这几个数），先看差距在网络还是在服务端。
2. **对齐自己的分层预算**，看自己哪层明显不合理。
3. **找架构差异假设**：对方是不是有边缘缓存？是不是预计算？是不是流式返回让体感更快？

最后一条很关键 —— **有时候对手不是更快，是更早开始给东西看**。流式输出把 TTFB 从 2s 降到 200ms，总时长没变但体感天差地别。

# Q4 · Agent 能否参与性能分析和问题定位？

## 结论

能，而且投入产出比很高。但要说清楚**边界在哪**，否则听起来像在吹。

一句话定位：**Agent 是「跑工具 + 读输出 + 提假设」的助手，不是拍板的人。**

## Agent 真正擅长的部分

性能排查里有大量**低创造性、高体力消耗**的活，这正好是 Agent 的主场：

| 活 | 人做 | Agent 做 |
|---|---|---|
| 读火焰图找热点 | 眼睛扫，容易漏 | 解析 collapsed stack，按占比排序输出 |
| 翻几万行日志找异常模式 | 几小时 | 几分钟 |
| 跨多个 trace 找共性 | 手动比对 | 批量拉取 + 聚合 |
| 写复现脚本 / 压测脚本 | 半天 | 十分钟 |
| 把散落的证据合成报告 | 枯燥 | 天生擅长 |
| 列候选假设并排序 | 受经验局限 | 覆盖面广，能列出你没想到的 |

**最大的价值是覆盖面**：人排查时会不自觉地锚定在自己熟悉的方向上，Agent 会老老实实把所有分支都过一遍。

## Agent 的边界

| 边界 | 为什么 |
|---|---|
| 业务语义判断 | "这个接口本来就该慢 3 秒，它在做全量对账" —— Agent 不知道 |
| 历史包袱 | "这段代码是为了兼容某个客户加的，不能删" —— 不在代码里 |
| 线上写操作 | 改配置、重启、扩容、回滚 —— 错了代价太大 |
| 最终定性 | 结论要有人签字，出了事 Agent 不背锅 |

## 工具设计：这才是能不能落地的关键

Agent 能力上限由**给它什么工具**决定，而不是模型多强。分两档给：

**放开（只读，随便跑）**
- metrics 查询（Prometheus / Splunk）
- trace 查询
- 日志检索
- 只读 profiler（attach 采样，不改变进程行为）
- 读代码、读配置

**Gate（必须人工确认）**
- 任何配置修改
- 重启 / 扩缩容 / 流量切换
- 数据库写操作
- 生产环境的 attach 类操作（有极小概率影响进程）

> 这个分档背后是一个通用原则：**按「可逆性」来划线**。可逆的放开，不可逆的 gate。这条在设计任何 Agent 的工具面时都适用，展开见 [[03-Coding-Agent-实践]]。

## 落地形态：把 SOP 变成 Skill

最有效的用法不是「你帮我看看为什么慢」，而是**把 Q3 那套排查流程写成一个 Skill**，让 Agent 按步骤走：

1. 每一步必须**产出证据**（命令输出、图表、数据），不能只给结论
2. 每一步结束**回报当前假设和排除了什么**
3. 关键节点（比如"确定是 DB 问题，准备看慢查询"）停下来让人确认方向
4. 最终报告的格式固定：现象 → 排查路径 → 证据 → 根因 → 建议 → 未验证项

**「未验证项」这一栏很重要** —— 逼 Agent 显式说出哪些是推测、哪些是实锤，比它自信满满地给个结论有用得多。

## 面试怎么答

> 能参与，而且在体力活上提效很明显 —— 读火焰图、翻日志、找共性、写复现脚本这些，能把几小时压到几十分钟。
> 但它的角色是助手：提假设、跑工具、整理证据。**需要业务语义的判断和线上写操作要人来兜**。
> 落地的关键不在模型，在工具面设计 —— 只读工具放开，不可逆操作 gate 住；再把排查 SOP 固化成流程，要求每一步都产出证据、显式标注哪些还没验证。
