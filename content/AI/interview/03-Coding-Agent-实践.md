# Q10 · 平时主要使用哪些 Coding Agent？

## 先给分类框架，再填工具

直接列工具名是最差的答法。先给一个**按介入深度的分层**，再说自己在每层用什么、为什么：

| 层 | 形态 | 代表 | 适合的活 |
|---|---|---|---|
| **终端 / 自主型** | 能执行命令、改多文件、自己迭代 | Claude Code、Codex CLI、Gemini CLI | 重构、排查、跨文件改动、写测试 |
| **IDE 内联型** | 在编辑器里补全和小范围改 | Cursor、GitHub Copilot、Windsurf | 写单个函数、补样板代码、改小 bug |
| **Review / CI 型** | 挂在 PR 或流水线上 | Copilot code review、自建 review skill | merge 前把关、规范检查 |

## 选型维度（这才是面试官想听的）

| 维度 | 为什么重要 |
|---|---|
| **能不能执行命令** | agentic 和纯补全的分水岭。能跑 test 才能自我验证，不能跑就只是个高级补全 |
| 上下文窗口 | 决定能不能一次装下整个模块 |
| 权限模型 | 能不能细粒度控制哪些操作要确认 —— 生产环境的硬门槛 |
| 可扩展性 | hooks / skills / MCP —— 能不能把团队的规范和 SOP 固化进去 |
| 企业合规 | 代码是否出网、有无数据留存、能否私有部署 |

## 怎么答才不假

> 主力用 XX 做复杂任务 —— 因为它能跑命令、能自己验证，重构和排查这类活能一次性做完。
> 写代码时在 IDE 里用 YY 补全，反馈快，不用切窗口。
> PR 上挂了 review，主要是卡规范类问题。
> 切换的判断标准很简单：**这个活需不需要「改完跑一下看对不对」**。需要就上自主型，不需要就补全。

> [!warning] 别踩的坑
> - 报十个工具名 —— 显得没有主见
> - 说"都差不多" —— 显得没深用过
> - 只说工具不说场景 —— 显得没方法论

# Q11 · 如何使用 Coding Agent 完成项目开发？

## 一句话工作流

**先立地基 → 澄清需求 → 出计划让人 review → 小步执行 → 只信实际输出 → 沉淀成可复用资产。** 全程在隔离分支里干。

## 阶段展开

### 阶段 0：立地基（一次性投入，收益最大）

在仓库根目录写 `CLAUDE.md` / `AGENTS.md`，内容包括：

- 构建 / 测试 / lint 的**确切命令**（别让它猜）
- 目录结构和各模块职责
- 代码风格约定、命名习惯
- **禁忌清单**：不能改的文件、不能引的依赖、不能用的 API

> 这份文件的质量直接决定了后面所有产出的下限。写它花的两小时，比后面调 prompt 花的二十小时都值。

### 阶段 1：澄清，别急着写

需求模糊时**先让它提问**。直接说"帮我实现登录"，它会自己编一堆假设，然后你在代码层面发现假设错了，返工成本极高。

### 阶段 2：先出计划，人 review 计划

**改计划比改代码便宜一个数量级。** 让它先输出：要改哪些文件、每个文件改什么、按什么顺序、怎么验证。人看完确认了再动手。

计划阶段最容易发现的问题：它准备去改一个不该动的模块、它误解了某个概念、它漏了一个依赖方。

### 阶段 3：TDD 执行

**先让它写测试再写实现。** 好处有三个：
1. 测试就是需求的可执行表达 —— 测试写错了说明需求理解错了，这时候纠正最便宜
2. 给了它一个客观的完成标准，不用靠"感觉写完了"
3. 防止它改着改着把别的东西改坏

### 阶段 4：验证 —— 不信自述，只信输出

> [!danger] 这是最关键的一条
> Agent 说"测试都通过了"**不算数**，要看实际的命令输出。
> 它会因为各种原因产生偏差：跑了但没看全、跑的是子集、跑挂了但认为无关紧要。
> 规矩很简单：**没有贴出实际输出的"完成"，一律视为未完成。**

### 阶段 5：隔离

用 worktree 或独立分支。理由不是怕它写错 —— 是怕**写错之后不好回退**。在独立分支上，最坏情况就是丢弃整个分支，代价可控。

### 阶段 6：上下文卫生

- **一个 session 一件事**。任务切换时上下文里的残留会持续污染判断。
- 发现它开始车轱辘话、反复改同一处、越改越乱 —— **上下文脏了，重开**，别硬掰。
- 长任务中途做一次 handoff，把结论沉淀成文档再开新 session。

### 阶段 7：沉淀

同一个流程走过三次以上，就该固化：

| 形态 | 适合什么 |
|---|---|
| **Skill** | 有多步流程和判断的 SOP（发布、review、诊断） |
| **slash command** | 高频的单一动作 |
| **hook** | 必须每次都执行的强制动作（提交前格式化、禁止改某些文件） |

**hook 和 skill 的区别要说清楚**：skill 是"模型可以选择用"，hook 是"harness 强制执行，模型绕不过去"。真正的红线（比如禁止 push 到主干）必须用 hook，写在 skill 里模型可能会忽略。

# Q12 · 什么是 Context Engineering？

## 定义

> **在有限的上下文窗口里，决定「放什么、什么时候放、放多少、怎么排」，让模型在每一步都拿到刚好够用的信息。**

和 prompt engineering 的关系：

| | Prompt Engineering | Context Engineering |
|---|---|---|
| 范围 | **一次调用**怎么写 | **整个 agent 生命周期**里上下文怎么演化 |
| 关注 | 措辞、示例、格式 | 装配、检索、压缩、隔离 |
| 类比 | 写好一句话 | 管理一块稀缺内存 |

**最好的类比就是内存管理**：上下文窗口是一块固定大小的高速内存，什么该常驻、什么该按需换入、什么该换出、什么该压缩 —— 全是经典的资源调度问题。

## 四个基本动作

### Write —— 写出去

把信息落到上下文之外，需要时再读回来。

- memory 文件 / 外部笔记：跨 session 存活
- scratchpad：本次任务的中间结论，写到文件里而不是堆在对话里
- 好处：**信息没丢，但不占窗口**

### Select —— 选进来

只把当前这一步需要的东西放进来。

- RAG 检索：按语义召回相关片段，而不是把整个知识库塞进去
- **tool search**：工具很多时先搜再加载 schema
- **skill 渐进加载**：description 常驻（几十 token），正文按需读（几千 token）

### Compress —— 压缩

已经在上下文里的东西，想办法占更少空间。

| 手段 | 做什么 | 什么时候用 |
|---|---|---|
| **compaction** | 把早期对话**摘要**成一段 | 快到窗口上限了 |
| **context editing** | **清理**旧的 tool_result / thinking 块 | 老的工具输出已经没用了 |
| 裁剪 | 直接丢最老的消息 | 最粗暴，会丢信息，慎用 |

摘要和清理的区别：摘要保留信息但降低精度，清理是直接扔。老的工具输出（比如十轮前的一次目录列表）通常可以直接扔。

### Isolate —— 隔离

把会产生大量中间垃圾的活，扔进**独立的上下文**里做，只回传结论。

这就是 subagent 的核心价值 —— 不是"多个模型协作"，而是**上下文隔离**。

举例：要在 200 个文件里找某个函数的所有调用点。
- 不隔离：200 个文件的内容全进主上下文，窗口爆了，而且噪声淹没了真正的任务
- 隔离：派一个 subagent 去搜，它自己看完 200 个文件，只回传"在这 5 处被调用"
- **主上下文只增加了 5 行**

## 排布原则：缓存决定顺序

prompt cache 是**前缀匹配**的 —— 从头开始逐字节比对，遇到第一个不同的字节，**从那里往后全部失效**。

所以排布规则很硬：

```
稳定 ────────────────────────────────► 易变
tools  →  system  →  历史消息  →  检索结果  →  当前输入
```

推论（都是实战踩过的坑）：

| 操作 | 后果 |
|---|---|
| 中途增删工具 | 整个缓存全废（工具在最前面） |
| system prompt 里放 `当前时间：{now}` | **每次请求缓存全失效**，成本翻十倍 |
| 中途换模型 | 缓存全废 |
| JSON 序列化 key 顺序不固定 | 字节不一致，缓存失效 |

对应的解法：

| 问题 | 解法 |
|---|---|
| 要中途加操作指令 | 追加一条 system 角色的消息到 `messages` 尾部，而不是改顶层 system |
| 要中途换工具集 | 用 tool search（追加 schema 而非替换） |
| 某段子任务想省钱换小模型 | 开 subagent 用小模型，主循环模型不变 |

**排查方法**：看响应里的 `cache_read_input_tokens`。重复请求它一直是 0，就说明有东西在偷偷让缓存失效 —— 九成是时间戳或 UUID。

## 核心指标：信噪比

不是"塞了多少"，是**塞进去的东西里有多少是这一步真正需要的**。

常见坏味：

| 坏味 | 后果 |
|---|---|
| 整个文件糊进去 | 90% 是噪声，模型注意力被稀释 |
| 历史无限增长 | 早期的错误尝试一直在，模型反复被带偏 |
| 工具定义几十个 | 选错工具的概率飙升 |
| 失败的尝试留在上下文里 | 模型会"学习"这些失败模式，继续犯同样的错 |

最后一条尤其反直觉：**失败的尝试不清理，模型会倾向于重复它。** 因为上下文里出现过的模式，本身就在提高该模式的输出概率。

# Q13 · 如何针对开发、测试、运维等不同任务组织 Skills？

## 先理解 Skill 的加载机制

Skill 的设计精髓是**两段式加载**：

| 部分 | 何时进上下文 | 成本 | 作用 |
|---|---|---|---|
| **description** | **始终常驻** | 几十 token | 让模型知道"有这么个能力，什么时候该用" |
| **正文（SKILL.md）** | 判断相关后才读 | 几千 token | 告诉模型"具体怎么做" |
| **references/** | 正文里指到才读 | 任意大 | 详细规范、模板、示例 |

理解了这个，组织原则就是自明的：

> **description 是唯一花常驻成本的部分，所以它决定命中率，是调优的第一优先级。**

## 组织原则

### 1. 按任务动词切，不按知识领域切

```
✅ review-pr / create-test-plan / release-prep / diagnose-issue
❌ java-knowledge / testing-knowledge / devops-knowledge
```

原因：Skill 是被**任务**触发的，不是被**话题**触发的。「Java 知识」这种 description 没法写触发条件 —— 什么时候算"需要 Java 知识"？

### 2. description 里必须写触发条件和触发词

```yaml
# ❌ 差
description: 代码审查相关的规范和流程

# ✅ 好
description: |
  对 xxx 仓库的 PR 或本地改动做代码审查。当用户说"review PR 1234"、
  "检查我的改动"、"code review"，或在该仓库目录下要求审查代码时使用。
  PR 模式会把结论发成 GitHub comment，本地模式会存报告并进入修复循环。
```

**触发词要写用户实际会说的话**，包括中文口语说法。这直接决定命中率。

### 3. 正文写流程和检查清单，不写百科

Skill 正文的定位是 **SOP，不是教材**。

```markdown
✅ 1. 用 `gh pr diff` 拿到改动
   2. 按 references/checklist.md 逐条过
   3. 每个发现要有 file:line 和复现路径
   4. 输出前自查：有没有把风格问题报成 bug

❌ 什么是代码审查？代码审查是一种软件质量保证活动...
```

### 4. 大内容拆到 references/，正文只放指针

正文控制在能一眼读完的长度，详细规范放子文件，用一行指出去："具体规则见 `references/java-rules.md`"。模型需要时才会去读。

## 分层示例

| 层 | Skill | description 要点 |
|---|---|---|
| **开发** | `scaffold-module` | 新建模块 / 新增 service 时用 |
| | `commit-convention` | 提交代码、写 commit message 时用 |
| **测试** | `create-test-plan` | 从 Jira ticket 生成测试计划 |
| | `report-test-results` | 测完回填结果到 ticket |
| **运维 / 发布** | `release-prep` | 发版前摸底 diff 和 ticket |
| | `diagnose-issue` | 线上问题排查 SOP |

## 两个实战问题

### 防误触发

description 之间**语义要互斥**。两个 skill 的 description 有重叠，模型会随机挑一个，表现就是"有时候对有时候不对"，极难排查。

发现误触发时，修的方式是**给两边都加否定条件**：
- A: "...用于 X 场景。**不要用于 Y**，那种情况用 B。"
- B: "...用于 Y 场景。**不要用于 X**。"

### 迭代闭环

```
命中率不行  → 改 description（触发词、触发条件）
效果不行    → 改正文（流程、检查清单）
上下文太重  → 把内容下沉到 references/
```

改完怎么确认真的变好了？—— **这正是 Q16 的问题**，见 [[04-Agent-工程化评测]]。这两题连着答会很漂亮。

# Q14 · 如何使用 Agent 做 Auto Research？

## 整体形态

```
        研究问题
           │
    ┌──────┴──────┐
    │ 1. 分解       │  拆成互相独立的子问题
    └──────┬──────┘
           ▼
    ┌─────────────┐
    │ 2. 多路并行搜 │  不同角度、不同来源，各自独立上下文
    └──────┬──────┘
           ▼
    ┌─────────────┐
    │ 3. 深读       │  值得读的才展开读全文
    └──────┬──────┘
           ▼
    ┌─────────────┐
    │ 4. 对抗验证   │  另一个 agent 专门去证伪
    └──────┬──────┘
           ▼
      有新信息？──是──► 回到 2
           │否
           ▼
    ┌─────────────┐
    │ 5. 综合成文   │  带来源标注
    └─────────────┘
```

## 关键设计点

### 分解：为了上下文隔离，不是为了"并行快"

拆子问题的**首要目的是隔离**（见 Q12 的 Isolate）。每个 subagent 自己去读几十个网页，只回传几行结论，主上下文才装得下。并行带来的速度提升只是副产品。

拆分原则：子问题之间**尽量无依赖**。有依赖的要串行（A 的结果决定 B 搜什么）。

### 来源多样性：防回声室

最常见的失败是：五个 agent 用几乎一样的关键词搜，返回几乎一样的结果，然后互相印证，得出一个**看起来证据充分实际上只有一个来源**的结论。

解法是**强制分配不同的检索角度**：

| 角度 | 例子 |
|---|---|
| 按来源类型 | 官方文档 / 社区讨论 / 论文 / 代码仓库 / 新闻 |
| 按时间 | 最新进展 / 历史沿革 |
| 按立场 | 支持的证据 / **反对的证据** |
| 按实体 | 按公司 / 按产品 / 按人物分头查 |

"反对的证据"这一路单独派人去搜，效果特别好 —— 它逼着系统去找反例，而不是一路确认偏误。

### 对抗验证：证伪，不是复核

**"再检查一遍"和"想办法推翻它"是完全不同的指令。** 前者倾向于确认，后者才能发现问题。

```
❌ 请复核这个结论是否正确
✅ 请尝试推翻这个结论。找出任何反例、过时信息、来源不可靠或推理跳跃的地方。
   如果无法确定，默认判定为「不成立」。
```

需要更强保证时可以用**多视角投票** —— 三个验证者各带一个不同的镜头（事实准确性 / 来源可靠性 / 逻辑自洽性），多数通过才算数。

### 收敛条件：loop-until-dry，不是跑固定轮数

| 方案 | 问题 |
|---|---|
| 跑固定 N 轮 | N 小了漏长尾，N 大了纯烧钱 |
| 一直跑到"觉得够了" | 永远不停 |
| **连续 K 轮没有新信息就停** | ✅ 对未知规模的探索，这是正确的收敛条件 |

实现要点：维护一个"已见过的信息"集合，**去重要对着「所有见过的」而不是「已确认的」** —— 否则被判否的信息每轮都会重新出现，永远收敛不了。

### 溯源：不能溯源的必须标出来

每条结论挂来源。溯不到源的**明确标为「未验证」**，不能混在确定结论里。

这一条看似基础，但它是 auto research 能不能用的分水岭 —— **一份分不清哪些是实锤哪些是推测的报告，等于没用**，因为人还得全部重新核一遍。

### 预算与截断透明

有 token 上限，被截断的部分**要显式 log 出来**。

> [!warning]
> 静默截断是最危险的 —— 报告读起来完整无缺，实际上漏了一半。
> 规矩：任何地方做了 top-N、采样、跳过重试，都要在结果里写明"因为 X 原因，Y 部分未覆盖"。

## 常见失败模式汇总

| 失败 | 表现 | 对策 |
|---|---|---|
| 回声室 | 结论看似多方印证，实则同源 | 强制分配不同检索角度 |
| 幻觉引用 | 编造 URL 或论文标题 | 强制访问验证，访问不到就丢弃 |
| 无限发散 | 越搜越偏，最后在研究别的问题 | 每轮回到原始问题重新对齐 |
| Token 爆炸 | 一次研究烧掉巨额成本 | 预算硬上限 + 分阶段确认 |
| 确认偏误 | 只找支持的证据 | 单独派一路专门找反例 |
