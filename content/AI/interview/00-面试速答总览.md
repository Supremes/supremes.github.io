## 一、性能工程与 benchmark（Q2-4）

### Q2 · 如何设计 benchmark，保证不同方案在相同环境下比较？

**一句话**：benchmark 的本质是控制变量实验 —— 只留一个变量，其它全钉死，然后跑够多次看分布而不是看单次。

采分点：
- **环境钉死**：同一台机器、同一容器规格、固定 CPU/内存、固定运行时版本和 GC 参数。云上要注意邻居噪声，最好独占。
- **预热**：JVM 要跑够 warmup 让 JIT 编译完，缓存要预热。用 JMH 而不是自己 `System.nanoTime()` —— 它会帮你处理死代码消除和常量折叠。
- **交替执行**：跑 A/B/A/B，不要跑完 A 再跑 B。机器状态会随时间漂移（温度、后台任务），交替能把漂移平摊到两组。
- **看分布**：p50/p95/p99 + 方差，不看均值。均值会被长尾骗。
- **LLM 场景额外**：pin 住具体 model id（别用 `latest` 别名）、固定 prompt、temperature 归零或固定 seed、同一题跑 N 次（N≥3），**token 消耗和成本也是指标**。

> [!warning] 陷阱
> 说不出「为什么要预热」和「为什么要交替跑」就是没做过。另外被问「跑几次够」时别说"跑一次"，正确答法是"跑到方差收敛，或者至少让组间差异大于组内方差"。

### Q3 · 一个系统比竞品慢时，怎样定位具体慢在哪个环节？

**一句话**：先确认两边测的是同一件事，再自顶向下按层剥离，用 trace 定位到哪一层，用 profiler 定位到层内哪一行。

采分点：
- **第 0 步是对齐口径**：同样的请求、同样的数据量、同样的网络位置、同样的并发。很多"慢"是测法不同，不是系统不同。
- **分层拆解**：客户端 → DNS/TLS/网络 RTT → 网关 → 应用 → 中间件 → DB → 下游依赖。每层给一个耗时预算（latency budget），看谁超预算。
- **有 trace 就看 trace**：OpenTelemetry / Jaeger 的 span 火焰图，哪个 span 宽就是谁的锅。
- **没 trace 就用方法论**：RED（Rate/Errors/Duration，看服务）+ USE（Utilization/Saturation/Errors，看资源）。
- **进到应用内**：async-profiler 出火焰图，**wall-clock 模式和 CPU 模式都要跑** —— 两者差得大说明在等（IO/锁），差得小说明真在烧 CPU。
- **四类根因分开判**：CPU 密集 / IO 等待 / 锁竞争 / GC 停顿。

> [!warning] 陷阱
> 只看均值。慢通常是 p99 的事，均值看不出来。另外别一上来就猜"肯定是数据库"—— 先量再改是底线。

### Q4 · Agent 能否参与性能分析和问题定位？

**一句话**：能，但它的角色是「跑工具 + 读输出 + 提假设」的助手，拍板和高危操作留给人。

采分点：
- **擅长**：跑 profiler 并解读火焰图、批量翻日志/trace 找异常模式、写复现脚本和压测脚本、把多份证据合成对比报告、把候选假设按可能性排序。
- **不擅长**：需要业务语义的判断（"这个接口本来就该慢"）、跨系统的历史知识、需要线上写操作的验证。
- **关键在工具设计**：只读工具（metrics 查询、trace 查询、日志检索、只读 profiler）可以放开；写操作（改配置、重启、扩容）必须 gate 在人工确认后面。
- **落地形态**：把排查 SOP 写成 Skill，Agent 按步骤走，每步必须产出证据，人在关键节点 review。

> [!warning] 陷阱
> 别说"Agent 能自动定位性能问题"，这是吹。正确的表述是"能把 3 小时的体力活压到 20 分钟，但结论要人签字"。

## 二、Agent 运行机制（Q5-9）

### Q5 · 一次 Agent 请求从用户输入到最终回答的完整链路是什么？

**一句话**：输入 → 组装上下文 → 调模型 → 看 `stop_reason` → 要么出答案，要么执行工具把结果回灌再调一次，循环到收敛。

采分点（按顺序背）：
1. 入口：前端 → 网关 → Agent 服务
2. **上下文组装**：system prompt + 工具定义 + 历史消息 + 检索到的知识 + 当前输入
3. **预算检查**：token 计数，超了就压缩/裁剪/compaction
4. **调 LLM**（带 tools、tool_choice、thinking/effort）
5. **看 `stop_reason`** 分叉：`end_turn` 出答案 / `tool_use` 去执行工具
6. **执行工具**：参数校验 → 权限 gate → 执行 → 拿结果
7. **回灌**：完整 assistant content（含 `tool_use` 块）追加为 assistant 消息，`tool_result`（带 `tool_use_id`）追加为 user 消息
8. 回到第 4 步循环
9. 流式输出：SSE 把 delta 推给前端
10. 收尾：trace 落库、token 计费、指标上报

> [!warning] 陷阱
> 漏掉「API 是无状态的，每轮要把完整历史重发一遍」这句就减分。

### Q6 · 大模型如何判断是否需要调用工具？

**一句话**：没有额外的判断器 —— 工具定义作为 prompt 的一部分进上下文，模型经过训练后把「输出一个 tool_use 块」当成一种合法续写，本质还是 next-token prediction。

采分点：
- 工具的 `name` / `description` / `input_schema` 会被渲染进 prompt 的最前面（在 system 之前），所以**改工具集会让整个 prompt cache 失效**。
- **description 要写「什么时候调用」，不只写「做什么」**。这是命中率最大的杠杆。
- 工程可控：`tool_choice` = `auto`（默认）/ `any`（必须调至少一个）/ `{type:"tool",name}`（强制指定）/ `none`（禁用）。
- 工具太多会稀释注意力 → 用 tool search / `defer_loading` 按需加载。
- 三种典型 failure mode：**该调不调**（描述缺触发条件）、**乱调**（描述太宽泛）、**参数幻觉**（schema 描述不清，可用 `strict: true` 约束）。

### Q7 · Function Call 和 Tool Result 如何重新进入模型上下文？

**一句话**：作为普通消息追加到 `messages` 数组里重发 —— assistant 消息带 `tool_use` 块，紧跟一条 user 消息带 `tool_result` 块，靠 `tool_use_id` 配对。

采分点：
- **必须回填完整的 `response.content`**，不能只取 text。丢了 `tool_use` 块，下一轮 `tool_result` 就找不到对应的调用，直接 400。
- `tool_result` 放在 `role: "user"` 的消息里（Anthropic 的设计；OpenAI 是单独一条 `role: "tool"`）。
- **并行调用**：一条 assistant 消息里可能有多个 `tool_use` 块，所有 `tool_result` 必须放进**同一条** user 消息。拆开发会让模型以后不再做并行调用。
- **失败也要回**：`is_error: true` + 错误文本。静默丢弃会让模型卡住。
- 有 thinking 块时，同模型续跑要原样带回去。

### Q8 · Agent Loop 在什么条件下继续执行，又在什么条件下结束？

**一句话**：`stop_reason == "tool_use"` 就继续，`end_turn` 就结束 —— 但工程上必须再叠一层硬性熔断，光靠模型自己收敛不安全。

采分点：

| 类别 | 条件 |
|---|---|
| 继续 | `tool_use`（要调工具）、`pause_turn`（server tool 达内部迭代上限，原样重发即可续跑） |
| 模型侧结束 | `end_turn` 正常完成、`max_tokens` 被截断、`stop_sequence`、`refusal` 安全拒绝 |
| 工程侧熔断 | 迭代次数上限、token/成本预算耗尽、wall-clock 超时、用户中断、连续 N 次工具失败、检测到重复循环 |

> [!warning] 陷阱
> 只判 `end_turn` 不判其它 —— `max_tokens` 会被当成"正常结束"，用户拿到半截答案还不知道。必须显式处理每一种 `stop_reason`。

### Q9 · ReAct 是什么？

**一句话**：Reasoning + Acting —— 让模型交替产出「思考 → 行动 → 观察」三元组并循环，直到给出最终答案。

采分点：
- 对比纯 CoT：CoT 只在脑子里推，接触不到外部世界，事实性问题必幻觉；ReAct 能去查。
- 对比纯 Action：没有 Thought 环节，模型不做规划，工具乱调。
- **早期是纯 prompt 工程**：用文本模板 `Thought: ... Action: ... Observation: ...` 让模型续写，靠 stop sequence 截断，再正则解析 —— 脆得很。
- **现在被原生 tool use 取代**：`tool_use` / `tool_result` 是结构化 block 不用解析，extended thinking 承担 Thought 的角色。
- 所以标准答法是：**ReAct 是思想，现代 API 的 tool use + thinking 就是它的工程化实现**。

## 三、Coding Agent 实践（Q10-14）

### Q10 · 平时主要使用哪些 Coding Agent？

**一句话**：按介入深度分三层用 —— 终端自主型跑复杂任务，IDE 内联型写代码，CI 型做 review。

采分点：
- 终端/自主型：Claude Code、Codex CLI、Gemini CLI —— 能跑命令、能改多文件、适合重构和排查。
- IDE 内联型：Cursor、GitHub Copilot、Windsurf —— 补全和小范围改动，反馈快。
- Review/CI 型：Copilot code review、自建 review skill —— 卡在 merge 前。
- **选型维度**：上下文窗口、能不能执行命令（agentic vs 纯补全）、权限模型、可扩展性（hooks / skills / MCP）、企业合规。

> [!warning] 陷阱
> 别报菜名。面试官要听的是「你在什么场景切换、为什么」。诚实说主力用什么，比列十个工具强。

### Q11 · 如何使用 Coding Agent 完成项目开发？

**一句话**：先把项目约定写进配置文件当地基，然后走「澄清 → 出计划 → 人 review 计划 → 小步执行 → 验证输出」，全程在隔离分支里干。

采分点：
- **地基**：`CLAUDE.md` / `AGENTS.md` 写清构建命令、目录结构、代码约定、禁忌。这是所有后续质量的下限。
- **改计划比改代码便宜**：让它先出 plan，人 review plan，通过了再动手。
- **TDD 优先**：先让它写测试再写实现，测试就是验收标准。
- **不信自述，只信输出**：它说"测试通过了"不算，看实际命令输出。
- **隔离**：worktree 或独立分支，别在主干上放手。
- **上下文卫生**：一个 session 一件事，脏了就重开。
- **沉淀**：重复三次以上的流程做成 Skill / slash command / hook。

### Q12 · 什么是 Context Engineering？

**一句话**：在有限的上下文窗口里决定「放什么、什么时候放、放多少、怎么排」，让模型每一步都拿到刚好够用的信息 —— prompt engineering 管一次调用，context engineering 管整个 agent 生命周期。

采分点（四个动作，背下来）：

| 动作 | 含义 | 手段 |
|---|---|---|
| **Write** | 写出去，不占窗口 | memory 文件、scratchpad、外部笔记 |
| **Select** | 按需选进来 | RAG 检索、tool search、skill 渐进加载 |
| **Compress** | 压缩已有的 | compaction（摘要）、context editing（清理旧 tool result / thinking） |
| **Isolate** | 隔离脏活 | subagent 把探索过程关在子上下文里，只回传结论 |

- **核心指标是信噪比**，不是塞了多少。
- **缓存视角**：上下文是前缀匹配缓存的，改前面会让后面全部失效 → **稳定的放前面（tools → system → messages），易变的放后面**。
- 常见坏味：整个文件糊进去、历史无限增长、工具定义过多、失败的尝试留在上下文里反复污染。

### Q13 · 如何针对开发、测试、运维等不同任务组织 Skills？

**一句话**：Skill 是「按需加载的 SOP」—— description 常驻上下文负责命中，正文按需读负责执行，所以按**任务动词**切分而不是按知识领域。

采分点：
- **description 是唯一常驻的部分**，决定命中率，必须写触发条件和触发词。这是调优的第一优先级。
- **正文写流程和检查清单，不写百科**。大块内容拆到 `references/` 子文件，正文只放指针。
- 按动词切：`review PR`、`create test plan`、`release prep` —— 而不是「Java 知识」「测试知识」。
- 分层示例：开发（脚手架 / 规范 / 提交约定）、测试（用例设计 / 测试计划 / 结果上报）、运维（发布 SOP / 回滚 / 日志排查）。
- **防冲突**：description 之间要互斥，overlap 会误触发。
- **迭代闭环**：命中率不行改 description，效果不行改正文。

### Q14 · 如何使用 Agent 做 Auto Research？

**一句话**：多路并行搜（不同角度）→ 深读 → 对抗验证 → 综合，收敛条件是「连续 K 轮没有新信息」而不是「跑够 N 轮」。

采分点：
- **分解**：拆成互相独立的子问题，并行 subagent，各自只回传结论 —— 这是 context isolation，也是能扩规模的原因。
- **来源多样性**：搜索引擎 / 官方文档 / 代码仓库 / 论文 / 内部知识库分头走，避免所有 agent 搜同一个词形成回声室。
- **对抗验证**：结论派第二个 agent 去**证伪**（不是复核），不确定默认判死。
- **溯源**：每个结论挂来源，溯不到源的标「未验证」。
- **预算**：有 token 上限，被截断的部分要显式 log 出来 —— 静默截断会被读成"已覆盖全部"。

> [!warning] 陷阱
> 说不出收敛条件就是没做过。固定轮数会漏长尾，无限循环会烧钱。

## 四、Agent 工程化评测（Q15-17）

### Q15 · 如何记录每轮实验的耗时、Token 消耗、结果和失败路线？

**一句话**：建一个 Trace → Turn → ToolCall 的三层结构化模型，append-only 落 JSONL，**关键是记全「变量组」**，否则记了也没法对比。

采分点：
- **变量组字段**（决定这条记录能不能参与对比）：prompt 版本、model id、effort、skill 版本、git commit、输入 hash。
- **性能字段**：TTFT（首 token 延迟）、总时长、input / output / cache_read / cache_creation token、换算成本。
- **行为字段**：`stop_reason`、工具调用序列、迭代轮数、重试次数。
- **结果字段**：最终产物、评分、失败原因分类。
- **失败路线要记过程不只记结果**：走到哪一步崩的、当时上下文里有什么、模型输出了什么 —— 这是改 prompt 的唯一依据。
- 标准：OpenTelemetry GenAI semantic conventions；现成工具 LangSmith / Langfuse / Braintrust。

> [!warning] 陷阱
> 只打非结构化日志。日志好写不好聚合，最后没人分析。必须是结构化、可按变量组 group by 的。

### Q16 · 自动更新 AGENTS.md 或 Skills 后，怎样验证效果确实提升？

**一句话**：当成一次带 A/B 的发布 —— 固定评测集，改前改后各跑 N 次，比分布不比单次，还要跑回归集确认没有变差。

采分点：
- **前提是先有评测集**：20-50 条真实任务，覆盖典型 + 边界 + **历史失败 case**，带期望结果。
- **N ≥ 3**，因为模型本身有随机性，单次对比毫无意义。
- **指标**：任务成功率（主）、工具调用次数、token 消耗、耗时、人工干预次数。
- **分桶看**：只看总平均会掩盖「某一类任务大幅退化」。
- **必须有回归集**：只用新加的 case 验证 = 过拟合。
- 自动化成 CI，skill 改动触发。

> [!warning] 陷阱
> 评测集内容泄漏进 skill 正文 —— 那就是拿答案考试。

### Q17 · 如何通过评价脚本或者模型评审对比两个 Skill 的输出？

**一句话**：能写断言的一律写断言（快、免费、可复现），只有主观质量才上 LLM-as-judge，而且必须 pairwise + 位置随机化。

采分点：
- **脚本评审优先**：文件是否生成、测试是否通过、build 是否绿、schema 校验、关键字段正则。确定性的东西不该交给模型判。
- **LLM-as-judge 的四个必做**：
  1. **pairwise 而不是绝对打分** —— 绝对分数会漂移，相对比较稳得多。
  2. **位置随机化** —— A/B 交换位置各跑一次，消除 position bias（judge 系统性偏爱靠前的那个）。
  3. **匿名化** —— 不告诉 judge 哪个是新版。
  4. **先给理由再给结论** —— 顺序反了模型会先拍脑袋再编理由。
- rubric 拆成可判定的维度（正确性 / 完整性 / 可执行性 / 简洁性），每维给判定标准。
- judge 用同级或更强的模型。
- **抽样人工校准 judge**：算 judge 和人类的一致率，低于阈值这个 judge 就不能信。

## 五、网络与鉴权（Q18-22）

### Q18 · WebSocket 和 SSE 有什么区别？

**一句话**：WebSocket 是独立协议的全双工长连接，SSE 就是一个不结束的 HTTP 响应、只能服务端往客户端单向推。

采分点：

| 维度 | WebSocket | SSE |
|---|---|---|
| 协议 | `ws://` / `wss://`，HTTP Upgrade 握手后脱离 HTTP | 就是 HTTP，`Content-Type: text/event-stream` |
| 方向 | 全双工 | 单向（server → client） |
| 数据 | 文本 + 二进制 | 只有 UTF-8 文本 |
| 断线重连 | 自己实现 | 浏览器 `EventSource` 自动重连，带 `Last-Event-ID` |
| 代理穿透 | 有时被中间设备拦 | 普通 HTTP，穿透好 |
| HTTP/2 | 不走 | 走多路复用，不受浏览器同域连接数限制 |
| 调试 | 要专门工具 | `curl` 直接看 |

**结论**：LLM 流式输出用 SSE 就够 —— 输入走普通 POST，输出走 SSE。只有真需要双向实时（协同编辑、游戏、语音）才上 WebSocket。

### Q19 · Cookie 和 JWT 有什么区别？

**一句话**：这俩不是一个维度的东西 —— **Cookie 是传输/存储机制，JWT 是令牌格式**，JWT 完全可以装在 Cookie 里传。真正在对比的是「服务端有状态 Session vs 自包含无状态 JWT」。

采分点：

| 维度 | Session ID + Cookie | JWT |
|---|---|---|
| 状态 | 服务端存会话（内存 / Redis） | 服务端不存，信息在 token 里 |
| 水平扩展 | 要共享存储或粘性会话 | 天然无状态 |
| 撤销 | 删记录即时生效 | **难** —— 签出去就有效到过期 |
| 体积 | 只有一个 ID，很小 | 每次请求带完整 payload |
| 跨域 | 受同源 / SameSite 限制 | `Authorization` header 天然跨域友好 |
| 主要风险 | CSRF（Cookie 自动携带） | XSS（存 localStorage 时会被偷） |

- Cookie 三个安全属性要能背：`HttpOnly`（JS 读不到）、`Secure`（只走 HTTPS）、`SameSite`（防 CSRF）。
- **最佳实践**：JWT 放进 `HttpOnly + Secure + SameSite` 的 Cookie，两边优点都要。

> [!warning] 陷阱
> 上来就列表格对比"Cookie vs JWT"是掉坑里了。**先纠正问题本身**，这是最大的区分度。

### Q20 · JWT 的结构是什么？

**一句话**：三段用 `.` 连接，每段 Base64URL 编码 —— `header.payload.signature`。

采分点：
- **Header**：`{"alg":"HS256","typ":"JWT"}`，可能带 `kid`（密钥 ID，用于轮换）。
- **Payload**：claims。注册声明 `iss` `sub` `aud` `exp` `nbf` `iat` `jti`，再加业务自定义字段。
- **Signature**：`HMACSHA256(base64url(header) + "." + base64url(payload), secret)`。

> [!danger] 最重要的一句
> **Base64URL 是编码不是加密 —— payload 任何人都能解开看。** JWT 保证的是「没被篡改」，不是「看不见」。别往里塞密码、身份证、手机号。真要保密用 JWE。

### Q21 · 为什么 JWT 通常不需要像随机 Session ID 一样在服务端保存会话状态？

**一句话**：因为信息的位置不同 —— 随机 Session ID 本身没有含义，只是个指针，必须查表才知道对应谁；JWT 把身份和权限直接写在 token 里，服务端读一下就行，防伪靠签名而不是靠查库。

采分点：
- **Session ID 像存包柜号牌**：号牌上没内容，必须去柜台查。所以服务端必须存这张表。
- **JWT 像带防伪钢印的身份证**：信息印在证上，验一下钢印真假就够了。**验签只要密钥，不碰数据库。**
- 这就是"无状态"的全部含义：不是没状态，是**状态被搬到了客户端手上，用签名保证它没被改**。
- **代价是撤销困难**：改权限、登出、封号，已签发的 token 在过期前依然有效。
- **实践对策**：access token 设短（15 分钟内）+ refresh token 换发；高危场景维护黑名单（`jti`），但这时候其实又变回有状态了 —— 这个 trade-off 要主动说出来。

### Q22 · 服务端如何验证 JWT 的真实性和完整性？

**一句话**：切三段 → **校验 alg 白名单** → 找密钥重算签名做常量时间比对 → 签名过了再读 claims 校验时间和受众。顺序不能反。

采分点（按流程背）：
1. 按 `.` 切三段，Base64URL 解开 header。
2. **校验 `alg` 是否在自己的白名单里** —— 绝不能直接信 header 里写的算法。
3. 按 `kid` 找到对应密钥（非对称场景从 JWKS 端点拉，本地缓存）。
4. 用密钥对 `header.payload` 重算签名，和第三段比 —— **常量时间比较**，防时序攻击。
5. 签名通过后再校验 claims：`exp` 未过期、`nbf` 已生效、`iss` 签发者正确、`aud` 受众是我；留 60s 左右的 clock skew 容忍。
6. 业务层：`jti` 是否在黑名单、用户是否还存在或已被禁用。

> [!danger] 两个经典漏洞，必须能说出来
> - **`alg: none`**：攻击者把算法改成 none 并删掉签名段，实现不严的库会直接放行。
> - **RS256 降级成 HS256**：服务端用 RS256（公钥验签），攻击者把 alg 改成 HS256 并用**公钥当作 HMAC 密钥**签名。公钥是公开的，于是任何人都能伪造 token。
>
> 两个漏洞的根因是同一个：**信任了未经验证的 header**。

- 算法选型：`HS256` 对称，签验同一密钥，适合单体和内部服务；`RS256` / `ES256` 非对称，私钥签公钥验，适合多方验证和对外开放 —— 验证方拿到公钥也伪造不了。

## 六、算法基础（Q23-24）

### Q23 · 爬楼梯：N 级台阶，每次走 1 或 2 级，递归实现并解释递推关系和边界条件

**一句话**：`f(n) = f(n-1) + f(n-2)`，边界 `f(0)=1, f(1)=1` —— 就是 Fibonacci 移了一位。

**递推关系怎么推出来的**（这是考点，不是背结论）：
> 要站上第 n 级，**最后一步**只有两种可能 —— 从 n-1 迈 1 级，或从 n-2 迈 2 级。
> 这两类走法**既不重叠也不遗漏**（最后一步的步长不同，所以不可能是同一条路径），所以总数直接相加。

**边界为什么是 `f(0)=1`**：n=0 时"原地不动"本身算一种走法。这样定义能让 `f(2)=f(1)+f(0)=2` 和实际情况（1+1、2）对上。也可以定义 `f(1)=1, f(2)=2` 从 3 开始递推，等价。

```java
// 朴素递归 O(2^n) —— 面试要主动指出这里有大量重复子问题
static long climb(int n) {
    if (n <= 1) return 1;
    return climb(n - 1) + climb(n - 2);
}

// 记忆化 O(n)
static long climbMemo(int n, long[] memo) {
    if (n <= 1) return 1;
    if (memo[n] != 0) return memo[n];
    return memo[n] = climbMemo(n - 1, memo) + climbMemo(n - 2, memo);
}
```

追问速答：
- **朴素递归复杂度**？O(2^n)，因为 `f(n-2)` 被算了很多遍。画一层递归树就能看出来。
- **怎么优化**？记忆化 → 自底向上迭代 → 滚动变量把空间降到 O(1) → 矩阵快速幂 O(log n)。
- **会溢出吗**？`int` 在 n≈47 就爆，`long` 撑到 n=92，再大要 `BigInteger` 或题目要求取模。
- **递归深度**？n 大了栈溢出，生产代码用迭代。
- **变成 1/2/3 级**？`f(n)=f(n-1)+f(n-2)+f(n-3)`，边界补到三个。

### Q24 · 如何基于数组实现一个 Map？

**一句话**：三件事 —— 哈希函数把 key 映射到数组下标、冲突了怎么办、什么时候扩容。

采分点：
1. **定位**：`index = hash & (capacity - 1)`。容量取 2 的幂，用**位与代替取模**（快很多）。HashMap 还做一次扰动 `h ^= (h >>> 16)`，让高位参与运算 —— 因为容量小时只有低几位有效，不扰动的话高位信息全丢了。
2. **冲突处理**：
   - **拉链法**：每桶挂链表。Java 8 起链表长度 ≥8 **且**容量 ≥64 时转红黑树，最坏从 O(n) 降到 O(log n)。
   - **开放寻址**：线性/二次探测、双散列。**删除必须用墓碑标记**，直接删会把探测链断掉，后面的元素就找不到了。
3. **扩容**：负载因子（Java 默认 0.75），`size > capacity × 0.75` 就翻倍 rehash。0.75 是空间占用和冲突率之间的经验平衡点。
4. **`equals` / `hashCode` 契约**：`equals` 相等则 `hashCode` 必须相等（否则存进去找不到）；`hashCode` 相等不代表 `equals` 相等（所以查找要先比 hash 再比 equals）。**key 必须不可变**，否则 hash 变了就成了孤儿数据。

追问速答：
- **为什么容量必须是 2 的幂**？① 位与能代替取模；② 扩容时元素只可能留在原位或移到 `原位 + oldCap`，判断一个 bit 就行，不用重算 hash。
- **Java 8 为什么从头插改尾插**？头插在并发 resize 时可能把链表接成环，之后 `get` 会死循环打满 CPU。（不过 HashMap 本来就不保证线程安全，正解是 `ConcurrentHashMap`。）
- **怎么做线程安全**？`ConcurrentHashMap`：空桶用 CAS 写入，非空桶 `synchronized` 锁桶头，锁粒度到单个桶。
