# Q15 · 如何记录每轮实验的耗时、Token 消耗、结果和失败路线？

## 先定数据模型

不定模型直接打日志，最后一定是一堆没法聚合的文本。三层结构：

```
Trace（一次完整运行）
  ├─ 变量组、总耗时、总成本、最终结果、评分
  │
  ├─ Turn（一次 LLM 往返）
  │    ├─ TTFT、耗时、各类 token、stop_reason
  │    │
  │    └─ ToolCall（一次工具调用）
  │         └─ 工具名、参数、耗时、成功/失败、错误信息
  ├─ Turn ...
  └─ Turn ...
```

## 每层记什么

### Trace 层

**变量组**（决定这条记录能不能参与对比 —— 少一个字段，这条数据就废了）：

| 字段 | 为什么必须有 |
|---|---|
| `prompt_version` | 改了 prompt 要能区分 |
| `model_id` | **pin 到具体版本，不能是别名** |
| `effort` / 采样参数 | 影响质量和成本 |
| `skill_version` / `agents_md_hash` | Q16 要靠它做 A/B |
| `git_commit` | 代码也是变量 |
| `input_hash` | 确认两组跑的是同一题 |
| `run_group` | 同一批实验的标识 |

**结果字段**：最终产物、是否成功、评分、失败原因分类（枚举，不是自由文本）。

### Turn 层

| 类别 | 字段 |
|---|---|
| 延迟 | **TTFT**（首 token，决定体感）、总耗时 |
| Token | `input` / `output` / `cache_read` / `cache_creation` **要分开记** |
| 成本 | 按各类 token 的单价分别算 |
| 行为 | `stop_reason`、是否重试 |

> [!tip] 为什么 token 必须分四类记
> 缓存命中和不命中的**单价差一个数量级**。只记一个总数，你既算不准成本，也发现不了缓存失效。
> **`cache_read` 长期为 0 是最重要的告警信号** —— 说明有东西在偷偷破坏前缀（见 [[03-Coding-Agent-实践]] Q12）。

### ToolCall 层

工具名、规范化后的参数、耗时、成功失败、错误信息。

**顺序要保留** —— 工具调用序列本身就是重要信息。同样一个任务，A 版本调了 3 次工具，B 版本调了 15 次，即使都成功了，B 也更差。

## 失败路线：记过程，不只记结果

这是本题的题眼。**"失败了"这三个字没有任何调试价值。**

要记的是：

| 记什么 | 用来干什么 |
|---|---|
| 走到第几轮崩的 | 判断是早期理解错了还是后期执行错了 |
| 崩的时候上下文里有什么 | 判断是信息不够还是信息太杂 |
| 模型当时输出了什么原文 | 唯一能看出它在想什么的东西 |
| 工具报了什么错 | 判断是工具问题还是模型用错了工具 |
| 失败类型（枚举） | 能聚合统计：哪类失败最多就先修哪个 |

失败类型建议的枚举：`理解偏差` / `工具选错` / `参数错误` / `工具本身失败` / `上下文溢出` / `循环未收敛` / `输出格式错` / `事实幻觉`。

**能按类型聚合，才知道该优先修什么。** 这是从"救火"到"治理"的分界线。

## 落地方式

| 做法 | 评价 |
|---|---|
| 只打 `logger.info()` 文本日志 | ❌ 好写，不好聚合，最后没人分析 |
| **结构化 JSONL append-only + 可查询表** | ✅ 简单可靠，本地就能跑分析 |
| OpenTelemetry GenAI semantic conventions | ✅ 有行业标准的 span 属性命名，能接现成后端 |
| LangSmith / Langfuse / Braintrust | ✅ 开箱即用，适合不想自建的 |

自建的最小可用方案就是一个 JSONL 文件 + 一段 pandas 分析脚本，**先跑起来比选型重要**。

## 验收标准

给自己定一个硬标准：

> **能不能用一条查询回答「prompt v3 相比 v2，在同一批 50 个任务上，成功率、平均 token、p95 耗时各变化了多少」？**

答不上来，说明记的东西还不够用。

# Q16 · 自动更新 AGENTS.md 或 Skills 后，怎样验证效果确实提升？

## 心态先摆正

**把它当成一次带 A/B 的发布，而不是一次「改完感觉好像顺了」。**

prompt 和 skill 的改动有个很坑的特点：**它没有编译错误，也没有测试失败**。改坏了不会报错，只会让成功率从 85% 悄悄掉到 70%，几周后才被发现。所以必须有主动的验证机制。

## 前提：先得有评测集

没有评测集，后面全是空谈。评测集的要求：

| 要求 | 说明 |
|---|---|
| **20-50 条起** | 少于 20 条，随机性会淹没真实差异 |
| **真实任务** | 从线上真实请求里捞，不要自己编 |
| **三类都要有** | 典型 case + 边界 case + **历史失败 case** |
| **带期望结果** | 可以是标准答案，也可以是判定规则 |
| **分桶标注** | 按任务类型打标，后面要分桶看 |

**历史失败 case 尤其重要** —— 它们是过去踩过的坑，改动不能让它们复发。

## 验证流程

```
              固定评测集（N 条）
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   改前版本 A                 改后版本 B
   跑 M 次（M≥3）            跑 M 次（M≥3）
        │                       │
        └───────────┬───────────┘
                    ▼
            按变量组聚合对比
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    总体指标    分桶指标     回归集是否变差
```

### 为什么 M ≥ 3

**模型有随机性，单次对比毫无意义。** 同一个 prompt 跑三次可能一次成功两次失败。只跑一次得出的"提升了"，很可能只是运气。

至少跑 3 次看分布；样本少的时候，**组间差异要明显大于组内波动**才敢说有提升。

### 指标清单

| 指标 | 权重 | 说明 |
|---|---|---|
| **任务成功率** | 主指标 | 这是最终目的 |
| 工具调用次数 | 辅助 | 少即是好 —— 同样成功，绕路少的更优 |
| Token 消耗 | 辅助 | 直接对应成本 |
| 端到端耗时 | 辅助 | 体验 |
| **人工干预次数** | 辅助 | 真正的"能不能放手用"的指标 |

### 必须分桶看

只看总平均会掩盖**"某一类任务大幅退化"**。

真实例子：总成功率从 80% 涨到 83%，看起来是提升。分桶一看 —— 简单任务从 90% 涨到 98%，复杂任务从 60% 掉到 55%。这个改动实际上是有害的，因为复杂任务才是价值所在。

### 必须有回归集

**只用新加的 case 验证 = 过拟合。**

典型翻车路径：发现某类任务不行 → 往 skill 里加了针对性规则 → 用那类任务验证 → 成功率 100% → 上线 → 别的任务全崩了。

所以评测集要分两部分：
- **目标集**：这次改动想解决的问题
- **回归集**：以前就 OK 的任务，用来确认没变差

**回归集不能退化**是硬门槛，比目标集提升多少更重要。

## 三个陷阱

> [!danger] 1. 评测集泄漏
> 评测用例的内容被写进了 skill 正文、prompt 或者 few-shot 示例里 —— 那就是拿着答案考试。
> 要留一份**从未进入过任何上下文**的 holdout 集。

> [!danger] 2. 只测改动想解决的那一类
> 见上面的回归集说明。

> [!danger] 3. 拿"改完感觉更顺了"当结论
> 人对自己刚改的东西有强烈的正向偏见。必须有客观数据。

## 自动化

最终形态是进 CI：

```
skill / AGENTS.md 变更
        ↓
  触发评测流水线
        ↓
  跑目标集 + 回归集
        ↓
  ┌─────────────────────┐
  │ 回归集退化 > 阈值 → 拦截 │
  │ 目标集无提升 → 警告     │
  │ 都 OK → 放行           │
  └─────────────────────┘
```

跑一次全量评测的成本不低，可以分层：小改动跑快速子集，大改动跑全量。

# Q17 · 如何通过评价脚本或者模型评审对比两个 Skill 的输出？

## 总原则

> **能写断言的一律写断言，只有主观质量才交给模型判。**

理由很直接：脚本快、免费、100% 可复现；LLM judge 慢、花钱、还带随机性。把确定性的事交给模型判是浪费。

## 第一层：规则 / 脚本评审

优先做这一层。能覆盖的比想象中多：

| 检查项 | 怎么判 |
|---|---|
| 产物是否生成 | 文件存在性 |
| 代码是否能跑 | build 退出码 |
| 功能是否正确 | 跑测试套件 |
| 输出格式是否合法 | JSON schema 校验 |
| 是否包含必要字段 | 正则 / 结构解析 |
| 是否触碰了禁改文件 | `git diff --name-only` 比对 |
| 是否引入了禁用依赖 | 依赖树扫描 |

**这一层能判掉的，绝不上 LLM judge。**

## 第二层：LLM-as-judge

只用于确实主观的维度：可读性、完整性、是否切题、解释是否清楚。

### 四个必做（少一个结论就不可信）

#### 1. Pairwise，不要绝对打分

```
❌ "给这个输出打 1-10 分"
✅ "A 和 B 哪个更好？或者打平？"
```

绝对分数**漂移严重** —— 同一个输出今天打 7 分明天打 8 分，跨批次完全没法比。相对比较稳定得多，因为 judge 只需要判断相对优劣。

#### 2. 位置随机化（消除 position bias）

LLM judge 有**系统性地偏好靠前（或靠后）选项**的倾向，这个 bias 能达到十几个百分点。

做法：**同一对输出跑两次，第二次把 A 和 B 的位置互换。**

| 两次结果 | 判定 |
|---|---|
| 都说 A 好 | A 胜（稳） |
| 都说 B 好 | B 胜（稳） |
| 两次矛盾 | **判平局** —— 说明 judge 只是在偏好位置，不是在比质量 |

第三行是关键 —— 矛盾的时候不要取其中一个，那是在放大 bias。

#### 3. 匿名化

不能告诉 judge "A 是旧版 B 是新版"。要脱掉任何能识别身份的痕迹（包括输出里的版本号、时间戳、文件路径特征）。

#### 4. 先给理由，再给结论

```
❌ 输出格式：{ "winner": "A", "reason": "..." }
✅ 输出格式：{ "analysis": "...", "winner": "A" }
```

字段顺序在自回归模型里**是有意义的**：先出结论，后面的理由就是在给已经拍好的脑袋找说辞；先分析再结论，分析过程真的会影响结论。

### rubric 怎么写

**拆成可独立判定的维度**，每个维度给明确标准，最好带正反例：

```
维度 1 · 正确性
  判定：输出中的事实陈述、代码逻辑、命令是否正确
  好：所有命令可直接执行，参数正确
  坏：出现不存在的 API、命令有语法错误

维度 2 · 完整性
  判定：是否覆盖了任务要求的所有点
  好：需求里的每一条都有对应处理
  坏：遗漏了错误处理、遗漏了边界情况

维度 3 · 可执行性
  ...
维度 4 · 简洁性
  ...
```

**分维度打，再汇总** —— 比让 judge 直接给一个总体判断可靠得多，也能看出"A 在正确性上赢但在简洁性上输"这种有价值的细节。

### judge 模型选型

用**同级或更强**的模型当 judge。用弱模型评强模型的输出，它看不懂好在哪。

### 校准：judge 本身也要被评测

这一步最容易被跳过，但它决定了整套评测可不可信。

做法：**抽 20-30 对样本让人工判一遍**，算 judge 和人工的一致率。

| 一致率 | 结论 |
|---|---|
| > 80% | 可以信 |
| 60-80% | 勉强用，结论要谨慎 |
| < 60% | **judge 不可用**，回去改 rubric |

一致率低时，看不一致的样本 —— 通常是 rubric 里某个维度定义模糊，judge 和人的理解不一样。

## 输出格式

最终报告应该有：

| 内容 | 作用 |
|---|---|
| 胜 / 平 / 负计数 | 总体结论 |
| 各维度得分对比 | 看在哪个方面赢/输 |
| **差异最大的样本清单** | 最有价值的部分 —— 直接告诉你去看哪几个 case |
| judge 一致率 | 这份报告本身的可信度 |
| 覆盖说明 | 跑了多少、跳过了多少、为什么 |

**"差异最大的样本清单"是整份报告里最有用的东西** —— 分数告诉你结果，样本告诉你原因。

## 三题串起来的完整闭环

```
Q15 记录  →  有数据了
   ↓
Q16 验证  →  知道改动是好是坏了
   ↓
Q17 对比  →  能在多个方案里选最优了
   ↓
   进 CI  →  变成不会退化的工程能力
```

面试时如果被连着问这三题，**主动把这条线画出来**，比分别答三遍强得多。
