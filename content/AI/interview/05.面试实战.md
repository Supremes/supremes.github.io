# Agent 面试实战：系统设计、行为面试与 Coding Agent

这一组是临场用的：系统设计答题顺序、行为面试的项目材料，以及最常被当成系统设计题来考的 Coding Agent。

本文包含：

- Agent 系统设计与行为面试
- Coding Agent 工程

## Agent 系统设计与行为面试

系统设计题考察边界和取舍。行为题考察你是否真的做过。两类题都不接受只报框架名或产品名。

### 系统设计答题顺序

1. 明确用户、任务、成功标准和失败成本。
2. 画输入、Context、模型、工具、状态和输出。
3. 找出副作用、权限和不可控外部依赖。
4. 设计超时、取消、重试、幂等和恢复。
5. 定义 Trace、指标、评测集和发布门槛。
6. 讨论规模、成本、延迟和降级。

### 高频系统设计题

- 设计一个客服 Agent。
- 设计一个 Coding Agent。
- 设计 Deep Research Agent。
- 设计 1000 个工具的发现与调用系统。
- 设计带长期记忆的个人助手。
- 设计多 Agent 代码审查系统。
- 设计 Agent 评测平台。
- 设计远端 Sandbox 执行系统。

### 行为面试准备

至少准备四类项目：

| 案例 | 面试官关注 |
|---|---|
| 修复线上失败 | 定位证据、根因、恢复和防复发 |
| 架构取舍 | 为什么没选另一方案 |
| 指标冲突 | 质量、成本、延迟如何平衡 |
| 推动落地 | 如何让团队接受规范或平台 |

STAR 中的 Action 要写你做了什么，不要只说“团队完成了”。Result 使用真实数字。没有数字时，写可验证的交付物和影响范围。

### 常见追问

1. 这个设计最脆弱的地方是什么？
2. 流量扩大 10 倍后先坏哪里？
3. 模型换代后哪些组件可以删除？
4. 评测分数和业务反馈冲突怎么办？
5. 你做错过什么判断，后来怎么发现？
6. 如果重新做一次，会先改什么？

### 要点reference

- *这个设计最脆弱的地方*：dawn-ai 的答案是**执行面**——BashTool 跑在宿主机，cwd 和 denylist 不是安全边界；其次是 ReAct loop 是框架黑盒，做不了 HITL 的 suspend / resume。
- *流量扩 10 倍先坏哪里*：`chatStreamExecutor` 32 线程上限，每个 SSE 占一个线程最长 20 分钟，第 97 个并发直接 503；然后是 pgvector `index-type: NONE` 全表扫；然后是每请求 5~6 次 LLM 调用撞 RPM。
- *模型换代后哪些组件可以删*：query rewrite、HyDE、category classify 这些「帮模型理解」的前置调用最先删；re-plan 和 max-steps 这类预算控制不删；Memory 分层不删。判断标准：这个组件补的是模型能力还是系统约束。
- *评测分数和业务反馈冲突*：先查指标代理错了没、线上分布和 eval set 分布差多少、grader 有没有偏、版本对不对齐；冲突样本建新桶，不争谁更真。
- *做错过什么判断*：dawn-ai 有现成的——BashTool 写权限第一版做的是「对话授权」，模型说要写就放行，后来意识到决定权在可被注入的 LLM 手里，推翻改成 `allow-write` 确定性开关默认关。另一个：Plan 和 ReAct 两个 prompt 没对齐导致行为漂移，修法是结构化契约 + 动态 re-plan。
- *重做一次先改什么*：把 ReAct loop 从 Spring AI 收回自己写。它是 HITL、checkpoint / resume、长任务、多模态切换的共同地基，现在所有这些都被框架黑盒卡住。
- *30 分钟讲稿骨架（dawn-ai）*：
	1. 一句话定位：Spring AI 上的工具增强型 ReAct Agent，Plan + ReAct + 三类 Memory + Hybrid RAG + Sub-Agent + SSE，全链路 Prometheus / Langfuse。
	2. 画一次请求：`StepCollector.init` → Planner → system prompt 八段拼装 → 框架 tool loop → AOP 记 step → Redis → SSE `connected → plan → thinking → step → token → done`。
	3. 三个取舍讲透：Memory 三类记忆各去哪（EPISODIC 不进 prompt）；sub-agent 零继承 + 禁递归 + 软失败；BashTool 从对话授权翻盘到确定性开关。
	4. 两个数字：`replan-threshold: 2`、四个 token 预算段。
	5. 主动说短板：无 sandbox、无 MCP、无多模态、token 指标只记最后一次、Fact 写入无验证。
	6. 演进主线：Tool Gateway → Capability Router → Structured Edit → Workspace Manager → Sandbox Executor。

### 项目材料清单

- 一张架构图。
- 一条成功 Trace 和一条失败 Trace。
- 一份版本对比数据。
- 一次故障或错误决策复盘。

## Coding Agent 工程

Coding Agent 要完成理解仓库、制定修改、编辑文件、运行验证和交付变更。它的难点不只是生成代码，而是维护工程上下文和反馈循环。

### 复习范围

| 阶段 | 内容 |
|---|---|
| Discover | 仓库规则、依赖、入口、相关代码 |
| Plan | 目标、影响面、验收条件、任务依赖 |
| Edit | 精确修改、patch、结构化工具、冲突处理 |
| Verify | test、lint、build、类型检查、截图 |
| Deliver | diff、commit、PR、风险和回滚 |
| Isolation | worktree、容器、远端工作区 |

### 高频问题

1. Coding Agent 如何快速理解陌生仓库？
2. 为什么要先读再改，读多少才够？
3. `old_string` 精确替换为什么容易失败？
4. 多个 Agent 如何避免同时修改同一文件？
5. 如何让 Agent 验证 UI 改动？
6. AGENTS.md、Skill、MCP 各自放什么？

### 要点reference

- *怎么快速理解陌生仓库*：先读规则文件（AGENTS.md / CLAUDE.md / README）→ 入口和构建文件 → 按需 grep 到相关代码，不要全量读。读多少够：能说出改动会影响哪些调用方为止。
- *为什么先读再改*：编辑工具要精确上下文，不读就改 `old_string` 对不上；更重要的是不读就不知道项目约定，改出来的代码风格和隐含约束全错。
- *`old_string` 精确替换为什么容易失败*：0 次匹配——上下文过期或空白字符不一致；多次匹配——歧义。正确协议：默认 `expectedMatches=1`，0 次或多次都失败；带 `expectedSha256` 做 CAS 防并发修改；temp file + fsync + atomic rename；返回 unified diff。不用 regex，不默默替换全部。
- *多 Agent 避免改同一文件*：worktree 隔离，每个任务一个 snapshot，结束时合并 patch；共享 workspace 要单写者 lease + 逐文件 hash。
- *怎么验证 UI 改动*：截图工具 + 视觉断言，或 DOM 状态检查；没有验证命令的「完成」不算完成。
- *AGENTS.md、Skill、MCP 各放什么*：AGENTS.md 放这个仓库的硬约束和惯例（常驻）；Skill 放跨仓库的流程 SOP（按需加载）；MCP 放外部能力（工具）。
- *dawn-ai 实践*：**不是 Coding Agent，但有它的雏形和反面教材**。有 `BashTool`（`cat / grep / find / git` 放行，写操作默认拒，30s 超时，50KB 输出，连续 3 次失败熔断），没有 `EditFileTool` / `ApplyPatchTool`——开 `allow-write` 后靠 shell 改文件，shell quoting 脆、表达不了「只匹配一次」、没有版本校验、失败没有结构化 diff。没有 worktree / snapshot / ChangeSet，`baseDir` 只是初始 cwd。演进顺序：`BashTool` 后面抽 `CommandExecutor` → 加结构化 Read / Edit / ApplyPatch → `WorkspaceManager` 先做本地 git worktree → container executor 接同一接口。

### 工具设计

至少要有搜索、读取、编辑、执行、诊断和版本控制能力。读取工具返回行号与范围，编辑工具要求精确上下文，执行工具保留退出码和结构化错误。

### 失败模式

- 没读项目规则就开始修改。
- 只修表面症状，没有追调用链。
- 测试失败后反复试错，不更新假设。
- 修改范围过大，夹带无关重构。
- 声称完成，但没有运行验收命令。
- 子 Agent 重复搜索，反而增加成本。

### 项目证据

选一个真实修复，展示初始假设、搜索路径、最小 diff、验证命令和最终结果。最好保留一次错误假设及其修正过程。
