# Agent 生产化：评测、可观测性、可靠性、安全与性能

这一组回答「Agent 怎么上线」：评测证明它有效，可观测性留下证据，可靠性处理出错之后的事，沙箱限制工具的执行环境，安全管理授权，性能与成本决定它值不值。重试与 Trace 的耦合放在「可靠性与生产化」一节。

本文包含：

- Agent 评测与可观测性
- Agent 可靠性与生产化
- [Agent 沙箱与执行环境](#agent-sandbox)
- Agent 安全与权限
- Agent 性能与成本

## Agent 评测与可观测性

评测判断系统是否达到目标。可观测性保留运行证据，帮助解释分数和定位首错。Trace 本身不是评测，Judge 也不是真值。

### 复习范围

| 主题 | 内容 |
|---|---|
| 评测视角 | Outcome、Trajectory、Turn / Step |
| 指标 | 成功率、`pass@k`、`pass^k`、成本、延迟、安全 |
| Dataset | 典型、边界、历史失败、holdout |
| Grader | 状态验证、规则、LLM Judge、人工 |
| Trace | run、turn、span、tool call、版本和错误 |
| 实验 | A/B、配对分析、置信区间、CI 门禁 |

### 高频问题

1. 为什么只看最终答案不够？
2. `pass@k` 和 `pass^k` 分别测什么？
3. LLM-as-a-Judge 有哪些偏差，怎么校准？
4. 如何从生产 Trace 生成回归用例？
5. Langfuse 属于 Trajectory Layer 吗？
6. 如何证明一次 Prompt 或 Skill 修改真的提升了？

### 要点reference（速记版，详见下文「Agent 评测」深挖）

- *为什么只看最终答案不够*：Outcome 放过越权、绕路、偶然成功和 reward hacking；Trajectory 才能定位首错。两个一起看：Outcome 判成败，Trajectory 做诊断，步数冗余当软分不一票否决。→ 深挖「三种检查粒度」。
- *pass@k vs pass^k*：`pass@k = 1-(1-p)^k` 是能力上限，多试几次有机会；`pass^k = p^k` 是重复稳定性，生产看这个。p=0.9 时 pass@8 ≈ 100%、pass^8 = 43%。`p^k` 依赖 IID，共享故障会让失败相关。→ 深挖「指标」。
- *Judge 偏差怎么校准*：position / verbosity / self-preference / style 四种。缓解：交换顺序复评、Rubric 惩罚冗长、异构 Judge、要求逐维引用证据、人工金标算 kappa。Judge 只管开放式质量，能程序判的先程序判。→ 深挖「LLM-as-a-Judge」。
- *从生产 Trace 生成回归用例*：两种——E2E 从初始状态重跑；trajectory-prefix 冻结到失败前一步只评下几步动作，答案给可接受动作集不给唯一路径。→ 深挖「数据集」。
- *Langfuse 属于哪层*：观测与评测平台层，管 Trace UI / Score / Dataset / Experiment，不管 Agent Runtime 的调度、checkpoint、幂等。→ 深挖「Trajectory 和可观测性」。
- *怎么证明一次修改真的提升*：固定 case 集配对对比、报样本量和置信区间、核心桶零回归、veto = 0、p95 和 cost_per_success 不过线。单次 A/B 不算数。→ 深挖「设计一套 Agent Eval Pipeline」。
- *dawn-ai 实践*：Trace 走 OTLP → Langfuse（`sampling 1.0`），sub-agent 的 LLM span 通过 `AiInteractionContext.wrap` 把 sessionId 显式传到 worker 线程，归到同一 Session。Metrics 三段式 `ai.<component>.<metric>`：`ai.tool.duration / calls{tool,status}`、`ai.planner.result{status}`、`ai.rag.retrieval{result=hit|miss}`、`ai.subagent.dispatches{type,status}`、`ai.error.total{type}`。三条告警：tool 错误率 >10%、RAG 命中率 <50%、planner fallback >20%。**已知短板**：`ai.token.input / output` 只记最后一次 LLM 调用的 usage，ReAct 多轮的中间调用没算，成本被低估；`RetrievalEvaluator` 只有检索评测，没有端到端 answer 评测和 CI 门禁。

### 判分顺序

```text
最终状态 / 可执行测试
→ 确定性规则与 Policy
→ LLM-as-a-Judge
→ 高风险、分歧和低置信样本交给人
```

### 常见错误与风险

- 评测集泄漏进 Prompt 或训练数据。
- 只跑一次，随机波动被当成提升。
- 总平均掩盖核心任务桶退化。
- Judge 偏爱长答案、固定位置或同源模型。
- Grader 自己有缺陷，却把错误归给 Agent。
- 失败 run 没有落库，产生幸存者偏差。

### 项目证据

准备一次真实 A/B。至少展示样本量、任务分桶、版本、成功率、成本、p95 延迟、置信区间和代表性失败轨迹。



## Agent 评测

> [!abstract] 先记住这件事
> Agent 评测检查的是模型、Harness、工具、策略和环境共同产生的行为。
>
> - Outcome 检查任务是否完成，环境状态是否正确。
> - Trajectory 检查工具、参数、顺序、策略和恢复路径。
> - Turn / Step 检查单步质量、成本、延迟和风险。
> - System 检查数据集、环境和评分器能否支撑结论。
>
> 能写成程序的判断先交给程序。开放问题再用 LLM-as-a-Judge。高风险和判断不清的样本留给人。`pass@k` 只能说明多试几次有机会成功，不能证明生产可靠。

![Agent 评测体系总览](../../svg/agent-eval-system.svg)

时间不够时，先看指标、系统设计和最后的检查清单。准备项目经历时，挑一个真实问题，讲清楚你如何建集、定位、修复和回归。

### 评测对象

#### 被测的是整个 Agent 系统

Agent 的输出由多个变量共同决定：

```text
Agent Behavior
= Model
+ System Prompt / Skill
+ Context / Memory / Retrieval
+ Tool Schema / Tool Runtime
+ Orchestration / Retry / Termination
+ Permission / Policy
+ Environment State
```

公开模型榜单回答不了 "这个 Agent 能不能在我的业务里上线"。模型提供能力，Harness 决定系统如何使用这些能力。评测要把两者放在一起。

区分模型瓶颈与 Harness 瓶颈，可以做两类实验：

- Model swap 固定 Harness，只换模型。分数随模型明显变化时，瓶颈更可能在模型。
- Ablation 固定模型，关闭或替换一个 Harness 组件。它适合检查工具、记忆、提示词和策略是否真的有用。

#### 三种检查粒度

| 视角 | 问题 | 常用方法 | 盲区 |
|---|---|---|---|
| Outcome / Final state | 最终真的完成了吗？ | 单元测试、数据库状态、文件/DOM/API 验证 | 不能解释为什么成功或失败 |
| Trajectory | 过程是否正确、经济、安全？ | 工具/参数/顺序检查、路径效率、首错归因 | 不应强制唯一参考路径 |
| Turn / Step | 这一步是否异常？ | 实时规则、轻量分类器、span 指标 | 局部合理不代表全局成功 |

Per-turn 更像在线监控和过程评分的粒度。它不是一套公认的学术分层，面试时别说得太满。

#### Outcome 和 Trajectory 要一起看

- 只看 Outcome：可能放过越权、绕路、偶然成功和 reward hacking。
- 只看 Trajectory：可能误杀合法替代路径；Agent 不必复刻人工参考步骤。
- 最终状态判断任务是否完成。
- 必要约束守住流程和安全底线。
- 步数、回退和冗余调用通常用于诊断，不要轻易设成一票否决。

### 指标

#### 先按用途分

| 维度 | 主指标 | 典型诊断指标 |
|---|---|---|
| 有效性 | Task Success Rate、状态正确率 | 子目标完成率、事实正确率 |
| 轨迹质量 | 合法动作率、工具/参数正确率 | 冗余调用、回退、循环、首错步骤 |
| 可靠性 | `pass@1`、`pass^k`、方差 | 随机种子敏感性、重复运行一致性 |
| 效率 | 成功任务成本、端到端延迟 | 轮数、token、工具次数、TTFT、p95 |
| 安全合规 | policy violation、越权率 | 注入成功率、敏感数据泄露、未确认写操作 |
| 鲁棒性 | 扰动后成功率 | API 抖动、页面变化、长上下文、歧义输入 |
| 用户体验 | CSAT、任务放弃率 | 澄清次数、人工接管率、首响时间 |

只报平均成本会藏住失败重试和长尾任务。至少补上：
>
> - `cost_per_success = 总成本 / 成功任务数`
> - 延迟看 `p50 / p95 / p99`
> - 质量、成本、延迟放在同一份报告里

#### `pass@k` 看能力上限

同一任务尝试 $k$ 次，至少一次成功即通过：

$$
\mathrm{pass@k}=1-(1-p)^k
$$

上式假设每次尝试独立，且单次成功率都是 $p$。它适合：

- 搜索、漏洞发现、开放式探索；
- 可以生成多个候选，再由人或验证器挑选的任务；
- 回答 "给足预算，系统是否有机会做成"。

如果从同一任务生成了 $n$ 个样本，其中 $c$ 个成功，代码生成评测常用无偏估计：

$$
\widehat{\mathrm{pass@k}}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}
$$

#### `pass^k` 看重复稳定性

同一任务连续运行 $k$ 次，要求全部成功：

$$
\mathrm{pass}^{k}=p^k
$$

若单次成功率 $p=0.9$：

| k | `pass@k` | `pass^k` |
|---:|---:|---:|
| 1 | 90% | 90% |
| 4 | 99.99% | 65.61% |
| 8 | 约 100% | 43.05% |

Demo 只需挑出一次成功。生产会把每次失败都算进去。这就是两个指标看起来差得很远的原因。

若同一任务实际运行 $n$ 次，其中 $c$ 次成功，任务级经验估计为：

$$
\widehat{\mathrm{pass}^{k}}
=\frac{\binom{c}{k}}{\binom{n}{k}},\qquad n\ge k
$$

τ-bench 也先按任务计算 `pass^k`，再对任务聚合。这里的 $k$ 和 turn 数无关，也不表示从多次尝试中挑最好的一条。

#### `pass^k` 容易算错，也容易讲错

1. `p^k` 依赖 IID 假设。共享服务故障、脏状态和同一个 prompt 缺陷会让失败相关，不能机械乘方。
2. 不要混淆两个实验：
   - 同一任务重复 $k$ 次：测重复稳定性；
   - 连续 $k$ 个不同生产任务：测业务流水线可靠性。
3. 扣款、发信和删数据不能直接重复。要在可重置沙盒中运行，或使用幂等键。
4. 报告 `pass^k` 时，同时给出 `pass@1`、样本量、置信区间、任务桶和失败相关性。

#### 护栏和一票否决

主指标提升不代表应该上线。常见护栏：

- 安全违规不得增加；
- 核心任务桶不得退化；
- p95 延迟、成本、人工接管率不能越过阈值；
- 幻觉、越权、未确认高风险操作可设为 veto。

先定义业务目标，再写不能变差的护栏。Prompt 长度、工具次数这类机制指标只能解释变化，不能代替业务结果。

### Benchmark

| Benchmark | 任务形态 | 主要验证方式 | 面试时强调的边界 |
|---|---|---|---|
| [GAIA](https://arxiv.org/abs/2311.12983) | 多步推理、搜索、文件与多模态 | 简短答案匹配 | 适合测通用工具协作；公开题存在污染风险 |
| [BFCL](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html) | Function / Tool Calling | 函数、参数、执行结果与 API 状态 | 偏工具调用协议，不等于端到端业务 Agent |
| [SWE-bench Verified](https://github.com/SWE-bench/SWE-bench) | 修复真实 GitHub issue | `FAIL_TO_PASS` + `PASS_TO_PASS` 测试 | 受环境、测试覆盖、Harness 与数据污染影响 |
| [SWE-bench Pro](https://github.com/scaleapi/SWE-bench_Pro-os) | 更长程、多仓库与多语言软件任务 | 容器内测试验证 patch | 更接近工程但运行昂贵；公开历史代码仍可能泄漏修复 |
| [WebArena](https://arxiv.org/abs/2307.13854) | 可复现网站上的网页任务 | URL、HTML 与程序化页面状态 | 沙盒可复现，但与真实网站分布仍有差距 |
| [OSWorld](https://os-world.github.io/) | 桌面应用跨应用操作 | OS / 应用状态验证函数 | 环境复杂，初始化和 evaluator 可靠性本身是难点 |
| [τ-bench](https://arxiv.org/abs/2406.12045) / [τ²-bench](https://arxiv.org/abs/2506.07982) | 多轮客服、用户模拟、工具和 policy | 最终数据库状态 + 对话/流程约束 | 用户模拟器与 policy grader 也必须被校准 |
| [Terminal-Bench](https://www.tbench.ai/) | 真实感命令行任务 | 容器内脚本、文件与程序行为 | 靠近工程环境；镜像、网络、资源上限和污染需治理 |
| 多 Agent 协作集 | 委派、通信、协作完成任务 | 组件 + 交互 + E2E 自建 Rubric | 尚无覆盖所有协作范式的统一金标准 |

#### 面试时怎么介绍一个 Benchmark

别背排行榜。说清四件事就够了：

1. Agent 在哪里操作？
2. 输入和目标是什么？
3. 最终状态怎么验证？
4. 它漏掉了哪些生产因素？

#### 公开高分不能直接拿来做上线决定

- 数据污染：公开任务可能进入训练或提示工程；
- evaluator 漏洞：测试过松、状态未真正检查；
- 环境差异：沙盒 API、页面和真实生产不同；
- 任务分布不同：公开平均分未覆盖你的关键长尾；
- 预算不同：Benchmark 给足步数和 token，生产有成本/时延上限；
- 风险不同：公开评测失败只是 0 分，生产失败可能产生真实副作用。

公开 Benchmark 适合找能力边界。上线决定还是要看自己的任务和失败成本。

### LLM-as-a-Judge

#### 先确认是否真的需要 Judge

评分优先级：

```text
可执行真值 / 最终状态
    > 确定性规则与 Schema
    > LLM-as-a-Judge
    > 人工处理高风险、低置信度和分歧样本
```

适合 Judge 的内容：

- 开放式报告是否覆盖关键点；
- 回答是否忠于证据、清晰、合规；
- 两个方案哪个更好，以及差异出现在哪个维度。

不该交给 Judge 的内容：

- 文件是否生成、测试是否通过；
- 数据库最终状态、金额和权限是否正确；
- JSON 是否符合 Schema；
- 工具参数是否违反确定性 policy。

#### 已知偏差

| 偏差 | 表现 | 缓解 |
|---|---|---|
| Position bias | 偏爱 A/B 中固定位置 | 交换顺序复评；矛盾则打平或转人工 |
| Verbosity bias | 更长的答案更易得高分 | Rubric 惩罚无关冗长；审计分数与长度相关性 |
| Self-preference | 偏爱同模型家族的风格 | 异构 Judge、人工金标校准 |
| Style / authority bias | 被流畅、自信或术语掩盖 | 要求逐维度引用可观察证据 |

#### 落地方式

1. 先写 Rubric。每一维都要有可观察的 1–4 档或 pass/fail 标准。
2. 分开必要项、加分项和 veto。安全错误不能被平均分冲淡。
3. 去掉候选中的模型名、版本号和其他身份线索。
4. 比较模型和 Prompt 时优先做 pairwise。绝对分很容易跨批次漂移。
5. 交换 A/B 顺序再评一次。结果随位置变化的样本应标记为不确定。
6. Judge 要引用输出或轨迹中的证据，再给 verdict。不需要它暴露隐藏 Chain-of-Thought。
7. 用人工金标检查一致率或 Cohen's kappa。Judge 或 Rubric 改版后重做校准。

#### Judge 输出

```json
{
  "rubric_version": "refund-v3",
  "dimensions": [
    {
      "name": "policy_compliance",
      "score": 4,
      "evidence": ["tool_call#3 先检查退款期限", "final state 为 refunded"],
      "confidence": 0.94
    }
  ],
  "vetoes": [],
  "verdict": "pass",
  "needs_human_review": false
}
```

> [!warning] 这些做法会让分数失去意义
> - Judge 直接给一个总分，没有证据；
> - Rubric 写成 "回答是否优秀"；
> - Agent 和 Judge 同源，却从不做人类校准；
> - 用多数投票掩盖所有 Judge 共享的系统偏差；
> - 把 Judge 结论当真值，而不保留原始轨迹供复核。

### 数据集

#### 一个 Eval Case 要留下什么

```yaml
id: refund-expired-order
input: 用户请求与已知上下文
initial_state: 可重置的订单、账户与时间
environment_version: refund-sim@sha256:...
agent_config:
  model: pinned-model-id
  prompt_version: v17
  toolset_version: v5
constraints:
  required: [查询订单, 检查政策, 获得确认]
  forbidden: [越权退款, 编造审批记录]
expected_outcome:
  state_assertions: [...]
  response_requirements: [...]
graders: [state_grader, policy_grader, response_judge]
tags: [refund, policy, adversarial, level-2]
```

#### Golden Set 怎么分

| 桶 | 作用 |
|---|---|
| 典型流量 | 保证主路径真实代表业务 |
| 边界 / 对抗 | 歧义、注入、权限、异常、超时 |
| 历史失败回归 | 修过的问题不能复发 |
| Holdout | 从未进入 prompt、few-shot、训练和调参过程 |

此外必须记录任务类型、难度、风险、语言、工具链等标签，避免总平均掩盖关键桶退化。

#### 两种回归任务

端到端回归：

- 从初始状态跑到结束；
- 验证真实任务是否完成；
- 最接近业务，但贵且难定位首错。

Trajectory-prefix 回归：

- 冻结到历史失败前的上下文与环境状态；
- 只评下一步或下几步动作；
- 适合快速验证工具选择、澄清、权限判断和恢复策略。

Trajectory-prefix 的答案应列出可接受动作和禁止动作，不要只给一条参考轨迹。

#### 防污染

- 数据集、Prompt、Skill、训练数据之间做来源追踪；
- 公开集只做外部参照，自建私有集做决策；
- 参数化生成任务，但保留人工审查；
- 定期加入生产新失败，旧失败进入回归集；
- 对 evaluator 做反向测试：准备表面正确、实际错误的诱骗样本；
- Dataset、环境、Rubric、模型和代码全部版本化。

### 设计一套 Agent Eval Pipeline

我会按系统真正运行的顺序答这类题。这样不容易漏掉 reset、版本和失败样本。

#### 1. 定义成功和失败成本

先问：

- 最终可验证状态是什么？
- 哪些错误是 veto？
- 谁定义 Rubric，业务 owner 还是算法团队？
- 失败可否重试，是否有真实副作用？

#### 2. 建立可重置环境

- 固定时间、数据快照、工具版本和依赖；
- 容器 / VM / 模拟数据库隔离副作用；
- 每个 episode 前 reset，结束后校验残留；
- 外部 API 尽量录制回放，或显式记录不可控变量。

#### 3. 构建分桶数据集

真实流量 + 边界对抗 + 历史失败 + holdout，并给每个 case 定义初始状态、预期结果、约束和 grader。

#### 4. 执行和限流

- 每配置多次采样；
- A/B 交替执行，降低时段负载偏差；
- 控制 RPM/TPM、超时和总预算；
- mutating task 使用独立沙盒，避免交叉污染。

#### 5. 按证据强度评分

1. 状态 / 测试 / Schema 等确定性验证；
2. 安全、policy 和过程不变量；
3. LLM Judge 处理开放式质量；
4. 高风险、分歧、低置信度样本进人工队列。

#### 6. 记录证据

```text
Run / Trace
  ├─ case_id, experiment_id, input_hash
  ├─ model / prompt / toolset / code / environment version
  ├─ final outcome, scores, vetoes
  └─ Turn / Span
       ├─ LLM: latency, TTFT, token, stop_reason
       ├─ Tool: name, normalized args, start/end, result/error
       └─ Policy: allow/deny/confirm + rule version
```

敏感输入、工具参数和输出默认脱敏；不要采集模型隐藏思维链。

#### 7. 做统计，找首错

- 报样本量、均值、分位数和置信区间；
- 同一批 case 对比配置时用配对分析；
- 二元结果可用 McNemar 或配对 bootstrap；
- 找首个导致偏离的错误，不要把最后的报错当根因；
- 输出各失败类型的数量、影响和代表轨迹。

推荐初始 taxonomy：

```text
任务理解 → 规划 → 工具选择 → 参数 → 工具/环境故障
→ 状态观察 → policy/安全 → 循环/终止 → 最终表达 → grader 缺陷
```

#### 8. 接入 CI 和线上回流

```text
代码 / Prompt / Skill / 模型变化
              ↓
快速集 → 回归集 → 全量 / 高风险集
              ↓
质量门槛 + 护栏 + 统计置信度
              ↓
灰度 / 影子流量 → 线上监控 → bad case 回流
```

门禁不要只写 "总分不能下降"：

- 核心桶零回归；
- veto 必须为 0；
- p95 延迟和成功任务成本不过线；
- Judge 与人工一致率未过门槛时，不允许自动拦截发布。

### Trajectory 和可观测性

#### 工程组件

| 层面 | 工程能力 |
|---|---|
| 数据模型 | trace/run/turn/span/tool_call、父子关系、时序、错误类型、版本 |
| 上下文传播 | OpenTelemetry Context、`AsyncLocalStorage` / `ContextVar` |
| 采集传输 | SDK hook、异步 batch、背压、重试、幂等去重 |
| 存储查询 | 元数据存储、OLAP、对象存储；按 case/version/error 建索引 |
| 分析 | 路径、延迟、成本、工具错误、首错与异常聚类 |
| 安全 | 脱敏、RBAC、租户隔离、保留策略、审计 |
| 回归资产化 | 从 trace 提取 E2E case 和 trajectory-prefix case |

表里的「重试」有两层：一层是采集链路自己的重试（上报失败要重发且幂等去重），另一层是 Agent 业务重试怎么进 span、重试率怎么当 SLI —— 后者见本文「可靠性与生产化 → 与可观测性的耦合」。

#### Langfuse 属于这一层吗

属于。它主要覆盖轨迹观测、查询、评分、Dataset 和 Experiment，不负责 Agent Runtime。

```text
Agent Runtime / Workflow
  └─ 产生结构化 Trace
       ├─ Langfuse / LangSmith / Phoenix：观察、调试、评分、分析
       ├─ Eval Harness / Braintrust 等：数据集、实验与回归工作流
       └─ Runtime 自身：授权、调度、checkpoint、resume、幂等与副作用
```

| 类别 | 代表 | 解决什么 | 不解决什么 |
|---|---|---|---|
| Telemetry 标准 | OpenTelemetry / OpenInference | span 模型、上下文传播、采集与后端解耦 | 不定义业务成功 |
| 观测与评测平台 | Langfuse / LangSmith / Phoenix | Trace UI、Score、Dataset、实验和线上分析 | 不替代可重置 Benchmark 环境 |
| 实验工作流 | Braintrust 等 | Dataset、Scorer、Experiment、CI 比较 | 不负责 Agent 权限与副作用 |
| Agent Runtime | LangGraph / Temporal / 自研 Harness | 调度、状态、checkpoint、resume、重试 | 不自动产生可信 Rubric 与 Golden Set |

只报一个平台名没有信息量。说清这些实现细节：

- 采集哪些事件；
- 如何关联版本与 case；
- 如何脱敏；
- 如何从 trace 找首错；
- 如何把生产 bad case 转成回归测试；
- 平台故障时为何不能影响 Agent 主链路。

深入记录字段与 A/B 对比方法见 [[04-Agent-工程化评测]]。

### 控制评测成本和延迟

#### 离线

- PR：小型 deterministic smoke set；
- 主分支：目标集 + 历史回归；
- 夜间：全量、多种子、多 Judge、对抗集；
- 发布前：高风险场景与真实环境复测。

#### 在线

- 全量：便宜的规则、状态检查、成本/延迟和 policy 指标；
- 抽样：轻量 Judge 或分类器；
- 小比例：强 Judge、多评委；
- 人工：高风险、低置信度、Judge 分歧与用户投诉。

#### 省预算

- 相同 case 复用不可变输入和环境快照；
- 先跑确定性 grader，失败后无需调用昂贵 Judge；
- 对重复近似轨迹去重采样；
- 先用快速集筛方案，再对候选跑全量；
- 分桶做 power analysis，把预算投向结论不确定的桶；
- 缓存 Judge 结果时必须绑定 Judge、Rubric 与输入哈希。

### 代码题

#### `pass@k` 和 `pass^k`

```python
from collections.abc import Sequence


def pass_at_k(results: Sequence[bool], k: int) -> bool:
    if not 1 <= k <= len(results):
        raise ValueError("k must be within the number of runs")
    return any(results[:k])


def pass_pow_k(results: Sequence[bool], k: int) -> bool:
    if not 1 <= k <= len(results):
        raise ValueError("k must be within the number of runs")
    return all(results[:k])
```

追问点：

- 输入为空、`k` 越界怎么处理；
- 这是单任务判定，跨任务还要取平均；
- 是否保证同一 case、同一配置；
- 副作用环境是否 reset；
- 运行失败通常也算不通过，不能静默丢弃。

#### 简易 Eval Harness

```python
async def evaluate_case(case, agent, graders):
    sandbox = await case.environment.reset()
    trace = await agent.run(
        case.input,
        environment=sandbox,
        timeout=case.timeout,
    )

    scores = []
    for grader in graders:
        scores.append(await grader.score(case=case, trace=trace, env=sandbox))

    return aggregate_with_veto(scores)
```

追问点：

- 并发限速、超时与取消；
- case 隔离和 deterministic reset；
- Agent 失败后仍要保留 trace；
- grader 异常不能伪装成 Agent 失败；
- 每个结果绑定完整版本；
- 结果写入要幂等，避免重试产生重复 run。

#### 轨迹比对

严格比较工具序列会惩罚合法替代路径。更合理的是：

1. 检查必要状态是否达成；
2. 检查 forbidden action 是否出现；
3. 检查关键事件的偏序关系，如 "确认" 必须发生在 "扣款" 前；
4. 冗余调用与步数作为软分；
5. 失败时定位首个违反不变量的步骤。

### 行为面试

#### 从 "感觉变差" 到可复现回归

- S：线上某类任务成功率下降，但日志只有最终错误。
- T：建立可定位、可回归的评测闭环。
- A：
  - 补齐 trace / turn / tool schema；
  - 从投诉和失败轨迹构建分桶 Golden Set；
  - 用状态 grader + Judge；
  - 首错归因后修复工具描述或编排；
  - 接入 CI。
- R：用真实数字说明成功率、人工接管、成本、定位耗时变化。也要说清仍未覆盖的边界。

#### 评测结论与业务反馈冲突

回答重点：

1. 先检查指标是否代理错了目标；
2. 比较线上流量与 Eval Set 分布；
3. 抽查 grader / Judge 是否偏置；
4. 检查环境、工具和版本是否一致；
5. 把冲突样本建成新任务桶，不要争论哪一方 "更真实"。

#### 面试追问

为什么选这个指标？

> 它直接对应业务可验证状态。过程指标用于诊断，成本和安全是护栏。

如何说服团队采纳评测结论？

> 展示版本可复现的配对结果、代表性轨迹、置信区间和失败桶，而不是只给一个平均分。

你踩过什么坑？

> 讲一个具体机制：数据泄漏、Judge 长度偏差、环境未 reset、失败样本被过滤、总分掩盖关键桶退化。

### 容易减分的回答

1. 只报最终准确率，不提环境状态和过程诊断。
2. 只背 Benchmark 名字，讲不出怎么验证。
3. 把 `pass@k` 当稳定性，把多试几次当生产可靠。
4. 说 "用 LLM Judge"，但没有 Rubric、校准和人工审计。
5. 强制匹配唯一参考轨迹，误杀合法替代路径。
6. 单次 A/B 就宣布提升，不报样本量和波动。
7. 只测目标 case，没有回归集与 holdout。
8. 把高风险 policy 写在 Prompt，而不是确定性编排层。
9. 记录原始 prompt、secret、header，却没有脱敏和权限治理。
10. 只说 Langfuse / LangSmith 工具名，不说事件模型和反馈闭环。
11. Agent 失败的 run 被代码异常过滤，造成 survivorship bias。
12. 忽略 grader 自己也可能出错，把 evaluator defect 归因给 Agent。

## Agent 可靠性与生产化

可靠性回答一个问题：出错之后系统怎么办。Agent 的错误来自模型、工具、环境三个源头，重试只对其中一小部分有效。先分类，再决定是重试、回灌给模型、重规划还是终止。

### 复习范围

| 主题 | 要讲清的内容 |
|---|---|
| 错误分类 | 瞬时错、确定性错、模型输出错、业务结果，四类处置完全不同 |
| 重试层级 | LLM API → 工具调用 → Step → Run，每层重试的对象不一样 |
| 幂等与副作用 | 超时 ≠ 没执行；写操作要幂等键，否则不重试 |
| 预算与终止 | 重试计入 token/时间/成本预算；连续同错触发 replan 或终止 |
| 持久化与恢复 | checkpoint 存什么、从哪个 step 续、未完成的工具调用怎么办 |
| [Sandbox](#agent-sandbox) | 执行隔离、资源上限和本地状态重建；外部副作用另行处理 |
| 发布 | 灰度、影子流量、rollback 时 Prompt / 工具 / 模型版本一起回 |

### 高频问题

1. 工具调用失败了，什么情况下该重试，什么情况下不该？
2. Agent 的重试和普通 RPC 重试有什么本质区别？
3. 模型输出了不存在的工具名或不合 schema 的参数，算错误吗，怎么处理？
4. 超时之后怎么知道工具有没有执行？
5. 重试怎么在 Trace 里体现，重试率能说明什么？
6. 进程崩溃后从哪里恢复，哪些状态恢复不了？

### 要点reference：错误重试机制

- *先分类再重试*：四类错误里只有第一类是传统意义的 retry。
	- **瞬时错**（429、5xx、连接重置、网络超时）→ 指数退避 + jitter 重试，尊重 `Retry-After`，有次数上限。
	- **确定性错**（400 参数错、401/403、工具不存在、schema 校验失败）→ 原样重发毫无意义。要么把错误信息作为 tool result 回灌给模型让它改参数，要么直接失败。
	- **模型输出错**（JSON 解析失败、幻觉工具名、参数缺字段）→ 不是工具的错，是模型的错。同样回灌让模型自纠，限 2~3 次，超了终止。
	- **业务结果**（测试没过、文件不存在、搜索为空）→ 这不是错误，是 Agent Loop 的正常一轮。模型看到结果决定下一步。把它当异常处理，Loop 就失去了判断机会。
- *Agent 重试 ≠ RPC 重试*：RPC 重试是同一请求重发，结果应当一致。LLM 调用是非确定性的，「重试」本质是**重新采样**，同一 prompt 可能给出不同的 tool call。所以要分清：重试的是 HTTP 请求，还是让模型再想一次。两者的预算、日志、语义都不一样。
- *四层重试位置*，从底到顶：
	- **LLM API 层**：SDK 内置，只管 429 / 5xx / 超时。对上层透明 —— 这是坑，见项目证据。
	- **工具调用层**：只有幂等工具能在这层重试。工具要声明自己是否幂等，Harness 据此决策，不能让模型判断。
	- **Step 层**：错误作为 observation 回灌，模型自纠。这是 Agent 特有的「语义重试」。
	- **Run 层**：checkpoint + resume，从最后一个成功 step 继续，不从头跑。前提是 step 结果可序列化、副作用已记录。
- *幂等与副作用*：
	- 超时不代表工具没执行。发邮件、扣款、`git push`、删文件这类写操作，超时后重试可能重复执行。
	- 写操作要么带幂等键（请求 id 落在工具侧去重），要么不重试、交给人确认。
	- 读操作随便重试。所以工具设计时把读写分开，比给每个工具单独写重试策略省事得多。
- *预算与死循环*：
	- 每次重试消耗的 token、时间、钱都计入 run 预算，不能游离在外。
	- 连续 N 次同一工具、同一参数、同一错误 → 不是再试一次，是触发 replan 或终止。模型陷入这种循环时自己跳不出来。
	- 用 `max_steps`、`max_consecutive_failures`、总超时三个阈值共同兜底，任一触发就停。
- *与可观测性的耦合*（面试里能拉开差距的部分）：
	- **每次 attempt 独立 span**，挂在同一个父 span 下，带 `attempt`、`error_type`、`backoff_ms`。不这么做，trace 里只看到「一次调用 30s」，看不出是 3 次 10s。
	- **重试率是领先指标**。上游限流或模型服务抖动时，重试率先涨，成功率后掉。按 `error_type` 分桶的 `llm_retry_rate`、`tool_retry_rate` 比成功率更早报警。
	- **重试 token 计入 run 成本**。只算最后一次成功的 token，`cost_per_success` 会系统性低估。
	- **retry 后成功的 run 要打标**。它算成功，但掩盖了不稳定；评测时按 `pass^k` 看会露馅。
	- **失败 run 必须落库**。被异常吞掉的 run 不进 trace，评测就有幸存者偏差。
	- **trace 上报自身要幂等**。否则重试导致重复 span，所有统计都翻倍。

### 常见错误与风险

- 所有异常走同一个 catch，429 和 400 用同样策略重试。
- 工具超时后立即重试，副作用执行了两次。
- 模型反复用同样参数调同一个失败工具，没人打断。
- SDK 层默认重试多次、退避到几分钟，上层只看到一个慢请求，排查半天以为是模型慢。
- 重试成功后 trace 里只有一条 span，重试率永远是 0。
- checkpoint 存了运行时对象引用，进程重启后反序列化失败。

### 项目证据

dawn-ai 没有引 Spring Retry 或 Resilience4j，走的是**语义层恢复**，传输层交给 Spring AI 默认。

| 机制 | 位置 | 做什么 |
|---|---|---|
| 连续空结果触发 replan | `ToolExecutionAspect` 环绕所有工具的 `apply()`；`replan-threshold: 2` | 用字符串启发式判定空结果（`docsFound=0`、`未找到`、`No results`），连续 2 次 → `TaskPlanner.rePlan()`，把新计划作为 tool result 回灌，同时 SSE 推 `replan` 事件。一次 run 只触发一次 |
| Sub-agent 超时软失败 | `GenericReActSubAgentExecutor`；`timeout-seconds: 60` | `future.get()` 超时 → `cancel(false)` 不强行中断（Spring AI HTTP 调用不一定响应 interrupt），返回 `PARTIAL_SUCCESS` + 已完成 steps 快照。`AiConfigurationException` 直接抛出不做软失败 —— 配置错不是可恢复错 |
| 工具级熔断 | BashTool `max-consecutive-failures: 3`、`timeout-seconds: 30` | 连续失败或空输出达阈值后，返回「停止调用」的 observation，让模型换路 |
| 预算兜底 | `max-steps: 10`、`max-calls-per-session: 3`、`max-dispatches-per-session: 3`、`stream.timeout-ms` | 步数、RAG 调用数、sub-agent 派发数、总时长四个上限 |
| 线程池满快速失败 | `RejectedExecutionException` → `SubAgentResult.failed` | 不排队不重试，直接告诉模型「稍后再试」 |

**短板**：`spring.ai.retry.*` 一项没配，走 Spring AI 1.1.x 默认（max-attempts 10、初始退避 2s、倍率 5、单次上限 3 分钟，4xx 不重试）。最坏情况一次 LLM 调用内部退避累计接近 20 分钟，Langfuse 里只看到一条超长 span，重试对上层完全不可见。面试讲这个：为什么没做、代价是什么、改的话先加什么指标。

## Agent 沙箱与执行环境 {#agent-sandbox}

Agent 会运行模型生成的代码、仓库脚本和第三方依赖。沙箱限制这些程序能访问的文件、网络、进程和资源。它保护的是执行环境，不能保证模型判断正确，也不能替代业务授权。

### 复习范围

| 主题 | 要讲清的内容 |
|---|---|
| 隔离选型 | 子进程、普通容器、gVisor、microVM 的机制和边界 |
| 执行协议 | Agent → Gateway → Executor，身份、命令、输出、取消和幂等 |
| Workspace | 挂载、快照、远端副本、ChangeSet、并发冲突 |
| 生命周期 | 按 run / session 分配、预热、回收、TTL、故障清理 |
| 资源和凭证 | CPU / 内存 / PID / 磁盘 / 日志上限、网络出口、短期凭证 |
| 副作用与恢复 | 本地状态重置、外部操作查证、旧执行者停止与失效 |

### 高频问题

1. `ProcessBuilder` 指定工作目录，算沙箱吗？
2. Agent 应用已经部署在 Docker 里，为什么工具执行仍要隔离？

6. 沙箱按每个 tool call 创建，还是按任务、会话创建？
7. 如何取消整个执行，而不只停止等待结果？
8. 沙箱重置后能否重试扣款、发信或数据库写入？

### 要点reference

#### 子进程、应用容器和工具沙箱的区别

`cwd` 只决定相对路径从哪里开始解析。普通子进程仍能使用操作系统授予它的权限，访问允许读取的绝对路径、网络和继承的环境变量。命令 denylist 可以降低误操作风险，但解释器、依赖和脚本里的行为远超过几个命令名称。

把整个 Agent 服务放进 Docker，只隔离了应用与宿主。若模型生成的代码也在该容器里、以同等权限执行，它仍可能接触应用配置、凭证和其他会话的数据。工具沙箱应是单独的执行环境，按任务或租户绑定权限，控制服务不与不可信代码共享全部权限。

也不是所有工具都要启动一个容器。受控的搜索 API 可以经网关直接调用；执行任意 shell、Python、浏览器脚本或仓库构建时，才需要根据风险选择隔离环境。**隔离边界由可执行行为决定，不由工具名称决定。**

#### Docker、gVisor、microVM 怎么选

| 方案                       | 实现原理                                           | 取舍                                                  |
| ------------------------ | ---------------------------------------------- | --------------------------------------------------- |
| 普通子进程                    | 继承所在环境的权限，可另行配置 OS 限制                          | 启动简单，但仅有 cwd、超时和命令过滤不足以约束不可信代码                      |
| 普通 Linux 容器              | namespaces 隔离资源视图，cgroups 限资源，共享承载容器的 Linux 内核 | 工具链兼容性较好；仍**依赖共享内核**与正确配置                           |
| gVisor                   | 用户态 Sentry 实现 Linux 系统调用接口，减少工作负载直接接触宿主内核的机会   | **增加隔离层**；要测系统调用兼容性、文件 I/O 和网络性能，它不是简单的 syscall 过滤器 |
| microVM，以 Firecracker 为例 | 基于 KVM 虚拟化运行独立 guest kernel，缩减虚拟设备模型           | **适合需要内核边界**的执行任务；增加 guest 镜像、网络、快照和生命周期管理工作        |

不要只背一张“安全性高、中、低”的表。先说明是否运行恶意或未知代码、是否共享宿主、能接受多少启动与运行开销，再验证方案。microVM 也不是绝对安全；gVisor、VMM 和宿主仍需维护补丁，授权过宽的挂载或网络访问也不会自动被修复。

#### 容器要配置哪些限制

| 机制 | 实际限制 | 常见误解 |
|---|---|---|
| mount / PID / network namespaces | 文件挂载、进程编号、网络设备等视图 | 独立 network namespace 不代表禁止出网，还要配置出口策略 |
| user namespace、rootless、非 root 用户 | 降低宿主权限或容器内权限，三者不能混称 | 镜像里设置 `USER` 不等于 Docker daemon 以 rootless 模式运行 |
| cgroups | CPU、内存、PID 数等资源 | 容器不会自动获得适合业务的配额，限制要显式设置并确认生效 |
| capabilities、`no-new-privileges` | 移除不需要的特权，阻止通过执行程序获得额外权限 | root 用户再加一份命令黑名单，不等价于最小权限 |
| seccomp、AppArmor / SELinux 等 | 限制系统调用或资源访问 | seccomp 不是按文件路径授权的替代品 |
| 只读 rootfs、受限可写卷 | 根文件系统不可改，只给 Workspace / 临时目录写权限 | 只读 rootfs 不会把额外挂载的可写目录也变成只读 |
| 存储配额与日志上限 | 限制可写层、卷、临时文件和输出增长 | CPU / 内存限制不能阻止磁盘或日志被写满 |

构建任务往往需要缓存、临时目录或下载依赖，应按实际需求开放指定目录和受控出口，不要为了让构建通过就开启 `privileged`、挂载整个 home 或暴露运行时管理 socket。

#### Agent 怎么和沙箱通信

```text
Agent / Tool
    ↓ 提交动作和工作区引用
Tool Gateway：校验身份、参数、授权、审批和预算
    ↓ 服务端封装执行请求
Sandbox Manager / Executor：分配环境、执行、取消、收集产物
    ↓ 受限 runtime API
独立工具沙箱
    ↑ stdout / stderr / 状态事件 / ChangeSet
```

Docker / containerd 管理权限留在可信的 Executor。Agent 和沙箱内代码不能拿到管理 socket，也不能自行指定宿主挂载目录、特权模式或租户身份。控制接口需要认证，并检查调用者是否有权操作对应的 `executionId` 和 `workspaceId`。

下面是服务端封装后的请求示意，不是 Dawn 已有 API。ID、策略和凭证引用由网关生成或校验，超时也受服务端上限约束：

```json
{
  "executionId": "exec-017",
  "runId": "run-042",
  "workspaceId": "ws-042",
  "baseRevision": "revision-7",
  "argv": ["mvn", "-q", "test"],
  "cwd": ".",
  "timeoutSeconds": 120,
  "policyRef": "java-build",
  "credentialRefs": ["maven-read-token"]
}
```

固定工具优先使用结构化 `argv`，避免拼接 shell 字符串。确需管道和脚本时，把 shell 执行作为明确授权的能力放进沙箱。`argv` 本身不是安全边界，程序及其参数仍要受策略和环境约束。

同机可用 Unix socket，远端可用 HTTP 或 gRPC。HTTP + SSE 可以返回状态和输出，取消走单独请求；gRPC streaming 也要把取消显式传到执行进程。Firecracker 的管理 API 用来配置 microVM，不是 guest 内执行任意命令的业务 API，仍需要受控的 guest 执行代理。

输出事件带 `executionId + seq`，结束结果区分正常退出、超时、取消、OOM 和策略拒绝。`exitCode=0` 只表示命令正常退出，不代表用户任务完成。流断了也不代表进程停止，客户端应能按执行 ID 查询状态；执行结果未知时，不生成新 ID 盲目重发。

#### Workspace 如何隔离和回传

| 方式           | 状态关系                       | 适用与风险                              |
| ------------ | -------------------------- | ---------------------------------- |
| bind mount   | 沙箱和本地看到同一批底层文件             | 省复制，但 Agent 的写入立即影响本地；需要明确授权和并发写控制 |
| 每任务快照 / 独立副本 | 从固定基线执行，结束后导出 ChangeSet    | 更适合检查后合并；任务失败可丢弃本地变更，但有复制或快照管理成本   |
| 远端 Workspace | 按 manifest 上传允许的输入，再下载产物差异 | SSH 只负责安全传输和远端认证，远端进程的隔离仍要另外做      |

Git worktree 解决版本工作区分离，不是 OS 安全边界。不同 worktree 还共享 Git 管理数据，若都暴露给不可信代码，就不能用它证明租户隔离。

`baseRevision` 要能还原实际输入。只存 commit 不够，允许输入中的未提交修改和未跟踪文件也要进入快照或 manifest，并保留路径与内容 hash。凭证文件不要跟着项目目录一起上传。

结果以 ChangeSet 回传，包含新增、修改、删除文件及其基线 hash。合并前检查目标文件是否仍匹配基线；有变化就报告冲突或做受控合并，不能直接覆盖。检查路径范围、符号链接和产物大小，避免把沙箱内路径直接解释为宿主路径。

Hash 比较之后还要防并发写入。应用变更时需要锁、版本条件或单写者机制；租约过期后的旧执行者，应由实际提交入口校验 generation / fencing token 拒绝其写入。多文件更新要设计失败恢复，不能把“逐个 rename 原子”误认为“整批修改原子”。

#### 生命周期、预热和取消

常见选择是一个 run 复用一个沙箱，让多次工具调用共享文件和依赖；确实需要跨 run 延续环境时，再绑定到 session。每个 tool call 都新建环境更干净，但会增加启动、依赖准备和状态传递成本。

完整生命周期包括创建、就绪、执行、收集产物和销毁。空闲 TTL、单次执行超时、整个 run 的总时限分别约束不同阶段。任务结束后按策略销毁或清理；清理失败要进入可观测的待回收状态，由后台 reaper 重试，不能只在 `finally` 里尽力删一次。

预热优先复用未注入用户数据和凭证的干净镜像或快照，不把上个租户用过的环境直接交给下个租户。跨租户可写缓存还会带来数据残留和缓存污染风险。镜像 pin digest 有助于复现，也要有升级补丁的机制。

取消时先停止接受新的执行请求，再向受管进程发送终止信号；宽限期后仍未退出，就终止该执行所属的进程组、cgroup 或整个专用沙箱。只杀父 shell 可能留下子进程，`Future.cancel()` 也不能证明远端执行已停止。超时应在 Executor 侧执行，控制服务断连后仍有效；确认资源已停止后，再回收 Workspace 并释放额度。

#### 网络出口和凭证放在哪里

网络默认拒绝，根据任务开放依赖镜像站或指定业务 API。策略由受控代理、防火墙或网络策略执行，限制访问宿主服务、其他租户网络和云元数据服务。只检查最初的 URL 字符串不够，DNS 解析与重定向后的实际目标也要受限制。

`credentialRefs` 只是服务端句柄。优先让可信网关代为完成带凭证的业务调用；确需把凭证交给执行程序时，只提供任务范围内的短期凭证，不继承宿主全部环境变量。传给不可信进程的 secret 就可能被该进程读取，不能因为它在容器里就宣称不会泄露。

输出和产物在记录到 Trace、发回模型前做脱敏、限长和不可信内容标记。输出超限要继续受控排空管道或终止任务，不能停止读取后把进程卡死。详细授权和审批规则见后文「Agent 安全与权限」。

#### 重置沙箱不能撤销外部副作用

删除可写层可以丢弃其中的本地修改，恢复快照可以恢复被纳入快照的状态。共享卷、外部数据库、邮件系统和支付服务不会因此回到过去。已应用到用户工作区的 patch 也需要独立的回滚机制。

沙箱内进程超时后，外部请求可能已经被对方执行。先记录待确认状态，按业务操作 ID 查询结果；可重试的写请求要用下游认可的幂等键，必要时走补偿或人工处理。Executor 按 `executionId` 去重只能减少重复派发，不能单独提供跨系统 exactly-once。

#### 沙箱效果怎么评

分别覆盖越界文件访问、未授权网络连接、其他租户数据可见性、资源限额、取消后的残留进程、租约过期后的旧写入，以及回收后的数据残留。是否拦住要看实际环境事件，不能只看模型有没有拒绝。

同时测合法任务是否还能完成。过严的系统调用或网络策略可能把正常构建也挡住。性能记录排队、冷启动 / 预热启动、执行、上传下载和回收耗时，并按 run 关联 `sandboxId`、镜像 digest、策略版本、Workspace 基线、执行原因和资源用量。启动慢与命令慢要能在 Trace 里分开。

### 常见错误与风险

- Agent 服务和任意代码在同一环境中共享凭证，应用容器化却没有隔离工具。
- 配了 CPU / 内存限制，遗漏 PID、磁盘、日志或总执行时限。
- 只读 rootfs 配上可写宿主目录，误以为本地文件已受保护。
- 客户端超时即返回取消成功，沙箱里的子进程仍在执行。
- 用旧基线产出的 patch 覆盖用户新修改，或旧租约持有者继续提交。
- 复用带用户数据的预热环境，造成跨会话污染。
- 重置沙箱后盲目重跑外部写操作，产生重复副作用。

### 项目证据与建议

以下现状依据仓库已有的 [Dawn 架构九问 Q6–Q9](../interview-backup/08-Dawn-AI-Agent-架构九问深挖.md)，不是对 Dawn 最新源码的重新审计。

| 已有笔记记录 | 应如何解释 | 建议，尚未由这份笔记证明已实现 |
|---|---|---|
| `BashTool` 用 `ProcessBuilder("/bin/bash", "-c", command)`，设置 `baseDir` | 在应用所在环境中启动 shell，cwd 不是文件访问边界 | 将执行委托给独立 Executor，配置隔离和资源限制 |
| 有命令过滤、写操作开关、执行超时和输出上限 | 属于已有风险控制，不等价于内核或租户隔离 | 保留这些控制，同时避免执行程序继承应用凭证 |
| Docker Compose 部署 Agent 应用，Skill 目录只读挂载 | 应用部署容器与每任务工具沙箱是两件事 | Manager 分配专用工具环境，Agent 不持有管理 socket |
| 没有 Workspace 快照、ChangeSet 和冲突检测 | 不能承诺任务修改可以审阅后合并或可靠回滚 | 引入基线 manifest、受控回传和版本条件检查 |

落地时可先定义 Executor 的请求、结果和取消协议，再接入独立容器与任务工作区。需要运行不可信多租户代码时，评估 gVisor 或 microVM。每一步用隔离检查、合法任务成功率和资源开销决定是否继续，不靠更换一个运行时名称证明安全。

## Agent 安全与权限

Agent 会读取不可信内容，也会调用真实工具。安全设计要把模型当成可能受诱导的决策者，权限和副作用由确定性系统控制。

沙箱选型、执行协议和 Workspace 隔离见 [Agent 沙箱与执行环境](#agent-sandbox)。本节侧重谁可以调用、凭证如何授予，以及高风险操作如何审批。

|---|---|

| 授权 | actor、resource、action、context |
| 执行 | sandbox、网络、文件、进程和资源限制 |
| 数据 | secret、PII、日志脱敏、保留策略 |
| 输出 | 数据外泄、危险内容、对外发送确认 |

6. 什么操作必须 Human-in-the-Loop？

### 要点reference

- *为什么 system prompt 防不住注入*：注入攻破的是模型的判断，用模型自己的判断去防是「自己防自己」。system prompt 是概率性软约束，只能降低采纳率，不能作为边界。目标改成：**注入成功了也拿不到权限、secret 和网络出口**。
- *模型可见 ≠ 可调用，怎么分离*：三个面分开——认知面（模型选工具）、权限面（系统判这个用户这个 turn 能不能调）、执行面（在哪跑、能碰什么）。模型只参与第一层。工程上先 policy filter 再给模型看候选工具，模型看不见自己无权的工具。
- *用户授权和工具凭证怎么传*：模型只看到 `credentialRef`，Executor 从 secret store 换短期 token；凭证不进 prompt、不进 tool result、不进日志。dawn-ai 的 `ProcessBuilder` 继承宿主环境变量，子进程能看到全部 credential，这是明确短板。
- *长任务 token 过期*：短期凭证 + 按任务注入 + 到期在 Executor 层刷新，模型无感。
- *工具输出进模型前做什么*：打信任标签、包边界、限尺寸。dawn-ai 用 `UntrustedContent.wrap()` 把 Web / RAG 内容包进 `<untrusted_external_content>`，先把正文里伪造的同名标签替换成占位符防 marker escape。Bash 读的文件内容**没有**统一包装，仓库文件里的间接注入靠模型自觉。
- *什么必须 HITL*：不可逆 + 高影响——删 / 覆盖文件、扣款、发信、外联发数据、执行下载的脚本。真 HITL 不是模型说「请确认」，是系统发 `approvalId + actionDigest + expiresAt`，Executor 只认匹配 digest、未过期、未用过的 token。dawn-ai 目前 HITL 只是 prompt 要求（`SECURITY_GUIDANCE`），没有可验证的审批 token；设计上唯一干净的拦截点是 `ToolExecutionAspect` 的 `@Around`，在 `proceed()` 前插 gate。
- *dawn-ai 实践*：BashTool 三档分级——硬红线（shutdown / mkfs，永拒、开关无效）/ 写操作（rm / mv / 重定向，受 `allow-write` 开关，**默认 false**）/ 只读 + 网络放行。`checkSecurity` 按 `; | && ||` 拆子命令逐段判，`stripPath` 防 `/sbin/shutdown`、`sudo` 包装绕过。这个决策的故事值得讲：第一版做的是「对话授权」（模型说要写就放行），后来推翻，因为决定权在可被注入操纵的 LLM 手里，是 security theater；真正的门控只能是不依赖 LLM 的确定性开关。还有：Skill 资源读取拒绝绝对路径、`..`、空字节，`toRealPath()` 后验证仍在 root 下；日志 mask API key 和 `Authorization`。

### 防线

- 不可信内容与系统指令分区。
- 工具调用前做参数和权限检查。
- 最小权限、短期凭证、按任务注入。
- 写操作按风险分级，必要时确认。
- 沙盒限制文件、网络、进程和资源。
- Trace 默认不记录 secret 和完整敏感内容。

### 常见错误与风险

- 把 API key 放进 Prompt。
- 只在会话开始鉴权，后续工具调用直接放行。
- 让模型自己判断是否有权限。
- 工具结果中的恶意文本覆盖系统意图。
- 日志和评测数据泄露用户内容。

## Agent 性能与成本

Agent 总延迟由多轮模型调用和工具执行累积。先判断是轮数过多，还是单轮过慢，再进入不同的排查路径。

### 复习范围

| 层面 | 指标 |
|---|---|
| 模型 | TTFT、prefill、decode、input/output token |
| 缓存 | cache read、cache creation、稳定前缀 |
| Agent Loop | turn 数、回退、重复工具调用 |
| 工具 | 开始时间、耗时、并发度、失败率 |
| 任务 | 端到端 p50/p95/p99、cost per success |
| 容量 | RPM、TPM、队列、背压和限流 |

### 高频问题

1. Agent 比竞品慢，第一步怎么拆？
2. TTFT 高和总生成时间长分别说明什么？
3. 为什么上下文越长，成本可能非线性增长？
4. 哪些工具可以并行，哪些必须串行？
5. Prompt Cache 为什么会失效？
6. 如何权衡成功率提升与 token、延迟增加？

### 要点reference

- *Agent 比竞品慢，第一步拆什么*：先分是轮数多还是单轮慢。轮数看 `steps.size()` 和 finishReason；单轮拆排队 → prefill（TTFT）→ decode → 工具。dawn-ai 每个 step 记 `durationMs`，Langfuse 里能看到 LLM span 和 tool span 的瀑布。
- *TTFT 高 vs 总时长长*：TTFT 高 = prefill 慢或排队，多半是 prompt 太长或没命中 cache；总时长长但 TTFT 正常 = decode 多或工具慢。
- *上下文越长成本为什么非线性*：attention $O(n^2)$；更实际的是每一轮 ReAct 都要把全部历史 + 工具结果重发一遍，n 轮就是 n 次全量 prefill。所以工具输出截断（`max-tool-output-tokens: 3000`）省的不是一次，是后面每一次。
- *哪些工具可并行*：只读可并行，写串行。dawn-ai 的 RAG 内部 Dense 和 BM25 在 `ragRetrievalExecutor`（4 / 16 / queue 128，`CallerRunsPolicy`）并行；工具之间的并行交给 Spring AI；sub-agent 目前同步阻塞，并行派发留了 `CompletableFuture` 扩展点没做。
- *Prompt Cache 为什么失效*：前缀变了。system prompt 里任何动态段落放在前面都会打掉 cache。dawn-ai 的 system prompt 是 base + 安全准则 + 画像 + 记忆 + skills + sub-agents + 计划 + topic，**动态段在中间**，稳定前缀只有 base + `SECURITY_GUIDANCE` 那一段。要吃 cache 得把动态段全挪到末尾。
- *成功率 vs token、延迟怎么权衡*：比 `cost_per_success` 不比单价。便宜模型失败重试后总成本可能更高。加 rerank / HyDE / re-plan 每项都是 +1 次 LLM 调用，要用评测收益换。
- *dawn-ai 实践*：四个 token 预算段——history 8000 / tool output 3000 / memory 1000 / skills 500，给模型的输入上限可控。`chatStreamExecutor` 8 / 32 / queue 64 `AbortPolicy`，满了直接 503 `CAPACITY_EXCEEDED`，不让 Tomcat 线程陪跑 20 分钟 SSE（`stream.timeout-ms: 1200000`）。Embedding 批处理先按 token 再按条数切（DashScope 单次最多 10 条硬限制）。**已知短板**：token 指标只记最后一次调用；没有 prompt cache 命中率指标；HyDE、rerank、query rewrite、category classify、fact extraction 全开时一次请求可能 5~6 次 LLM 调用，没有按阶段的成本分解。

### 排查顺序

1. 对齐模型、Prompt、工具、缓存和任务样本。
2. 比较 turn 数和单 turn 耗时。
3. 单 turn 内拆排队、prefill、decode 和工具。
4. 找重复调用、无效回退和大体积工具结果。
5. 用成功任务成本做最终比较。

### 常见错误与风险

- 只看平均延迟，忽略 p95。
- 只记录工具耗时，不记录开始时间，看不出串并行。
- A 组缓存命中，B 组冷启动。
- 用更便宜的模型，但失败重试导致总成本更高。
- 压缩上下文时丢失关键约束。
