# Q2 · 如何设计 benchmark，保证不同方案是在相同环境下进行比较？

## 先明确：Agent 语境下的「方案」和「环境」是什么

**被比较的方案**通常是这几类：

- 不同的 system prompt / 提示词版本
- 不同的模型或 effort 档位
- 不同的**工具设计**（一个大工具 vs 拆成几个小工具）
- 不同的**上下文策略**（全量历史 / compaction / RAG 检索）
- 不同的**架构**（单 agent vs multi-agent 分工）

**"相同环境"在这里不是指 CPU 和内存**，而是：

> 模型版本 + 采样参数 + 上下文构成 + 工具后端 + **缓存状态**

把这句先说出来，后面的展开才在点上。

## Agent benchmark 和传统 benchmark 的根本差异

| | 传统服务 benchmark | Agent benchmark |
|---|---|---|
| 被测对象 | **确定性**，同输入同输出 | **本身就随机**，同输入可能走不同路径 |
| 噪声来源 | 环境（CPU、GC、邻居） | **模型采样 + 环境** |
| 跑几次 | 跑够让环境噪声收敛 | **每题至少 3-5 次**，因为方案本身在抖 |
| 结论形式 | "A 比 B 快 15%" | "A 的成功率 78%±6%，B 是 71%±7%" |
| 主指标 | 延迟、吞吐 | **质量 / 成本 / 延迟三个一起报** |

**最重要的一句**：因为被测对象自带随机性，**跑一次得出的对比结论没有任何意义**。这是和传统 benchmark 最大的区别，必须主动说。

## 必须钉死的控制变量

### 1. 模型侧

| 项 | 怎么钉 | 不钉会怎样 |
|---|---|---|
| 模型版本 | **pin 到具体 model id，不用 `latest` 之类的别名** | 别名背后的模型会悄悄换，你以为在比 prompt，实际在比模型 |
| 采样参数 | temperature、top_p 固定 | 显然 |
| thinking / effort | 固定档位 | effort 直接影响质量和成本，是个大变量 |
| max_tokens | 固定 | 影响是否被截断 |

> [!warning] `temperature=0` ≠ 确定性
> 很多人以为温度归零就复现了。**不成立** —— 服务端 batching、浮点累加顺序、MoE 路由都会带来抖动。
> 温度归零只是**减小**方差，不是消除。所以还是要跑多次。

### 2. 上下文侧

| 项 | 怎么钉 |
|---|---|
| prompt | **逐字节固定**，包括空格和换行 |
| 工具集 | 完全一致 —— 工具定义在 prompt 最前面，加一个工具会改变整个前缀 |
| 检索结果 | RAG 场景要 pin 住索引快照，否则索引更新了对照组就失效 |
| 历史消息 | 组装逻辑一致 |

### 3. 缓存状态 —— 最隐蔽的一条

> [!danger] 这是 Agent benchmark 最容易翻车的地方
> A 方案跑第二遍时命中了 prompt cache，于是又快又便宜；B 方案是冷启动。
> **你以为在比方案，实际在比缓存命中率。** 成本能差 10 倍，TTFT 能差一倍。
>
> 对策：**要么全部预热到命中，要么全部冷跑**，并在报告里写明是哪种。
> 校验方式：看每次请求的 `cache_read_input_tokens`，确认两组处于同一状态。

### 4. 工具后端

工具是打真实后端还是 mock？必须一致。

- **mock 的好处**：延迟稳定、结果确定、不花钱，能把噪声隔离到只剩模型这一个来源
- **真实的好处**：反映端到端真实表现
- **实践**：调 prompt / 工具设计时用 mock（噪声小，信号清晰），最终验收用真实

## 评测集设计

| 要求 | 说明 |
|---|---|
| **20-50 条起** | 少于 20 条，随机性会淹没真实差异 |
| **来自真实流量** | 自己编的题会不自觉地贴着现有实现写 |
| **三类齐全** | 典型 case + 边界 case + **历史失败 case** |
| **分桶标注** | 按任务类型打标，后面要分层看 |
| **holdout 集** | 一份**从未进入过任何上下文**的集合，防泄漏 |

> [!danger] 评测集泄漏
> 如果评测用例的内容被写进了 system prompt、skill 正文或 few-shot 示例，
> 那就是**拿着答案考试**。分数会很好看，上线会翻车。

## 指标：三个维度必须一起报

只报一个维度是耍流氓。

| 维度 | 指标 |
|---|---|
| **质量** | 任务成功率（主）、分维度得分、人工干预次数 |
| **成本** | input / output / **cache_read / cache_creation** token 分开记，折算金额 |
| **延迟** | TTFT、端到端时长、**迭代轮数** |

为什么必须一起看：

> "新 prompt 成功率从 78% 提到 82%" —— 听起来是提升。
> 补一句"但平均 token 从 12K 涨到 41K，轮数从 4 轮涨到 13 轮" —— 这就变成了一个**要看场景才能定的取舍**，甚至可能是退步。

**token 必须分四类记**：缓存命中和未命中的单价差一个数量级，只记总数既算不准成本，也发现不了缓存失效。

## 执行流程

1. **交替执行 A/B/A/B**，不要跑完 A 再跑 B。模型服务的负载和限流有时段性，连着跑一组会把时段效应算到方案头上。
2. 每题跑 3-5 次。
3. 记录每次运行的完整 trace（字段清单见 [[04-Agent-工程化评测]] Q15）。
4. 按变量组聚合，出分布不出单值。

## 陷阱清单

| 陷阱 | 后果 |
|---|---|
| 只跑一次 | 结论 = 运气 |
| 缓存状态不一致 | 比的是缓存不是方案 |
| model 用别名 | 底层模型换了都不知道 |
| 只看成功率 | 忽略成本爆炸 |
| 评测集泄漏 | 分数虚高 |
| 用 LLM judge 但没校准 judge | 整套结论建立在沙子上（见 [[04-Agent-工程化评测]] Q17） |
| 两组在不同时段跑 | 混入 API 侧负载差异 |

## 一句话收尾

> Agent benchmark 的难点不在环境控制，在于**被测对象本身是随机的**。
> 所以核心动作是：把模型版本、采样参数、prompt、工具集、**缓存状态**全部钉死，
> 用固定的评测集跑多次，同时报质量 / 成本 / 延迟三个维度的分布 —— 不是单个数字。

# Q3 · 一个系统比竞品慢时，怎样定位具体慢在哪个环节？

## 第 0 步：确认口径一致

先排假问题（这一步在哪个语境下都成立）：

- 两边是**同一类任务**吗？对方的 demo 是简单问答，你的是多轮工具调用，没法比。
- 比的是**首字延迟还是总时长**？这两个在 Agent 场景下可以完全脱钩。
- 有没有**流式**？对方流式你非流式，体感差距巨大但总时长可能一样。
- 是**冷启动还是稳态**（缓存命中与否）？

## Agent 系统的延迟结构

传统后端的分层（网络 → 应用 → DB）在这里不适用。Agent 的延迟长这样：

```
用户提交
   │
   ├─ [1] 网关 / 鉴权 / 限流                          通常 <10ms，很少是瓶颈
   │
   ├─ [2] 上下文组装                                  RAG 检索、读文件、装配 messages
   │
   ├─ [3] LLM 调用 #1  ┌─ 排队 / 限流等待
   │                   ├─ prefill（读输入）  ← 输入越长越慢；缓存命中则大部分跳过
   │                   └─ decode（吐输出）   ← 输出越长越慢，逐 token
   │
   ├─ [4] 工具执行                                    串行还是并行？这里差距能到几倍
   │
   ├─ [5] LLM 调用 #2..N                              重复 [3][4]
   │
   └─ [6] 收尾

总时长 ≈ Σ(每轮 LLM 时间 + 每轮工具时间)
```

**关键结论**：Agent 的总延迟 = **轮数 × 单轮耗时**。所以定位的**第一个分叉**永远是：

> **是轮数太多，还是每一轮太慢？**

这一句是本题的题眼。分叉之后走的是完全不同的两条路。

## 六大根因（按实际发生频率排）

| # | 根因 | 症状 | 怎么确认 | 怎么修 |
|---|---|---|---|---|
| 1 | **迭代轮数太多** | 单轮不慢，但要跑十几轮 | 统计每个任务的 turn 数分布 | 合并细粒度工具、prompt 引导、开启并行工具调用 |
| 2 | **prompt cache 未命中** | 每轮 TTFT 都高，成本同步偏高 | 看 `cache_read_input_tokens` 是不是长期为 0 | 修前缀稳定性 —— 时间戳、UUID、中途改工具集 |
| 3 | **上下文膨胀** | 越到后面的轮次越慢 | 画 input_tokens 随轮数的增长曲线 | compaction / context editing / subagent 隔离 |
| 4 | **工具串行执行** | 工具耗时刚好是各工具之和 | 看 tool span 是首尾相接还是重叠 | 同一轮的多个 `tool_use` 并发执行 |
| 5 | **输出过长** | output_tokens 大，decode 时间长 | 看 output_tokens 分布 | 约束输出格式、禁止复述输入 |
| 6 | **模型 / effort 选高了** | 单轮就慢，且和任务难度不匹配 | 换档对比 | 分层路由：简单子任务给小模型 |

**前三条占了实际问题的绝大多数。** 第 2 条尤其阴 —— 它同时拖慢延迟和抬高成本，但不看指标完全发现不了。

## 怎么把 prefill 和 decode 拆开

这是 Agent 性能分析特有的技能：

| 观测量 | 主要由什么决定 |
|---|---|
| **TTFT**（首 token 延迟） | 排队等待 + **prefill**（≈ 输入 token 数，缓存命中可大幅跳过） |
| **TTFT 之后的时长** | **decode**（≈ 输出 token 数 × 单 token 生成速度） |

判断逻辑：

- **TTFT 高、decode 正常** → 输入太长、缓存没命中、或者被限流排队
- **TTFT 正常、decode 长** → 输出太长，或模型太大
- **两个都高** → 上下文膨胀 + 输出啰嗦，通常一起出现

## 需要什么可观测数据

一个够用的 Agent trace，应该能直接回答上面所有问题：

```
Trace（一次运行）
 ├── 总时长 / 总 token / 总成本 / 轮数
 ├── Turn 1: TTFT | 总时长 | input(其中 cache_read=?) | output | stop_reason
 │    └── ToolCall: 名称 | 开始时间 | 耗时 | 成功?      ← 开始时间能看出串/并行
 ├── Turn 2: ...
 └── ...
```

**`ToolCall` 一定要记开始时间，不只是耗时** —— 否则看不出是串行还是并行。这是很多自建 trace 漏掉的字段。

字段清单展开见 [[04-Agent-工程化评测]] Q15。

## 和竞品比：黑盒能测什么

拿不到对方内部数据，能测的只有 **TTFT** 和 **总时长**。但这两个数已经能推出不少东西：

| 观测 | 推断 |
|---|---|
| 对方 TTFT 极低但总时长差不多 | 他们赢在**流式和交互设计**，不是真快 |
| 对方简单问题快、复杂问题一样慢 | 有**模型分层路由** |
| 对方第二次问同样的问题明显更快 | 有**结果缓存**或语义缓存 |
| 对方一直很稳定 | 可能预热 / 预取 / 推测执行 |

> [!tip] 最容易被忽略的结论
> **体感延迟和总延迟是两回事。**
> 把 TTFT 从 3s 降到 300ms，总时长一点没变，用户会觉得快了十倍。
> 很多"竞品更快"其实是**交互设计赢了**，不是推理更快 —— 先流式吐规划、先显示"正在调用 XX 工具"，等待就不再是空白。
>
> 面试时能指出这一点，比列一堆优化手段更有说服力。

# Q4 · Agent 能否参与性能分析和问题定位？

## 结论

能，投入产出比很高。但要说清角色和边界：

> **Agent 是「跑工具 + 读数据 + 提假设」的分析助手，不是拍板的人。**

在 Agent 语境下，这题最有价值的答法是讲**用 Agent 分析 Agent 系统本身** —— 因为这是最贴题、也最能体现实操的场景。

## 为什么这活特别适合 Agent

性能排查的输入是**大量半结构化数据**（trace、日志、metric 时序），输出是**排好序的假设**。

- 数据量大到人看不动，但结构规整
- 需要跨很多条记录找共性 —— 人容易锚定在自己熟悉的方向
- 枯燥、重复、无创造性

这正好是 LLM 的强项区间。

## 用 Agent 分析 Agent 系统，具体能干什么

| 活 | 具体做法 |
|---|---|
| **找轮数异常的 case** | 扫全部 trace，挑出 turn 数在 p95 以上的，归纳它们的共性（都在调同一个工具？都是同一类输入？） |
| **反查缓存失效** | 找出 `cache_read = 0` 的请求，diff 它们的 prompt 前缀，定位是哪个字段在破坏稳定性 |
| **聚类失败模式** | 把失败 trace 按「模型输出的原文 + 崩溃位置」聚类，输出 Top N 失败模式及样本 |
| **版本对比归因** | 对比两次 eval 的结果，指出哪一类任务退化了、给出具体样本、给出可能原因 |
| **识别绕路模式** | 读 tool call 序列，找出「反复调同一工具」「调了但没用结果」「先查再查同一个东西」这类浪费 |
| **写复现脚本** | 把一个失败 case 变成可重跑的最小复现 |

**最大的价值是覆盖面**：人排查时会不自觉锚定在熟悉的方向，Agent 会老老实实把所有分支都过一遍。

## Agent 分析 Agent 的一个反身陷阱

这点很有意思，也是 Agent 语境独有的：

> [!danger] 别把原始 trace 直接喂给 Agent
> 一次 agent run 的完整 trace 轻松上万行，几百个 trace 就是几百万 token。
> 直接塞进去要么爆窗口，要么信噪比低到模型什么都看不出来。
>
> **正确做法**：先用**脚本**做聚合、采样、降维（按 turn 数分桶、只取失败的、只取字段摘要），
> 再把浓缩后的结果交给 Agent 做语义分析。
>
> 这就是 [[03-Coding-Agent-实践]] Q12 说的 **Select** 和 **Isolate** —— 确定性的过滤交给代码，语义判断才交给模型。

同一条原则的另一个应用：**能写断言的别让模型判**（见 [[04-Agent-工程化评测]] Q17）。

## 边界在哪

| 边界 | 为什么 |
|---|---|
| 业务语义判断 | "这个 agent 本来就该跑 20 轮，它在做全量迁移" —— 数据里看不出来 |
| 历史包袱 | "这个工具拆得细是为了做审计" —— 不在 trace 里 |
| 线上写操作 | 改配置、切流量、回滚 —— 错了代价太大 |
| 最终定性 | 结论要人签字 |

## 工具面设计：能不能落地的关键

Agent 的能力上限由**给它什么工具**决定，不是模型多强。**按可逆性划线**：

**放开（只读）**
- trace / metric / 日志查询
- eval 结果查询
- 读代码、读 prompt、读 skill
- 跑本地分析脚本

**Gate（必须人工确认）**
- 改 prompt / skill / 配置
- 触发线上重跑
- 任何生产写操作

> 这条「按可逆性划线」是设计任何 Agent 工具面的通用原则，
> 在 [[03-Coding-Agent-实践]] 里还会再出现一次。

## 落地形态：SOP 固化成 Skill

最有效的用法不是「你帮我看看为什么慢」，而是把 Q3 那套排查流程写成 Skill，让 Agent 按步骤走：

1. 每一步必须**产出证据**（查询结果、数据、图表），不能只给结论
2. 每一步回报**当前假设 + 已排除了什么**
3. 关键分叉点（比如"确定是轮数问题，准备去看工具设计"）停下来让人确认方向
4. 报告格式固定：现象 → 排查路径 → 证据 → 根因 → 建议 → **未验证项**

> [!tip] 「未验证项」这一栏是精髓
> 它逼 Agent 显式区分「实锤」和「推测」。
> 一份分不清哪些已验证的报告，人还得全部重新核一遍，等于没用。

## 面试怎么答

> 能，而且在体力活上提效很明显 —— 扫 trace 找异常、聚类失败模式、反查缓存失效、对比两个版本哪类任务退化了，这些人做要几小时，Agent 几十分钟。
> 它的角色是助手：提假设、跑查询、整理证据；**业务语义判断和线上写操作要人来兜，结论要人签字**。
> 落地关键不在模型，在两件事：**工具面按可逆性划线**，只读放开、不可逆 gate 住；
> 还有一个 Agent 特有的坑 —— **别把原始 trace 直接喂进去**，几百个 trace 几百万 token，
> 要先用脚本聚合降维再交给模型做语义分析。
