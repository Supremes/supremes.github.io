这份文档只讲面试最常问、线上最常用的主线：索引失效、`EXPLAIN`、MVCC / 锁、慢 SQL、分页、主从复制。

# 一、慢 SQL 排查主线

## 1.1 标准顺序

1. **先定位具体 SQL**
   - 慢日志、APM、`performance_schema`、`sys.statement_analysis`
2. **再看执行计划**
   - `EXPLAIN` / `EXPLAIN ANALYZE`
3. **判断慢在哪里**
   - 扫描行太多
   - 回表太多
   - 排序 / 临时表
   - 锁等待
   - 深分页
4. **最后再改**
   - 索引调整
   - SQL 改写
   - 拆大事务
   - 业务降维（缓存、异步、预聚合）

## 1.2 面试口述模板

> 我会先通过慢日志或监控拿到具体 SQL，再用 `EXPLAIN` 看 `type / key / rows / Extra`。如果是 `ALL`、`Using filesort`、`Using temporary` 或扫描行数远大于返回行数，优先考虑索引设计和 SQL 改写；如果 SQL 本身不差，就继续排查锁等待、大事务和深分页。

# 二、索引为什么会失效

## 2.1 高频失效场景

| 场景 | 为什么容易失效 | 常见改法 |
| --- | --- | --- |
| 联合索引不满足最左前缀 | B+ 树先按最左列有序 | 让查询条件从最左列开始命中 |
| 范围条件后继续依赖右侧列 | 范围后索引有序性被削弱 | 调整联合索引顺序，或把范围列尽量放后 |
| `LIKE '%xxx'` | 左侧模糊无法定位起点 | 改成前缀匹配、倒排、搜索引擎 |
| 对索引列做函数 / 计算 | 优化器没法直接用原始索引值 | 改写条件，必要时加函数索引或冗余列 |
| 隐式类型转换 | 列被转换后难以按原索引匹配 | 保持参数类型一致 |
| `OR` 跨不同列 | 代价过高时优化器可能放弃索引 | 拆成 `UNION ALL` 或补合理索引 |
| `!=` / `NOT IN` / 低选择性条件 | 过滤效果差，优化器可能全扫更便宜 | 结合高选择性列组成联合索引 |

## 2.2 联合索引记忆法

- 最左前缀能用到多少列，取决于**连续命中**到哪里。
- 先等值、后范围，通常更利于复用更多列。
- 不是“建了索引就一定走”，优化器看的是**代价**。

# 三、`EXPLAIN` 速查

## 3.1 重点字段

| 字段 | 重点看什么 |
| --- | --- |
| `type` | 访问类型，是否全表扫描 |
| `possible_keys` | 理论可选索引 |
| `key` | 实际使用索引 |
| `key_len` | 用到了联合索引的多少前缀 |
| `rows` | 预估要扫多少行 |
| `filtered` | 过滤比例 |
| `Extra` | 是否回表前过滤、排序、临时表等 |

## 3.2 `type` 从好到差

`system / const` → `eq_ref` → `ref` → `range` → `index` → `ALL`

- `range`：常见且可接受。
- `index`：全索引扫描，不一定比 `range` 好。
- `ALL`：全表扫描，先重点排查。

## 3.3 `Extra` 高频信号

| Extra | 含义 | 处理方向 |
| --- | --- | --- |
| `Using index` | 覆盖索引 | 通常是好事 |
| `Using index condition` | 索引下推（ICP） | 常见于联合索引过滤 |
| `Using where` | 还要继续做条件过滤 | 结合 `rows` 看是否可接受 |
| `Using filesort` | 不能直接按索引顺序取数 | 考虑索引顺序或改写 SQL |
| `Using temporary` | 用到了临时表 | 常见于 `GROUP BY / ORDER BY` 不匹配 |

# 四、MVCC、快照读与锁

## 4.1 一句话说清 MVCC

MVCC 不是“没有锁”，而是让**普通读尽量不加锁**。核心是：

- 行记录隐藏列（事务 ID、回滚指针）
- `undo log`
- `Read View`

## 4.2 快照读 vs 当前读

| 类型 | 常见语句 | 读到什么 |
| --- | --- | --- |
| 快照读 | 普通 `SELECT` | 事务视图中的历史版本 |
| 当前读 | `SELECT ... FOR UPDATE`、`FOR SHARE`、`UPDATE`、`DELETE` | 当前最新版本，并配合加锁 |

## 4.3 RC 与 RR 的区别

| 隔离级别 | Read View 生成时机 | 典型现象 |
| --- | --- | --- |
| RC（读已提交） | 每条语句一个 Read View | 可能不可重复读 |
| RR（可重复读） | 事务第一次一致性读生成一个 Read View | 普通快照读可重复；当前读靠锁抑制幻读 |

> 面试别说“RR 绝对没有幻读”。更准确的说法是：**InnoDB 在 RR 下，普通一致性读基于快照；加锁读和修改语句通过 next-key lock 抑制幻读。**

## 4.4 行锁要会说这三个

| 锁 | 锁住什么 | 典型用途 |
| --- | --- | --- |
| 记录锁（Record Lock） | 某条记录 | 等值命中索引 |
| 间隙锁（Gap Lock） | 两条记录之间的区间 | 防止区间插入 |
| next-key lock | 记录锁 + 间隙锁 | RR 下当前读常见默认形态 |

## 4.5 为什么会锁等待

- 没走索引，锁范围扩大
- 大事务长时间不提交
- 热点行更新频繁
- DDL 与 DML 冲突，卡在 MDL

# 五、分页为什么会慢

## 5.1 深分页的问题

```sql
SELECT *
FROM orders
ORDER BY id
LIMIT 100000, 20;
```

问题不是只取 20 行，而是**前面 100000 行也要扫描并丢弃**。

## 5.2 两个常用优化方向

### 方案一：延迟关联 / 覆盖索引

先用轻量索引拿主键，再回表取完整列：

```sql
SELECT o.*
FROM orders o
JOIN (
  SELECT id
  FROM orders
  WHERE status = 1
  ORDER BY created_at DESC, id DESC
  LIMIT 100000, 20
) t USING (id);
```

### 方案二：seek / 游标分页（推荐）

基于上页最后一条记录继续查：

```sql
SELECT *
FROM orders
WHERE (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

适用前提：

- 排序字段稳定
- 最好带唯一兜底列（如 `id`）
- 更适合“下一页”，不适合随机跳页

# 六、主从复制与读写一致性

## 6.1 主从复制主线

1. 主库提交事务，写 `binlog`
2. 主库把 `binlog` 推给从库
3. 从库写入 `relay log`
4. 从库回放 `relay log`，把数据应用到本地

## 6.2 面试要主动补一句

默认主从复制大多是**异步**的，所以一定存在：

- **复制延迟**：从库比主库慢
- **丢数据窗口**：主库刚提交、从库还没追上时主库宕机

## 6.3 常见应对手段

| 问题 | 常见方案 |
| --- | --- |
| 写后立刻读，结果不一致 | 写后读主库、会话粘主、延迟读从 |
| 主从切换丢一小段数据 | 半同步复制、合理 `min replicas`、GTID、故障切换策略 |
| 从库追不上 | 降低大事务、优化慢 SQL、提高从库规格、并行复制 |

# 七、面试高频答题模板

## 7.1 “这条 SQL 为什么慢？”

> 我会先拿到具体 SQL 和执行频次，再用 `EXPLAIN` 看是否走了合适索引、扫描行数是否过大、`Extra` 里有没有 `Using filesort / temporary`。如果计划没问题，再排查锁等待、大事务和深分页。

## 7.2 “为什么这个索引没生效？”

> 先看是否破坏了最左前缀，再看有没有函数、计算、隐式类型转换、左模糊匹配或低选择性条件。最后还要考虑优化器是否判断全表扫更便宜。

## 7.3 “主从复制有什么坑？”

> 核心坑是异步复制带来的复制延迟和切主丢数据窗口，所以要看业务对一致性的要求：强一致读主库，读多写少可读从库，关键链路再考虑半同步和故障切换策略。
