# MySQL 架构

## 连接器

- 建立连接、鉴权、维持会话。
- 连接数过多会带来上下文切换和内存压力，因此连接池很重要。

## 分析器

- 词法分析：识别关键字、表名、列名。
- 语法分析：判断 SQL 是否符合语法。

## 优化器

- 选择访问路径：走哪个索引、先扫哪张表、是否能用 ICP / 覆盖索引。
- 本质是在多个执行计划里找成本最低的一种。

## 执行器

- 做权限校验。
- 调用存储引擎接口实际执行。

## 存储引擎

- 最常考的是 InnoDB。
- InnoDB 提供事务、MVCC、行锁、崩溃恢复、聚簇索引。

## 查询缓存

- 老版本有，命中依赖“表没变”。
- **MySQL 8.0 已移除查询缓存**，面试不要再把它当主线能力。

# 日志

详见 [MySQL 日志系统](./mysql-日志.md)。这里先记职责分工：

| 日志 | 所在层 | 作用 |
| --- | --- | --- |
| `redo log` | InnoDB | 崩溃恢复，保证持久性 |
| `binlog` | Server 层 | 主从复制、归档、恢复 |
| `undo log` | InnoDB | 回滚、MVCC 历史版本 |

## 两阶段提交为什么存在

如果只写 `redo log` 不写 `binlog`，主从复制可能丢事务；如果只写 `binlog` 不写 `redo log`，主库宕机恢复后可能少数据。  
所以提交时要把两者串起来，尽量保证主库恢复和复制链路看到的是同一份事务结果。

# 事务与隔离

## ACID 对应到 MySQL

- **A（原子性）**：`undo log`
- **C（一致性）**：依赖 A / I / D 共同保证
- **I（隔离性）**：MVCC + 锁
- **D（持久性）**：`redo log`

## 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交（RU） | 可能 | 可能 | 可能 |
| 读已提交（RC） | 不会 | 可能 | 可能 |
| 可重复读（RR） | 不会 | 不会 | 普通快照读稳定；当前读依赖锁抑制 |
| 串行化（Serializable） | 不会 | 不会 | 不会 |

## 常见并发现象

### 脏读

读到了别的事务尚未提交的数据。

### 不可重复读

同一事务里两次读同一行，结果不同。

### 幻读

同一事务里按条件两次查范围，结果集“多了/少了”几行，通常与插入删除有关。

# MVCC

## MVCC 是什么

MVCC（Multi-Version Concurrency Control，多版本并发控制）让普通读尽量不和写互斥。

它依赖三样东西：

1. 行记录隐藏列（事务 ID、回滚指针）
2. `undo log`
3. `Read View`

## 快照读

- 普通 `SELECT` 默认就是快照读。
- 读到的是某个一致性视图中的版本，而不是“此刻最新值”。

## 当前读

以下语句属于当前读：

- `SELECT ... FOR UPDATE`
- `SELECT ... FOR SHARE`
- `UPDATE`
- `DELETE`
- `INSERT`

当前读会读取最新版本，并在需要时加锁。

## RC 和 RR 的核心区别

### RC（读已提交）

- 每条语句生成一个新的 `Read View`。
- 所以同一事务里，两次普通查询也可能看到不同结果。

### RR（可重复读）

- 事务第一次一致性读时生成 `Read View`，后续普通查询复用。
- 因此普通快照读能保持可重复。
- 但如果是当前读，就要靠记录锁 / 间隙锁 / next-key lock 去抑制幻读。

# 索引

## 为什么 InnoDB 常用 B+ 树

- 非叶子节点只存键值和指针，单页能放更多索引项。
- 叶子节点天然有序，适合范围查询。
- 磁盘 I/O 次数少，适合数据库页式存储。

## 聚簇索引 vs 二级索引

### 聚簇索引（主键索引）

- 叶子节点存整行数据。
- 一张 InnoDB 表只能有一个聚簇索引。

### 二级索引

- 叶子节点存主键值。
- 通过二级索引找到主键后，再回聚簇索引取整行，这就是**回表**。

## 覆盖索引

如果查询列都在二级索引里，直接返回，不必回表。

## 联合索引

联合索引本质上按“从左到右”的列顺序组织。

### 最左前缀

例如索引 `(a, b, c)`：

- `a`
- `a, b`
- `a, b, c`

都能高效利用；但 `b`、`b, c` 单独通常不行。

### 范围条件的影响

联合索引里，一旦在某列上进入范围匹配，后续列通常不能继续参与精确定位，只能在部分场景继续用于排序或过滤。

## 索引下推（ICP）

存储引擎在遍历索引时，先用能下推的条件做过滤，减少回表次数。  
它不改变结果，只是在**更早的阶段过滤掉不必要的记录**。

## 页分裂与页合并

- **页分裂**：插入位置在中间且页满了，需要拆页，容易导致碎片和写放大。
- **页合并**：删除后空间过空，可能触发页合并。

这也是为什么主键最好尽量单调递增：减少随机插入带来的页分裂。

# 锁

## 全局锁

`FLUSH TABLES WITH READ LOCK`

- 常用于一致性备份。
- 会阻塞整个实例的写。

## 表锁

`LOCK TABLES ... READ/WRITE`

- 粒度大，简单但并发能力差。

## 元数据锁（MDL）

- DML 会拿 MDL 读锁。
- DDL 会拿 MDL 写锁。
- 所以长事务可能把 DDL 卡很久。

## 行锁

InnoDB 的行锁建立在**索引**上。  
如果没走索引，常常会退化为更大范围的锁。

### 记录锁（Record Lock）

锁住某条已存在记录。

### 间隙锁（Gap Lock）

锁住两条记录之间的“空隙”，防止别人往这个区间插入。

### next-key lock

记录锁 + 间隙锁。  
这是 RR 下当前读很常见的默认行为，用来抑制幻读。

### 插入意向锁

插入前先声明“我要插这个区间”，便于多个插入并发协调。

## 死锁

### 为什么会发生

- 事务拿锁顺序不一致
- 热点行更新
- 范围更新锁住了交叉区间

### 常见处理

- 尽量按固定顺序访问资源
- 小事务、快提交
- 精准命中索引，缩小锁范围
- 必要时关闭热点上的过度并发

# 术语速记

- **脏页**：内存已改、磁盘未落盘的数据页。
- **回表**：二级索引命中后，再回主键索引取整行。
- **覆盖索引**：查询列都在索引里，不用回表。
- **Read View**：事务做一致性读时看到的“可见版本边界”。

# 面试收口

如果只能用一句话把 MySQL 讲清楚：

> MySQL 高频题基本都能落到三件事：**执行计划是否高效、版本并发控制是否正确、日志与复制链路是否可靠**。
