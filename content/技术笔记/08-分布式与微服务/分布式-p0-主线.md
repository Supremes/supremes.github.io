# 分布式 P0 主线

> 先回答“单机为什么不够”，再回答“多节点后丢了什么”，最后讲“如何把一致性、可用性、治理能力补回来”。

## 1. CAP 与 BASE

### CAP

- **C（一致性）**：同一时刻所有节点看到同样的数据。
- **A（可用性）**：每次请求都能拿到响应，但不保证是最新数据。
- **P（分区容错）**：网络分区时系统仍要继续工作。

面试里最容易答偏的一点：**CAP 只在网络分区发生时才真正有取舍意义**。分布式系统里 P 基本躲不掉，所以通常是在 **C 和 A 之间按场景取舍**。

- **CP**：优先一致性，常见于注册中心、元数据管理、强约束配置。
- **AP**：优先可用性，常见于缓存、推荐、读多写少且允许短暂不一致的场景。

### BASE

- **Basically Available**：基本可用
- **Soft State**：软状态
- **Eventually Consistent**：最终一致

一句话：**BASE 不是不要一致性，而是接受“强一致太贵”时的工程化妥协。**

## 2. 一致性与幂等

### 一致性

- **强一致**：写成功后立刻读到最新值。
- **最终一致**：允许短暂延迟，最终收敛。
- **读写一致性常见补法**：
  - 版本号 / CAS / 乐观锁
  - 重试 + 去重
  - 延迟双删、消息通知、异步对账
  - 主写从读场景下的读路由控制

### 幂等

幂等要解决的是：**同一个请求重放多次，只产生一次业务效果。**

常见落地：

- 请求唯一 ID
- 唯一索引 / 去重表
- 状态机流转校验
- MQ 消费去重
- 下游接口幂等 token

不要把幂等和分布式锁混为一谈：**幂等解决“重复执行”，锁解决“并发竞争”**。分布式锁单独见 [Redis 分布式锁实战](../06-Redis/redis分布式锁.md)。

## 3. 分布式事务：常见方案与取舍

| 方案 | 一致性 | 侵入性 | 优点 | 代价 / 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 强一致 | 高 | 理论简单 | 同步阻塞、协调者单点、性能差，互联网业务少用 |
| TCC | 最终一致 | 很高 | 业务可控，补偿清晰 | 要自己写 Try / Confirm / Cancel，研发成本高 |
| Saga | 最终一致 | 中 | 适合长链路流程 | 需要补偿逻辑，过程中可能短暂不一致 |
| 本地消息表 / Outbox | 最终一致 | 中 | 落地最常见 | 需要投递、重试、对账 |
| 最大努力通知 | 最终一致 | 低 | 简单实用 | 适合可补偿、允许延迟的通知型流程 |

面试建议的结论顺序：

1. **能不用分布式事务就不用**，优先拆成最终一致。
2. **能异步就异步**，优先 Outbox / MQ。
3. 只有确实需要业务补偿编排时，再考虑 **TCC / Saga**。

## 4. 服务发现

微服务一旦拆开，调用方首先要知道“目标服务现在在哪”。

- **注册中心职责**：注册实例、健康检查、摘除故障节点、提供查询
- **客户端发现**：消费者自己拉取实例列表并做负载均衡
- **服务端发现**：由网关 / 代理统一转发

常见机制：

- 心跳续约
- 健康检查
- 上下线通知
- 临时节点 / 租约模型

## 5. 负载均衡

负载均衡本质上是：**把请求稳定地送到健康节点上，并尽量让整体吞吐和延迟更优。**

常见策略：

- 轮询
- 加权轮询
- 最少连接
- 一致性哈希
- 就近路由

常见分法：

- **L4**：按 IP + 端口转发，性能高
- **L7**：按 HTTP 路径、Header、Cookie 转发，策略更灵活
- **客户端负载均衡**：如 Spring Cloud LoadBalancer
- **服务端负载均衡**：如 Nginx、Envoy

## 6. 限流

限流是为了避免系统被突发流量或异常请求打垮。

常见算法：

- 固定窗口：简单，但容易临界突刺
- 滑动窗口：更平滑
- 令牌桶：最常用，允许一定突发
- 漏桶：输出速率稳定

常见落点：

- 网关限流
- 服务级限流
- 下游依赖保护
- 用户 / 租户 / 接口维度限流

## 7. 熔断、降级、隔离

- **重试**：解决偶发失败，但会放大雪崩，不能乱用
- **熔断**：失败率或超时达到阈值时，直接快速失败
- **降级**：返回兜底值、缓存值、静态页、稍旧数据
- **隔离**：线程池隔离、信号量隔离，避免故障扩散

面试一句话：**限流是入口挡流量，熔断是下游坏了先断开，隔离是把风险关在小房间里。**

## 8. 配置中心

配置中心解决的是：**配置不能跟着实例散落、改配置不能重启一大片。**

关注点：

- 配置集中管理
- 环境隔离
- 动态刷新
- 灰度发布
- 版本回滚
- 审计与权限控制

## 9. 分布式 ID

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| UUID | 简单、无中心 | 太长、无序、索引不友好 |
| 数据库自增 / sequence | 单调递增，易懂 | 有中心依赖，扩展性一般 |
| 号段模式 | 吞吐高，常见于业务系统 | 要维护发号服务 |
| Snowflake | 趋势递增，性能好 | 依赖机器号和时钟，时钟回拨要处理 |

面试高频追问：**为什么很多库不喜欢 UUID 做主键？**  
答：因为随机、长、离散，会让索引和页分裂成本更高。

## 10. 复习时的最短主线

可以按下面顺序串起来：

1. 单机扛不住，于是拆成分布式。
2. 一拆就遇到网络分区，所以有 CAP。
3. 为了可用性，很多业务接受最终一致，也就是 BASE。
4. 节点变多后，要补幂等、事务、服务发现、负载均衡。
5. 流量再变大，就要限流、熔断、隔离、配置中心和分布式 ID。
