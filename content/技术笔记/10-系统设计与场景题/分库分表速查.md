# 分库分表速查

> 核心目标：把单库单表的容量和吞吐压力分散到多个节点；代价是查询、事务、扩容和运维复杂度上升。

## 30 秒口述

分库分表不是数据量大就立刻拆，而是单库单表经过索引、SQL、缓存、读写分离和归档优化后，仍无法满足容量或吞吐目标时才考虑。设计时先确定业务边界和分片键，再选择取模、范围或路由表等算法。真正困难的不是把数据写散，而是跨分片查询、分页、事务、全局 ID、扩容迁移和热点治理。

## 什么时候需要拆

不要用固定行数作为唯一标准，应以压测和线上指标判断。

### 常见信号

- 单表索引过大，查询延迟持续超出 SLO。
- 单库连接数、CPU、I/O 或写入吞吐接近瓶颈。
- 数据增长速度超过单机容量规划。
- 大表 DDL、备份、恢复和迁移窗口无法接受。
- 不同业务模块互相争抢数据库资源，需要故障隔离。

### 拆之前先做

1. 修正索引和慢 SQL。
2. 冷热数据分离、历史数据归档。
3. 缓存高频读，削减无效访问。
4. 读多写少时考虑主从复制和读写分离。
5. 大字段、搜索、分析任务迁到更合适的存储。

> 能通过单库优化解决的问题，不要提前引入分片复杂度。

## 四种拆分方式

| 方式 | 怎么拆 | 主要收益 | 典型代价 |
| --- | --- | --- | --- |
| 垂直分库 | 按业务域拆库，如用户库、订单库 | 隔离业务和故障 | 跨库事务、跨域关联 |
| 垂直分表 | 把大字段或低频字段拆到扩展表 | 减小行宽，提高热点查询效率 | 多一次查询或关联 |
| 水平分库 | 同一张逻辑表按规则分到多个库 | 分散连接和写入压力 | 路由、事务、扩容复杂 |
| 水平分表 | 同一张逻辑表拆成多张物理表 | 控制单表数据量和索引高度 | 聚合、分页、运维复杂 |

面试中说“分库分表”通常重点指**水平分片**。

## 分片键怎么选

分片键决定数据分布和大部分查询能否单路由。

### 选择原则

- 高频查询条件中稳定存在。
- 基数高、分布均匀，避免热点。
- 创建后尽量不变，否则需要跨分片搬迁。
- 能让相关数据尽量落在同一分片。
- 符合数据隔离边界，如 `user_id`、`tenant_id`、`order_id`。

### 常见取舍

| 分片键 | 优点 | 风险 |
| --- | --- | --- |
| `user_id` | 用户维度查询和订单列表容易单路由 | 商家维度查询可能跨片 |
| `tenant_id` | 天然租户隔离 | 大租户可能形成热点 |
| `order_id` | 单订单查询稳定、分布容易均匀 | 查用户全部订单可能跨片 |
| 时间 | 归档、按时间范围查询方便 | 最新时间段形成写热点 |

> 没有同时满足所有查询的分片键。先确定核心访问路径，次要路径通过索引表、搜索系统、数据仓库或冗余视图解决。

## 路由算法

| 算法 | 路由方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 取模 / 哈希 | `hash(key) % N` | 简单、分布通常均匀 | 扩容时大量数据重映射 |
| 范围 | 按 ID 或时间区间 | 范围查询、归档方便 | 容易产生热点和数据倾斜 |
| 一致性哈希 | key 落到哈希环节点 | 扩容迁移量较小 | 实现和均衡治理更复杂 |
| 路由表 | 单独记录 key 到分片映射 | 路由灵活、可定向迁移 | 多一次查询，路由表要高可用 |
| 地理 / 租户 | 按地区、租户固定路由 | 隔离和合规清晰 | 大区或大租户不均衡 |

### 数量规划

- 分片数不要只按当前数据量计算，要预留增长空间。
- 物理库数量和逻辑分片数量可以分离：先多设逻辑分片，再映射到较少物理节点。
- 避免把表数量写死在业务代码里，统一交给路由层管理。

## 拆分后最难的七件事

### 1. 跨分片查询

- 带分片键：直接路由到一个分片。
- 不带分片键：广播查询后归并，成本随分片数增长。
- 高频非分片键查询：建立映射表、冗余索引或使用 Elasticsearch。

### 2. 跨库 Join

- 优先调整领域边界，避免在线跨库 Join。
- 冗余少量稳定字段，使用本地 Join。
- 先查主数据 ID，再批量查其他分片并在服务层组装。
- 分析型关联交给离线数仓，不放在核心交易链路。

### 3. 排序与分页

每个分片先取候选集，路由层再做归并排序。深分页需要从各分片读取大量数据，代价很高。

优先方案：

- 使用游标 / seek 分页。
- 排序字段带唯一兜底列，如 `(created_at, id)`。
- 限制随机跳页。
- 复杂检索使用独立搜索索引。

### 4. 聚合统计

- 分片内先聚合，再汇总。
- 高频指标做预计算或异步汇总。
- 大规模报表进入 OLAP / 数仓。

### 5. 分布式事务

单分片事务仍由本地数据库保证；跨分片后不能再默认依赖单库 ACID。

优先顺序：

1. 通过分片键和业务边界让事务落在同一分片。
2. 使用本地事务 + Outbox / MQ 实现最终一致。
3. 需要补偿流程时考虑 Saga / TCC。
4. 强一致场景才评估 XA，并接受性能与可用性代价。

### 6. 全局唯一 ID

不能继续依赖每张分表各自的自增主键。

常见方案：

- Snowflake：吞吐高、趋势递增；要处理机器号和时钟回拨。
- 号段模式：批量申请 ID，数据库压力小；依赖发号服务。
- UUID：无中心，但随机且较长，对 B+ 树主键不友好。

### 7. 热点与数据倾斜

- 监控各分片数据量、QPS、延迟和热点 key。
- 对大租户使用二级分片或独立分片。
- 热点读加缓存，热点写拆桶或异步聚合。
- 不要把“平均分布”误当作“流量均匀”。

## 扩容与迁移

取模分片从 `N` 扩成 `2N` 会改变大量 key 的路由，不能直接改配置上线。

### 安全迁移主线

1. **确定新旧路由规则**：记录版本，支持灰度和回滚。
2. **迁移存量数据**：离线回填或在线复制。
3. **同步增量变更**：优先 CDC / binlog；谨慎使用业务双写。
4. **校验数据**：数量、校验和、抽样和业务对账。
5. **灰度切读**：先少量读取新分片，持续比对结果。
6. **切换写入**：确认新链路稳定后再切主写。
7. **观察与回滚窗口**：保留旧数据，稳定后再下线。

> 业务双写存在部分成功问题，不能只靠 `try/catch` 保证一致；应有重试、对账和补偿机制。

## ShardingSphere 解决什么

| 形态 | 说明 | 适合场景 |
| --- | --- | --- |
| ShardingSphere-JDBC | 应用内嵌路由和改写能力 | Java 应用、性能优先、可接受 SDK 耦合 |
| ShardingSphere-Proxy | 独立代理，对应用表现为数据库 | 多语言接入、统一治理 |

常见能力：

- SQL 解析、路由、改写、执行和结果归并。
- 分片规则、绑定表、广播表。
- 分布式主键。
- 读写分离、影子库等治理能力。

它不能消除分布式系统的客观代价：跨片事务、广播查询、深分页和扩容迁移仍需业务设计。

## 高频追问

### 分区表等于分库分表吗

不等于。MySQL 分区表仍由一个数据库实例管理，主要改善数据组织和分区裁剪；它不能突破单实例的 CPU、连接数和故障域上限。

### 为什么不能按手机号取模

手机号可能变化、涉及隐私，而且业务查询不一定总带手机号。分片键应稳定、分布均匀并匹配核心查询。

### 分片键选错后怎么办

短期通过映射表、冗余索引补查询；长期需要设计新路由、迁移存量、同步增量并灰度切换，不能直接在线改算法。

### 如何避免跨库事务

让同一聚合的数据按相同分片键落在同一分片；跨领域操作改成事件驱动和最终一致，配合幂等、重试、对账和补偿。

### 分库分表后怎么查全局数据

交易链路尽量单路由；运营搜索使用冗余索引或 Elasticsearch；统计分析走汇总表、OLAP 或数仓，避免在线广播扫全库。

## 面试回答模板

1. **先说瓶颈**：容量、写吞吐、连接数还是隔离问题。
2. **说明前置优化**：索引、缓存、归档、读写分离是否已经做过。
3. **给出拆法**：垂直还是水平，为什么。
4. **确定分片键和路由**：核心查询如何单路由，数据是否均匀。
5. **补齐代价**：跨片查询、事务、分页、ID、扩容。
6. **说明迁移与兜底**：回填、增量同步、校验、灰度、回滚。

## 速查 Checklist

- [ ] 是否真的需要拆，而不是 SQL 或索引问题？
- [ ] 核心查询是否都带分片键？
- [ ] 是否存在大租户、热点 key 或时间热点？
- [ ] 跨片查询、分页、聚合如何处理？
- [ ] 事务能否收敛到单分片？
- [ ] 全局 ID 如何生成？
- [ ] 扩容时如何迁移、校验和回滚？
- [ ] 是否具备分片级监控、对账和故障隔离？
