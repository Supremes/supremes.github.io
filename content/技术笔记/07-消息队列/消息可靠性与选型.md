一句话先背：**消息可靠性 = 生产端确认 + Broker 持久化 / 副本 + 消费端确认 + 业务幂等。**

# 一、先分清交付语义

| 语义 | 含义 | 代价 |
| --- | --- | --- |
| At Most Once | 最多一次，可能丢，但不重复 | 最简单，可靠性最低 |
| At Least Once | 至少一次，不丢，但可能重复 | 业务必须幂等 |
| Exactly Once | 理论上不丢不重 | 成本高，且通常只在特定边界内成立 |

> 面试里不要把 “Exactly Once” 讲成银弹。跨 MQ、数据库、缓存的全链路精确一次，最终还是要回到**幂等设计**。

# 二、消息为什么会丢

## 2.1 生产者侧

常见丢失原因：

- 发送超时后应用没重试
- RabbitMQ 没开 `publisher confirm`
- Kafka `acks` 太低，只拿到 Leader 本地确认

常见做法：

- **RabbitMQ**：开启 `publisher confirm`
- **Kafka**：`acks=all`、合理重试、`enable.idempotence=true`

## 2.2 Broker 侧

常见丢失原因：

- 队列 / 主题不持久
- 单副本
- 主从切换时副本没追上
- 允许不安全选主

常见做法：

| 组件 | 关键做法 |
| --- | --- |
| Kafka | 副本因子 >= 3、`min.insync.replicas`、`unclean.leader.election.enable=false` |
| RabbitMQ | durable queue、persistent message、新项目优先 quorum queue |

## 2.3 消费者侧

常见丢失原因：

- 业务还没处理完就先 ACK / 提交 offset
- 消费线程异常退出但外部状态没落地

正确思路：

1. 先执行业务
2. 业务成功后再 ACK / commit
3. 失败则重试或进死信

# 三、为什么一定会有重复消息

只要你追求的是 **at-least-once**，重复就是正常现象：

- 生产端重试可能重复发
- 消费端处理成功但 ACK 丢了
- Rebalance 后分区被别人接管重放
- Broker 认为超时，触发重投

## 3.1 幂等怎么做

### 业务主键幂等

- 订单号
- 支付流水号
- 业务事件 ID

### 数据层幂等

- 唯一索引
- 去重表
- 状态机校验（只有 `INIT -> SUCCESS` 能转）

### 消费层幂等

- 先查是否处理过
- 再执行业务
- 成功后记录处理结果

> 面试一句话：**MQ 负责尽量不丢，幂等负责兜底去重。**

# 四、顺序怎么保证

## 4.1 顺序的边界

绝大多数 MQ 只能保证：

- **单个队列内有序**
- 或 **单个分区内有序**

不能天然保证“全局严格有序”。

## 4.2 Kafka 的顺序

- 同一个业务 key 打到同一个 partition
- 同一个 partition 内顺序消费
- 如果为了提吞吐把同一 partition 并发处理，顺序就会被你自己打破

## 4.3 RabbitMQ 的顺序

- 单队列天然 FIFO
- 但多消费者并行、失败重回队列、优先级等都会破坏“业务完成顺序”

## 4.4 面试建议

> 先追问“你要的是全局顺序，还是同一订单 / 同一用户维度的局部顺序？”  
大多数业务只需要**按业务 key 保序**。

# 五、积压怎么处理

## 5.1 先找原因，不要先喊扩容

常见原因：

- 下游服务慢
- 消费逻辑太重
- 热点分区 / 热点队列
- Rebalance 频繁
- 单次拉取太小，吞吐上不去

## 5.2 观察指标

| 组件 | 重点指标 |
| --- | --- |
| Kafka | consumer lag、每分区 lag、消费速率、Rebalance 次数 |
| RabbitMQ | ready、unacked、ack rate、queue depth |

## 5.3 常见处理手段

| 场景 | 处理思路 |
| --- | --- |
| 消费逻辑重 | 异步化、批处理、把慢 RPC 拆出去 |
| Kafka 热点分区 | 调整 key 分布、增加分区前先评估顺序影响 |
| RabbitMQ 队列堆积 | 增消费者、调 `prefetch`、拆队列 |
| 下游服务不稳 | 限流、降级、隔离重试流量 |

# 六、重试、死信、延迟重试

## 6.1 不要无限原地重试

无限重试的后果：

- 队列被坏消息堵住
- 重试风暴
- 下游雪上加霜

## 6.2 正确分流

| 失败类型 | 处理方式 |
| --- | --- |
| 短暂失败（网络抖动、下游超时） | 有上限的重试，最好指数退避 |
| 业务永久失败（参数错、状态错） | 直接进死信，人工或离线处理 |

## 6.3 死信队列的作用

- 留痕
- 隔离坏消息
- 支持人工补偿

> 死信队列不是“失败就扔垃圾桶”，而是**把异常消息从主链路摘出去**。

# 七、Kafka Rebalance 为什么总被问

## 7.1 触发场景

- 消费者加入 / 退出
- 消费者长时间没心跳
- `max.poll.interval.ms` 超时
- 分区数变化

## 7.2 影响

- 分区会重新分配
- 这段时间吞吐抖动
- 如果 offset 提交时机不对，容易重复消费

## 7.3 如何降低影响

- 处理线程别长时间阻塞 `poll`
- 业务成功后再提交 offset
- 尽量减少无意义的消费者抖动
- 使用更平滑的分配策略（如 cooperative sticky 思路）
- 长任务拆给异步线程池，但提交点要和结果一致

# 八、Kafka vs RabbitMQ 怎么选

| 维度 | Kafka | RabbitMQ |
| --- | --- | --- |
| 核心定位 | 高吞吐事件流 / 日志流 | 低延迟业务消息 / 复杂路由 |
| 吞吐 | 很高 | 中高，但通常低于 Kafka |
| 路由能力 | 相对简单 | Exchange 路由更灵活 |
| 消费模型 | 分区 + Consumer Group | Queue + ACK + Binding |
| 重试 / 死信 | 需要业务或中间层设计 | 机制更直观 |
| 顺序语义 | 分区内顺序 | 队列内顺序 |
| 积压处理 | 更擅长长时间、大规模积压 | 适合业务消息，不擅长超长海量堆积 |
| 典型场景 | 埋点、日志、事件总线、流处理 | 订单、通知、任务分发、业务解耦 |

## 8.1 一句话选型

- **需要高吞吐、可回放、事件流**：偏 Kafka
- **需要复杂路由、业务重试、死信治理方便**：偏 RabbitMQ

# 九、面试口述模板

## 9.1 “怎么保证消息不丢？”

> 我会拆成三段看：生产者是否确认成功、Broker 是否持久化并有足够副本、消费者是否在业务成功后再 ACK / 提交 offset。最后用业务幂等兜底重复问题。

## 9.2 “为什么会重复消费？”

> 因为大多数系统追求的是 at-least-once。只要有重试、超时、ACK 丢失、Rebalance，就可能重放，所以消费者必须幂等。

## 9.3 “Kafka 和 RabbitMQ 怎么选？”

> 看核心诉求。如果是事件流、吞吐、回放、长时间积压，优先 Kafka；如果是业务消息、路由、重试、死信治理体验，优先 RabbitMQ。
