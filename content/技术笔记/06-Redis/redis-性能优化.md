# 一、先用排障主线看问题

## 1.1 常见症状

| 症状 | 优先怀疑 |
| --- | --- |
| QPS 掉、响应变慢 | 慢命令、网络 RTT、CPU 打满 |
| 周期性抖动 | `fork`、AOF 重写、RDB、内存碎片 |
| 个别接口雪崩 | hotkey、缓存失效、下游慢 |
| 单次命令卡顿 | bigkey、Lua 太重、批量删除 |
| 节点内存高 | bigkey、过期策略不合理、淘汰策略不匹配 |

## 1.2 排查顺序

1. **看整体**
   - `INFO`
   - CPU、内存、网络、连接数
2. **看命令**
   - `SLOWLOG GET`
   - `INFO commandstats`
3. **看 key**
   - bigkey / hotkey
4. **看持久化**
   - RDB / AOF 是否在抖
5. **看业务模式**
   - 是否一次取太大对象
   - 是否把 Redis 当数据库全量扫

# 二、bigkey 与 hotkey

## 2.1 bigkey 为什么危险

- 单次读写网络包大
- 删除和迁移成本高
- 编码转换和序列化更重
- 容易拖慢主线程

## 2.2 hotkey 为什么危险

- 单点流量集中
- 容易把单个分片、单个 CPU 核打满
- 下游数据库在失效瞬间也可能被打爆

## 2.3 常见处理

| 问题 | 处理思路 |
| --- | --- |
| bigkey | 拆分 key、缩字段、分片存储、避免整对象频繁读写 |
| hotkey | 本地缓存、多副本分摊、逻辑过期、限流降级 |

## 2.4 常见观察手段

```bash
redis-cli --bigkeys
MEMORY USAGE some:key
```

> 线上不要把“查全部 key”当常规动作，优先抽样、监控、热点统计。

# 三、慢命令比“慢查询”更关键

Redis 没有关系型数据库那种复杂执行计划，很多慢问题本质是：

- 单条命令处理数据太大
- Lua 脚本做了过重逻辑
- 全量扫描、排序、聚合
- 网络往返次数太多

## 3.1 高频慢命令来源

- `KEYS *`
- 大范围 `SMEMBERS` / `LRANGE`
- 大对象上的 `HGETALL`
- 一次返回超大 `ZRANGE`
- 大事务 / 大 Lua

## 3.2 处理原则

- 避免全量读
- 尽量分页
- 能按需字段取，就别整对象全取
- 能批量发，就别高 RTT 单条循环发

## 3.3 Pipeline 适合什么

Pipeline 解决的是**网络 RTT 高**，不是命令本身重。

适合：

- 多次独立小命令批量发送

不适合：

- 单条命令本身就很重
- 需要强原子性的场景

# 四、内存与淘汰策略

## 4.1 常见误区

- 把 Redis 当无限内存
- 只会背 `allkeys-lru`，却不知道业务是不是允许淘汰
- 过期时间设置过于集中，造成同一时刻大批失效

## 4.2 选策略时先问三个问题

1. **是不是所有 key 都允许淘汰？**
2. **是不是只有带 TTL 的 key 才能淘汰？**
3. **业务更怕写失败，还是更怕误淘汰？**

## 4.3 常见策略

| 策略 | 适用理解 |
| --- | --- |
| `noeviction` | 不允许淘汰，写入直接失败 |
| `allkeys-lru` | 通用缓存场景常见默认答案 |
| `volatile-lru` | 只有带过期时间的 key 才参与淘汰 |
| `volatile-ttl` | 更偏短期数据 |

# 五、持久化为什么会带来抖动

## 5.1 两个高频来源

### `fork`

无论 RDB 还是 AOF 重写，都可能触发 `fork`。  
数据集大时，`fork` 本身就可能带来抖动。

### COW（Copy-On-Write）

后台子进程落盘期间，如果主线程继续大量写，会复制很多内存页，导致：

- 内存瞬时升高
- 延迟抖动

## 5.2 你在面试里要主动补的一句

> Redis 的抖动不一定来自命令本身，也可能来自持久化阶段的 `fork + COW`。

# 六、实践侧优化清单

## 6.1 读写模型

- 热点数据尽量短 key、轻 value
- 少做全量扫描
- 减少大对象 JSON 反复序列化

## 6.2 命令层

- 批量独立命令用 Pipeline
- 高成本操作拆小
- 删除大 key 时避免同步暴力删除

## 6.3 架构层

- 缓存层做多级缓存
- 热点数据预热
- 分片均衡，避免单分片过热

# 七、面试高频答法

## 7.1 “Redis 线上为什么会突然卡一下？”

先看是不是慢命令，其次看是不是 bigkey / hotkey，再看是不是 RDB 或 AOF 重写触发的 `fork + COW` 抖动。

## 7.2 “怎么发现性能瓶颈？”

先看 `INFO` 和资源监控，再看 `SLOWLOG`、`commandstats`，然后定位 key 模型是不是有 bigkey / hotkey。

## 7.3 “Pipeline 能提升什么？”

它主要减少网络往返次数，适合很多轻量独立命令一起发；如果命令本身很重，Pipeline 也救不了。
