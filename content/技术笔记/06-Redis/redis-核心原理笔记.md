# 一、渐进式 rehash 怎么讲

## 1.1 为什么不是一次性 rehash

如果哈希表里已经有几十万甚至几百万个 key，一次性搬迁会把主线程卡住，造成明显抖动。

## 1.2 渐进式 rehash 的核心逻辑

1. Redis 同时维护旧表和新表。
2. 每次增删改查时，顺手迁一点桶。
3. 查询期间可能要先查旧表，再查新表。
4. 新写入优先进入新表，避免旧表边搬边长。

> 面试一句话：**把一次大停顿拆成很多次小成本，分摊到后续请求里。**

# 二、Cluster 的 Hash Slot 与 Hash Tag

## 2.1 为什么是 16384 个槽

- 方便做数据分片和迁移。
- 客户端先算 `CRC16(key) % 16384`，再找到对应节点。

## 2.2 Hash Tag 什么时候用

多 key 操作必须落在同一槽位，否则 Cluster 无法原子执行。

```text
{user:1001}:profile
{user:1001}:balance
```

上面两把 key 会因为 `{user:1001}` 这个 Hash Tag 被算到同一槽位。

# 三、Redis 事务到底保证什么

## 3.1 `MULTI / EXEC`

- 保证命令按顺序串行执行。
- **不保证传统数据库意义上的回滚。**
- 如果是运行期某条命令报错，前面成功的命令不会自动撤销。

## 3.2 `WATCH`

- 本质是乐观锁。
- 在提交前发现 key 被别人改过，就放弃执行事务。

## 3.3 Lua 脚本

- 在 Redis 内部原子执行。
- 比手写多条命令更适合做扣减、校验删除锁、限流等场景。

> 面试里如果被问“Redis 事务为什么不如数据库事务强”，核心就答：**它重点解决原子执行，不解决复杂回滚和隔离级别问题。**

# 四、bigkey / hotkey 的本质

## 4.1 bigkey

单个 key 数据量太大，问题通常出在：

- 网络包大
- 删除阻塞
- 迁移慢
- 序列化 / 反序列化重

常见处理：

- 拆 key
- 改数据结构
- 过期淘汰
- 对删除使用异步思路（如惰性删除能力）

## 4.2 hotkey

不是大，而是**访问过于集中**。

常见处理：

- 本地缓存兜底
- 多副本分摊热点
- 限流 / 降级
- 拆读路径

# 五、哪些事别让 Redis 硬扛

- **强一致分布式锁**：优先考虑 Zookeeper / etcd。
- **核心业务消息主链路**：需要高可靠、复杂路由、积压治理时，优先专用 MQ。
- **超大对象聚合存储**：会放大 bigkey 问题。
