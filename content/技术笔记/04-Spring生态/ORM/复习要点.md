## 一句话结论

Hibernate 是管理实体生命周期和关联关系的全功能 ORM 框架；MyBatis 是以 SQL 为中心的映射框架，MyBatis-Plus 则在 MyBatis 之上补充通用 CRUD 和条件构造能力。选型关键不是谁更高级，而是项目更重视领域模型还是 SQL 控制力。

## 30 秒口述

JPA 是 ORM 规范，Hibernate 是其主流实现，并提供 HQL、缓存等扩展能力；Spring Data JPA 又在 JPA 之上提供 Repository 抽象。MyBatis 不属于 JPA 体系，它要求开发者显式控制 SQL，再把参数和结果映射为 Java 对象；MyBatis-Plus 进一步减少单表 CRUD 的样板代码。Hibernate 适合关联关系较多、以领域模型为中心的业务，MyBatis 更适合复杂 SQL、报表和需要精细控制执行计划的场景。

## 概念层级

| 名称 | 定位 | 关键能力 |
| --- | --- | --- |
| JPA / Jakarta Persistence | Java ORM 规范 | 定义 `EntityManager`、实体映射和 JPQL 等标准 API |
| Hibernate | ORM 框架、JPA Provider | 实现 JPA，并提供 HQL、二级缓存等扩展 |
| Spring Data JPA | JPA 之上的 Repository 抽象 | 自动生成常见 CRUD、分页和派生查询 |
| MyBatis | SQL 映射框架 | 管理 SQL、参数绑定以及结果映射 |
| MyBatis-Plus | MyBatis 增强工具 | 提供 `BaseMapper`、Wrapper、分页和插件机制 |

## Hibernate 核心机制

- **对象关系映射**：通过注解或 XML 建立实体、属性、关联关系与数据库表之间的映射。
- **持久化上下文**：`EntityManager` / `Session` 跟踪托管实体，一级缓存也位于其中。
- **脏检查与 `flush`**：托管实体发生变化后，Hibernate 会在刷新持久化上下文时生成对应 SQL；`flush` 不等于事务已经提交。
- **关联与抓取策略**：支持 `@OneToMany`、`@ManyToOne` 等关联映射，以及 `LAZY`、`EAGER` 抓取策略。
- **查询方式**：JPQL 是 JPA 标准查询语言；HQL 是 Hibernate 的查询语言和 JPQL 超集。动态查询还可使用 Criteria API，确有数据库特有能力或性能需求时再使用原生 SQL。
- **缓存**：一级缓存默认存在，作用域是当前持久化上下文；二级缓存需要显式配置，可在多个会话之间共享实体数据。

### Hibernate / JPA 的 Spring Boot 3 配置

引入 JPA starter，Hibernate 版本交给 Spring Boot BOM 管理；数据库驱动按实际环境另行添加。

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
```

常用 `application.yml`：

```yaml
spring:
  jpa:
    open-in-view: false
    hibernate:
      ddl-auto: validate
    properties:
      hibernate:
        format_sql: true
        jdbc:
          batch_size: 50
        order_inserts: true
        order_updates: true
```

- `open-in-view: false`：将持久化上下文限制在事务边界内，避免 Web 层意外触发懒加载；需要的数据应在 Service 事务内查询完整。
- `ddl-auto: validate`：只校验实体映射与数据库结构。生产环境应使用 Flyway、Liquibase 等迁移工具管理 DDL，不使用 `update` 自动改表。
- `batch_size`：开启 JDBC 批处理，具体大小要结合驱动和压测确定；使用 `IDENTITY` 主键生成策略时，实体插入通常无法批处理。
- `order_inserts` / `order_updates`：按实体和主键重排同类 SQL，提高组成批次的机会。
- 方言通常可由 Hibernate 根据 JDBC 元数据识别，无需固定 `hibernate.dialect`。

本地排查 SQL 时可按需开启日志，参数绑定日志可能包含敏感信息，不应长期用于生产环境：

```yaml
logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE
```

单数据源场景下，Spring Boot 会自动配置 `EntityManagerFactory` 和 `JpaTransactionManager`；只有多数据源或特殊定制时才需要手写这些 Bean。

### N+1 问题

`LAZY` 只能推迟关联加载，不能自动解决 N+1。查询出 N 个主实体后，如果循环访问尚未加载的关联属性，就可能额外执行 N 次查询。

常见治理方式：

- 使用 JPQL/HQL `join fetch` 一次抓取当前场景所需的关联。
- 使用 Spring Data JPA `@EntityGraph` 声明抓取图。
- 使用批量抓取，将 N 次查询合并为少量 `IN` 查询。
- 面向查询结果使用 DTO 投影，避免加载不需要的完整实体图。

## MyBatis / MyBatis-Plus 核心机制

- **显式 SQL**：SQL 通常写在 XML 或注解中，开发者直接控制查询条件、关联方式和返回列。
- **映射机制**：Mapper 接口定义调用入口，MyBatis 负责参数绑定，并通过自动映射或 `ResultMap` 组装结果。
- **动态 SQL**：MyBatis 使用 `if`、`where`、`foreach` 等 XML 标签或 SQL Provider 生成 SQL；Wrapper 属于 MyBatis-Plus。
- **MyBatis-Plus 增强**：`BaseMapper` 提供通用单表 CRUD；`LambdaQueryWrapper`、`LambdaUpdateWrapper` 等 Wrapper 负责构造查询或更新条件。
- **实体状态**：MyBatis 不维护 JPA 式持久化上下文，也不做脏检查；新增、修改和删除通常需要显式调用对应 Mapper 方法。
- **关联查询**：可以使用 JOIN + `ResultMap` 一次组装，也可能因嵌套查询或循环调用 Mapper 产生 N+1。

### MyBatis-Plus 常见扩展

- **乐观锁**：实体版本字段使用 `@Version`，并配置 `OptimisticLockerInnerInterceptor`。
- **逻辑删除**：字段使用 `@TableLogic` 或全局配置逻辑删除规则。
- **动态表名**：配置 `DynamicTableNameInnerInterceptor`，在运行时替换 SQL 中的表名。

### MyBatis-Plus 的 Spring Boot 3 配置

Boot 3 使用专用 starter。使用分页插件时，从 MyBatis-Plus 3.5.9 开始还要显式引入 JSQLParser 模块；版本应通过项目属性集中维护。

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
    <version>${mybatis-plus.version}</version>
</dependency>

<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-jsqlparser</artifactId>
    <version>${mybatis-plus.version}</version>
</dependency>
```

常用 `application.yml`：

```yaml
mybatis-plus:
  mapper-locations: classpath*:/mapper/**/*.xml
  type-aliases-package: com.example.persistence.entity
  configuration:
    map-underscore-to-camel-case: true
  global-config:
    db-config:
      logic-delete-field: deleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

- `mapper-locations`：指定 Mapper XML 路径；使用默认目录且不写 XML 时可以省略。
- `type-aliases-package`：替换成项目实体包，仅在 XML 中使用类型别名时需要。
- `map-underscore-to-camel-case`：将 `user_name` 等列名映射到 `userName` 属性。
- `logic-delete-field`：按统一字段名启用全局逻辑删除；如果只在部分实体上使用 `@TableLogic`，可省略该项。

分页和乐观锁通过统一拦截器注册，分页拦截器应放在其他 SQL 改写插件之后：

```java
import com.baomidou.mybatisplus.extension.plugins.MybatisPlusInterceptor;
import com.baomidou.mybatisplus.extension.plugins.inner.OptimisticLockerInnerInterceptor;
import com.baomidou.mybatisplus.extension.plugins.inner.PaginationInnerInterceptor;
import org.mybatis.spring.annotation.MapperScan;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
@MapperScan("com.example.persistence.mapper")
public class MyBatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor());
        return interceptor;
    }
}
```

- `@MapperScan` 的包名替换为项目 Mapper 包，配置后无需在每个接口上重复添加 `@Mapper`。
- 单一数据库类型确定时，可给 `PaginationInnerInterceptor` 指定对应 `DbType`；数据库无关或多数据源场景可不固定。
- Spring Boot 会自动配置 `SqlSessionFactory` 并接入 Spring 事务，普通单数据源项目无需手写。
- 本地排查 SQL 时调整 Mapper 包的日志级别即可，不建议使用 `StdOutImpl` 作为生产日志实现。

## 核心对比

| 维度 | Hibernate / JPA | MyBatis / MyBatis-Plus |
| --- | --- | --- |
| 抽象中心 | 实体及其生命周期 | SQL 及其执行结果 |
| SQL 生成 | 框架根据映射和查询模型生成 | 开发者编写，MP 可生成通用 CRUD SQL |
| SQL 控制力 | 较间接，需检查最终 SQL | 直接，适合精细优化 |
| 状态管理 | 有持久化上下文、脏检查 | 无实体状态跟踪，操作更显式 |
| 关联处理 | 注解映射、级联和抓取策略 | JOIN、嵌套查询和 `ResultMap` |
| 动态查询 | Criteria、Specification、QueryDSL | 动态 SQL、Provider、Wrapper |
| 复杂查询 | 可用 JPQL/HQL，必要时使用原生 SQL | 直接编写 SQL，更贴近数据库能力 |
| 主要风险 | N+1、懒加载异常、生成 SQL 不符合预期 | SQL 分散、映射维护成本、数据库方言耦合 |
| 适用场景 | 领域模型和关联关系较丰富的业务系统 | 复杂查询、报表、遗留库和 SQL 优化要求高的系统 |

## 事务处理

两者都能参与 Spring 声明式事务，事务能力最终建立在 Spring 事务抽象和数据库事务之上，不应简单比较谁“更支持事务”。

- Hibernate/JPA 通常由 `JpaTransactionManager` 管理；事务提交前会刷新持久化上下文，将脏检查结果同步到数据库。
- MyBatis 通常通过 MyBatis-Spring 接入 `DataSourceTransactionManager`；Mapper 执行 SQL 的时机更加显式。
- 两者都要关注传播行为、隔离级别、回滚规则以及事务边界；不要在同一业务链路中误用不同事务管理器，导致操作未处于同一事务。

## 常见追问

### `LAZY` 是否能避免 N+1？

不能。它避免的是不需要关联数据时的过早加载；如果随后逐条访问关联，仍会触发 N+1。

### Hibernate 会在修改对象后立即执行 `UPDATE` 吗？

不一定。托管实体通常先在内存中变更，Hibernate 在 `flush` 时根据脏检查结果执行 SQL。

### MyBatis 是否完全没有 N+1？

不是。嵌套 Select、循环调用 Mapper 或逐条补查关联数据都会产生 N+1。

### 如何做技术选型？

- 领域模型稳定、关联操作多、希望减少通用持久化代码：优先考虑 Hibernate / Spring Data JPA。
- SQL 复杂、依赖数据库特性、需要精细调优或对接遗留表结构：优先考虑 MyBatis / MyBatis-Plus。
- 同一系统可以按模块混用，但应统一事务边界，并避免为简单需求同时引入两套持久化模型。
