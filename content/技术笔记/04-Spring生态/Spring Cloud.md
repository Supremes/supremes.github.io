## 一句话结论

Spring Cloud 不是单个框架，而是一套围绕微服务治理问题的组件族：注册发现、配置、调用、网关、容错、消息和观测性。

## 30 秒口述

单体拆成微服务后，核心问题从“代码怎么写”变成“服务之间怎么找、怎么调、怎么配、怎么兜底、怎么观测”。Spring Cloud 就是围绕这些问题给出一组约定和组件。面试时不要只背组件名，更要把“它解决什么分布式问题”讲清楚。

## 组件地图

| 问题 | 常见组件 | 面试重点 |
| --- | --- | --- |
| 服务注册与发现 | Eureka、Nacos | 服务实例如何注册、心跳、下线、消费端如何拿实例列表 |
| 配置中心 | Spring Cloud Config、Nacos Config | 配置集中管理、动态刷新、环境隔离 |
| 服务调用 | OpenFeign、Spring Cloud LoadBalancer | 声明式调用、超时、重试、负载均衡 |
| API 网关 | Spring Cloud Gateway | 统一入口、路由、鉴权、限流、灰度 |
| 容错限流 | Resilience4j、Sentinel | 熔断、降级、限流、舱壁 |
| 消息与事件 | Spring Cloud Stream、Bus | 异步解耦、配置广播 |
| 链路追踪 | Micrometer Tracing、Zipkin、SkyWalking | TraceId 贯穿调用链 |

## 高频面试点

### 1. 注册中心解决的到底是什么问题

- 不是“把 IP 记到某个地方”这么简单，而是把 **实例上下线、健康检查、消费端感知变更** 标准化。
- 典型口述：服务启动后注册自己，注册中心维护实例列表，消费端拉取或订阅变更，再结合负载均衡策略选一个实例调用。

### 2. OpenFeign 和 Gateway 不要混

- **Gateway**：统一入口，面对外部流量。
- **OpenFeign**：服务与服务之间的内部调用。
- 两者经常一起出现，但解决的问题不一样。

### 3. 配置中心不只是“集中放配置”

- 真正价值是环境隔离、版本管理、热更新和权限治理。
- 动态刷新常会被追问到 `@RefreshScope` 或总线广播思路。

### 4. 熔断和重试不能乱配

- 只会“开重试”很危险，请求风暴会把下游打得更惨。
- 面试里更稳妥的说法是：**超时、重试、熔断、降级要一起设计**。

## 版本与生态口径

- `Ribbon`、`Hystrix`、`Zuul` 这套 Netflix 经典栈要知道，但最好主动补一句：**现在很多项目已转向 `LoadBalancer`、`Resilience4j`、`Gateway`**。
- Spring Cloud 和 Spring Boot 强依赖版本兼容，面试时可以顺手提一句“先看版本矩阵”。

## 常见追问 / 坑

- **注册中心挂了，服务还能不能调**：很多场景下，已缓存的实例列表还能支撑一段时间，但新实例注册、变更感知会受影响。
- **为什么网关不能完全替代 Nginx**：两者职责不完全重合，Nginx 更偏通用反向代理和边缘接入，Gateway 更懂 Spring 生态和业务路由。
- **为什么微服务更依赖监控和追踪**：因为一次请求会穿过多个进程，不再能靠单机日志定位问题。
- **单体项目值不值得上 Spring Cloud**：不是默认值得，先看团队规模、交付复杂度、部署和治理成本。

## 面试答题顺序建议

1. 先讲“微服务带来的治理问题”。
2. 再按注册发现、调用、配置、网关、容错、追踪分层讲组件。
3. 最后补版本演进和踩坑认知。
