## 一句话结论

Spring AOP 的本质是“代理拦截方法调用”，声明式事务只是这个代理链里最常见的一种增强。

## 30 秒口述

Spring 容器里注入到业务代码中的，很多时候不是原始对象，而是代理对象。外部调用先进入代理，代理按切点命中通知链，再调用目标方法。事务场景里，这条通知链会在方法前开启事务、方法后决定提交或回滚。所以只要绕过代理，比如自调用，AOP 和事务通常都会一起失效。

## AOP 代理怎么答

### 核心调用路径

`外部调用 -> Proxy -> Advice / Interceptor Chain -> Target`

### JDK 动态代理 vs CGLIB

| 维度 | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 主要前提 | 目标类有接口 | 通过生成子类代理 |
| 常见印象 | 更“接口导向” | 更“类代理导向” |
| 核心限制 | 主要面向接口方法 | `final` 类 / 方法不友好 |
| 面试重点 | 二者本质都是代理，不解决自调用问题 | 常见于 Spring Boot 默认类代理场景 |

### 通知类型速记

- `@Before`：方法前
- `@AfterReturning`：成功返回后
- `@AfterThrowing`：抛异常后
- `@After`：最终收尾
- `@Around`：最强，前后都能包

## 事务是怎么挂到 AOP 上的

### 关键角色

- `@Transactional`
- `TransactionInterceptor`
- `PlatformTransactionManager`

### 执行逻辑

1. 代理命中事务切点。
2. `TransactionInterceptor` 判断当前线程是否已有事务。
3. 按传播行为决定加入、创建、挂起还是报错。
4. 目标方法执行后，根据异常情况决定提交或回滚。

## 传播行为速记

| 传播行为 | 面试口径 | 常见场景 |
| --- | --- | --- |
| `REQUIRED` | 有就加入，没有就新建 | 默认值，最常见 |
| `REQUIRES_NEW` | 挂起外层，自己开新事务 | 审计日志、独立落库 |
| `NESTED` | 复用外层事务，但打保存点 | 局部可回滚场景 |

## 隔离级别速记

| 隔离级别 | 主要解决什么问题 | 面试常说法 |
| --- | --- | --- |
| `READ_COMMITTED` | 脏读 | 很多数据库默认或常见选择 |
| `REPEATABLE_READ` | 不可重复读 | MySQL 高频口径 |
| `SERIALIZABLE` | 并发问题最少，性能最重 | 了解即可，少作默认推荐 |

## 事务失效高频清单

1. **自调用**：`this.xxx()` 直接绕过代理。
2. **对象不是 Spring Bean**：自己 `new` 的对象没有代理。
3. **异常被吃掉**：异常没继续抛出，事务感知不到。
4. **受检异常没声明回滚**：默认只回滚 `RuntimeException` / `Error`。
5. **异步或新线程**：线程上下文切了，事务通常不会自然传播过去。
6. **方法可见性或代理限制**：面试里最稳妥的口径仍是把事务放在 `public` 方法上。
7. **选错事务管理器**：多数据源场景尤其容易出错。

## 自调用为什么失效

### 根因

外部调用走的是 `Proxy -> Target`；自调用走的是 `Target -> this.method()`。第二条路径没有经过代理，自然没有事务拦截器。

### 解决优先级

1. **拆分到独立 Service**：最推荐，职责更清晰。
2. **自我注入代理对象**：可用，但要控制复杂度。
3. **`AopContext.currentProxy()`**：能救火，但侵入性强，不是首选。

## 常见追问 / 坑

- **换成 CGLIB 能解决自调用吗**：不能。问题是“绕过代理”，不是“代理类型不对”。
- **`readOnly = true` 是不是绝对不能写**：不是，更多是优化提示和语义表达。
- **`REQUIRES_NEW` 有没有代价**：有，会额外占用数据库连接。
- **事务和数据库隔离级别谁说了算**：Spring 负责声明，最终由底层数据库实现。
