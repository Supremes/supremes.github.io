> **问题**：Dawn-Springboot 作为 Spring Boot + MyBatis Plus 的单体博客 / CMS，功能完整，但存在依赖注入、事务边界、日志追踪、缓存和线程池等方面的技术债。  
> **决策**：从代码缺陷、性能瓶颈、可观测性和现代化演进四条线做审计，并给出分阶段重构路线。  
> **结果**：沉淀出一份按优先级排序的风险清单和演进路线图，可直接用于项目深挖回答。  
> **可追问**：为什么字段注入不推荐、事务为什么要缩小边界、缓存一致性怎么处理、为什么要引入链路追踪。

## 1. 项目概况

- 项目形态：基于 Spring Boot + MyBatis Plus 的单体博客 / CMS。
- 已接入能力：Redis、RabbitMQ、Elasticsearch、策略模式封装的上传与搜索等。
- 整体判断：功能完备，但在高并发稳定性、代码整洁度和现代 Spring 最佳实践上仍有明显技术债。

## 2. 核心缺陷分析

### 2.1 依赖注入反模式：字段注入过多

**问题**：

- 大量使用字段注入，组件与 Spring 容器强耦合。
- 依赖关系不显式，也不利于单元测试和不可变设计。

**建议**：

- 统一改为 **构造器注入 + `final` 字段**。
- 如果一个类构造器参数很多，也能反向暴露“类职责过重”的问题。

```java
@Service
@RequiredArgsConstructor
public class ArticleServiceImpl extends ServiceImpl<ArticleMapper, Article> implements ArticleService {

    private final ArticleTagMapper articleTagMapper;
    private final RedisService redisService;
}
```

### 2.2 事务粒度失控

**问题**：

- 事务方法如果把文件上传、缓存清理、消息发送等耗时 I/O 一起包进去，会长时间占用数据库连接。

**风险**：

- 高并发下容易出现连接池被占满，系统响应抖动甚至假死。

**建议**：

- 事务只包真正的数据库操作。
- 非 DB 逻辑尽量移出事务，必要时用 `TransactionTemplate` 精细化控制。

### 2.3 异常处理与日志链路不完整

**问题**：

- 局部 `try-catch` 容易把异常语义和堆栈信息吃掉。
- 异步链路或 MQ 消费缺少统一 TraceId 时，排障成本会明显上升。

**建议**：

- 统一异常出口，避免 `e.printStackTrace()` 这类写法。
- 升级到 Spring Boot 3 体系时，用 Micrometer Tracing 替代旧 Sleuth 方案。

### 2.4 DTO / VO 过于贫血

**问题**：

- 仅承载数据的 DTO / VO 充斥大量样板代码。

**建议**：

- 在 Java 17+ 目标下，可对只读传输对象尝试使用 Record，减少样板和提升语义清晰度。

## 3. 性能瓶颈预警

### 3.1 MyBatis Plus 的 N+1 查询隐患

- 如果在文章、评论等场景里循环查标签、用户信息，会放大数据库压力。
- 优先考虑 `IN` 查询做内存组装，或者系统性重写查询模型。

### 3.2 Redis 缓存一致性与击穿防护不足

- 只有基础缓存读写还不够，热点数据场景要考虑击穿、穿透和更新一致性。
- 可以考虑多级缓存、分布式锁、布隆过滤器等组合策略。

### 3.3 线程池参数硬编码

- 线程池核心参数如果写死，流量波动时很难按环境调整。
- 建议外置到配置文件，并接入监控指标观测队列长度和拒绝次数。

## 4. 建议补齐的架构能力

### 4.1 升级到 Java 21 / Spring Boot 3.2+ 后再评估虚拟线程

- 这个方向针对 I/O 密集任务很有价值，但前提是先把基础升级和兼容性做好。

### 4.2 以 WebClient 替代旧式同步 HTTP 调用

- 如果项目存在第三方抓取或导入场景，WebClient 更符合现代 Spring 风格。

### 4.3 动态配置能力

- 上传策略、敏感词、开关类配置如果要频繁调整，最好有运行时热更新能力。

### 4.4 领域事件解耦长链路业务

- “发布文章 -> 更新索引 -> 推送通知 -> 记录日志” 这类长链路写在一个 Service 方法里，可读性和扩展性都差。
- 可以考虑 Spring Event 做解耦，再按同步 / 异步需求拆监听器。

## 5. 建议的重构路线图

### Phase 1：基础夯实

1. 升级到 Java 17。
2. 批量整改为构造器注入。
3. 梳理连接池和事务边界。

### Phase 2：性能与观测

1. 引入多级缓存思路。
2. 补链路追踪和业务指标。
3. 做慢 SQL 与索引治理。

### Phase 3：架构解耦

1. 引入事件驱动拆长链路。
2. 评估模块化单体或轻量 DDD 的落地方向。

## 6. 面试表达建议

如果被问“你怎么看这个项目的架构问题”，可以按这条线答：

1. **先肯定**：单体形态下，技术栈已经覆盖缓存、搜索、消息和安全。
2. **再指出关键债务**：字段注入、事务边界、链路追踪、缓存一致性、线程池配置。
3. **最后给演进优先级**：先稳态与可观测，再性能，再模块化改造。
