> **问题**：Dawn 已经具备较完整的 Spring Boot 单体项目形态，但如果想从“能跑”走向“更稳、更清晰、更可演进”，还需要系统性改造。  
> **决策**：从架构演进、设计模式、高并发与性能、代码质量、观测性五个维度提出改造建议，并安排为分阶段行动路线。  
> **结果**：得到一套可对外讲清楚“为什么这么改、先改什么、参考了什么项目”的项目升级蓝图。  
> **可追问**：为什么先做模块化单体、责任链能解决什么问题、缓存和 MQ 的可靠性怎么补、为什么要先补观测性。

## 1. 架构演进：先做模块化单体，再谈微服务

当前项目更像典型三层结构：

`Controller -> Service -> Mapper -> Entity`

这套结构能跑，但容易把业务逻辑全部堆进 Service 层。

### 建议

1. **先引入模块化单体思路**：按业务领域重新组织包结构，比如用户、博客、系统管理。
2. **再逐步引入 DDD 思想**：把状态流转、业务规则从“Service 的 if-else”下沉到领域对象。

### 为什么不是先拆微服务

- 微服务先引入的是治理成本，不是业务价值。
- 如果单体内部边界都没梳理清楚，拆出去只会把混乱从进程内搬到进程间。

### 可参考

- [Halo](https://github.com/halo-dev/halo)
- [Spring Modulith 官方示例](https://github.com/spring-projects/spring-modulith)

## 2. 设计模式实战：把“巨型方法”拆掉

项目已经有策略模式的影子，这是好基础，但还能继续往前走。

### 建议

1. **责任链模式**：把发布文章这种长流程拆成内容审查、摘要提取、正文保存、标签处理、索引更新、通知推送等节点。
2. **工厂模式 + Spring 自动装配**：把“接口实现到策略映射”的装配交给 Spring，减少手写分发。
3. **状态模式**：用于审核、作业或任务状态流转。

### 可参考

- [Apache ShenYu](https://github.com/apache/shenyu)

## 3. 高并发与性能：从“有 Redis / MQ”升级到“真正能扛边界场景”

### 缓存治理

- 只接了 Redis 不等于缓存设计完整。
- 热点数据要补击穿、穿透、一致性和多级缓存策略。

### 线程池治理

- 不要把线程池参数硬编码。
- 要能说明核心线程数、队列大小、拒绝策略和优雅关闭是怎么定的。

### MQ 可靠性

- 如果 MQ 用来发邮件、建索引、异步通知，就要继续补：
  - 重试
  - 死信队列
  - 幂等消费

### 可参考

- [mall](https://github.com/macrozheng/mall)

## 4. 代码质量：把“能跑的代码”提升为“可持续维护的代码”

### 建议

1. 补入参校验，减少手写空值判断。
2. 统一异常响应结构，沉淀业务错误码。
3. 减少样板代码和隐藏依赖，优先构造器注入。

> 这份路线图保留原文中的测试建议，但在当前知识库重构里不额外扩写实现步骤。

## 5. 观测性：不只看 CPU 和内存

如果项目已经有 Grafana / Docker Compose 之类基础设施意识，下一步要回答的是：

- TraceId 是否能贯穿请求、异步任务、MQ 消费？
- 有没有业务指标，如登录失败次数、搜索耗时、文章发布耗时？
- 指标对应的告警阈值和容量判断是什么？

### 建议

- 使用 Micrometer Tracing 做链路追踪。
- 使用 Micrometer Counter / Gauge / Timer 做业务指标。

### 可参考

- [Spring Boot PetClinic](https://github.com/spring-projects/spring-petclinic)

## 6. 行动路线图

### 第一阶段：先补稳态能力

1. 梳理依赖注入方式和事务边界。
2. 补统一异常处理、入参校验、核心链路日志。
3. 把线程池参数和关键开关外置配置。

### 第二阶段：再做高收益重构

1. 拆巨型 Service 方法。
2. 改造缓存和 MQ 可靠性。
3. 补业务指标和链路追踪。

### 第三阶段：最后做架构升级

1. 评估模块化单体。
2. 按业务边界引入领域事件。
3. 在边界稳定后，再考虑更重的分布式拆分。

## 7. 面试表达建议

如果面试官问“你会怎么继续演进这个项目”，可以按下面的顺序讲：

1. **先稳态**：事务边界、异常处理、线程池、监控。
2. **再解耦**：模块化、责任链、事件驱动。
3. **最后扩展**：缓存体系、MQ 可靠性、必要时再谈微服务。
